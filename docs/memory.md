# Memory and Dreaming

MatoLoop projects four memory layers into a normal project model request:

1. Canonical current-session context, compacted when necessary.
2. Every audience-visible pinned durable memory in full.
3. A compact index of recent project sessions.
4. Bounded automatic snippets from relevant unpinned durable memories and prior sessions.

When enabled, a saved Dreaming session summary participates in automatic session selection alongside original-message passages. The existing episode index makes its text available to PostgreSQL full-text search and queues its vector for the existing embedding worker. No additional query embedding or model call is needed. Sessions without a summary remain discoverable immediately. The project-session index, explicit original-message search, and current-session compaction are independent of summary search.

A selected session can supply a bounded summary and its matching original passage, with a link to that passage. A topical anchor newer than the summary's watermark uses the original passage instead. Automatic lexical ranking can also match informative words from the current message even when the full query, including the preceding turn, does not match a passage. This lets names mentioned only in conversation contribute without being registered as projects or integrations.

Durable memory and prior-session retrieval are independent. A conversation does not need to be processed by Dreaming before it can be found as prior-session context.

Project instructions are a separate optional authoritative layer for deliberately maintained project rules and decisions. Automatic project awareness comes from the compact project-local session index and bounded snippets of other owned sessions in that project; instructions do not replace the project history. Ambiguous requests use the current project as their topic, not unrelated memories. External sources may inform a solution but do not establish the current project's state.

The maintained user profile is separate from memory. Its full name, preferred name, form of address, pronouns, primary language, and primary residence are projected independently of `memoryMode`, are never embedded or searchable, and appear between the assistant persona and project context. Each field can define a shared, private-model-only, or public-model-only value; a trust-specific value overrides the shared value. Exact case- and whitespace-normalized profile duplicates are excluded from memory projection and retrieval.

## Access, Scope, and Trust

Each session has a mutable `memoryMode`:

- `full` can receive memory context, search memories through `context_search`, use `memory_browse` and `memory_write`, and act as a Dreaming and automatic prior-session source.
- `read_only` can receive memory context, search memories, and use `memory_browse`, but cannot write memories, run Dreaming, or act as an automatic prior-session source.
- `disabled` receives no automatic memory context and cannot browse or write memories or act as an automatic prior-session source. Permission-controlled conversation search remains available through `context_search`.

The owner memory switch and effective provider and model memory policies can further restrict model-facing memory. Tool support affects memory tools and Dreaming, but not host-side automatic retrieval. The authenticated UI can still search and manage durable memories while these switches are off. Authenticated global session search and explicit permission-controlled `session_browse`, `context_search`, and `session_read` also continue to cover owned `read_only` and `disabled` sessions.

Automatic relevant and recent prior-session retrieval uses only other `full` chat sessions owned by the same user. In project sessions, both searches filter to the current project before ranking and limits, without filling empty results from other projects. Standalone sessions retain owner-wide retrieval. Explicit conversation search and `session_browse` do not require the automatic `full` source mode. The current receiving session may be `full` or `read_only`. Retrieval filters by owner and excludes the current session before ranking unless an explicit search targets its exact ID. Public models receive only public source sessions, including titles and the project index; private models may receive both classifications. Cached automatic references revalidate session trust and applicable project membership before reuse. A project request additionally receives up to ten recent eligible `full` sessions from the same project, ordered by their latest eligible message. Each index item contains only its bounded title and exact `session_read` arguments for that latest message, never message content. Selecting the model is the release decision for the current session's already authorized messages; durable-memory audience filtering remains independent.

Durable memories and prior-session snippets are untrusted data, never instructions. Conflict priority is:

1. Current user message
2. Maintained user profile
3. User-configured project instructions
4. Pinned durable memory
5. Automatically retrieved or explicitly loaded durable memory
6. Prior-session snippet or transcript

## Automatic Context

Every eligible normal turn builds one query of at most 2,000 characters from the latest user message. When that message is short, the query includes the previous user message as follow-up context. The host computes at most one query embedding and shares it across searches for unpinned durable memories and relevant prior sessions. Memory source provenance does not affect automatic eligibility. Both searches combine PostgreSQL FTS and local cosine ranking; unavailable or invalid embeddings fall back to FTS.

When the latest user message explicitly names an enabled integration available in the current profile or the current project, the existing full-text indexes can prioritize one matching result per source. The surrounding query ranks matches for that name; the remaining slots keep the normal ranking. This lookup does not widen access, increase context budgets, or change explicit `context_search` queries.

The ranked results are cached across tool rounds in one agent run to avoid repeated embedding work. Before every later model request, the host reloads pins and revalidates cached automatic memories against current owner, audience, pin, and source state and cached episode references against current owner, current-session exclusion, source-session mode, and applicable project membership. Historical automatic memory envelopes use the same project boundary; incompatible old envelopes are omitted rather than rewritten at later turns.

The configurable fixed quotas default to:

- two relevant unpinned memory snippets through `automaticMemorySnippetLimit`;
- three relevant prior-session snippets through `automaticSessionSnippetLimit`;
- two recent-session snippets for first-turn bootstrap or explicit recent-session overview through `recentSessionSnippetLimit`.

An explicit request not to use memory or prior context, and detected requests that only transform supplied text, suppress automatic snippets. The first turn and explicit recent-session overview may add recent snippets; relevance retrieval still uses the same turn query. Duplicate source sessions are removed. Project requests prioritize relevant snippets from distinct owned sessions, then non-overlapping recent snippets, then unpinned memories. Standalone requests retain the smaller single relevant-session maximum and give recent snippets precedence.

The complete serialized automatic payload shares `automaticContextMaxTokens`, defaulting to 1,024 tokens and capped at 10% of usable raw input. This is a content quota, separate from request-estimation safety margins. The project-session index uses at most 2,000 characters and half the automatic budget. Snippets are shortened or omitted to fit using the model's character estimate; quotas are maxima, not guarantees. [Model Context Settings](harness.md#model-context-settings) defines usable input, reserves and final allocation once for all context consumers.

Visible pins are serialized in full outside the automatic snippet budget. Projection tries pins plus automatic snippets, then pins only, and fails safely if all visible pins and required context cannot fit. Pins are never silently truncated or dropped.

Each turn's selected host-marked memory envelope is snapshotted in its user message's private metadata and prepended to that user message in the model request, never represented as an assistant answer. Filenames in this envelope do not reactivate historical images or consume the current image budget. Retained envelopes replay at their originating turns, with identical consecutive envelopes emitted once, not moved before each new request. Before replay, owner, audience, revision, source eligibility, model trust and applicable project membership are revalidated; an invalid source discards the envelope. Disabled/suppressed context is not restored, legacy turns are not backfilled, and only the latest envelope describes current retrieval scope. The stable prompt defines these envelopes as reference data, not user requests or output to reproduce.

Selected summaries are loaded once per run and frozen across tool rounds; later requests revalidate source eligibility and the source revision without replacing their text with a newly generated summary. Historical summary envelopes retain their original content even when Dreaming creates a newer snapshot. Source-history invalidation and disabling summaries suppress those envelopes. Summary updates do not change session activity timestamps, tools, schema order, provider cache routing, or the stable system prefix. Summary-specific reading guidance appears only in turn-local envelopes containing summaries.

An automatic memory hit contains a short canonical-content preview and stable ID and revision. A relevant-session hit contains the strongest bounded topical anchor and exact `session_read` arguments; a recent hit contains a small tail. The project-session index points separately to the latest eligible message in each listed session so the model can read current details instead of treating an older semantic anchor as the final state. These references are discovery context, not complete evidence. `context_search` loads durable-memory details and matching conversation passages, while `session_read` loads required transcript detail or attachments under its exact permission boundary.

When `session_read` is available, the late memory context instructs the model to use sufficient excerpts directly and read missing details from matching supplied session references before asking the user to repeat information or claiming that prior context is unavailable. For the latest state, it prefers the project-session index over an older topical anchor. This guidance also applies when only the project-session index is supplied, without adding automatic retrieval or changing the stable system prompt.

Explicit durable-memory overview intent uses bounded chronological prefetch and continuation state while still injecting every visible pin in full. `memory_browse`, `context_search`, `session_browse`, and `session_read` remain available for deliberate retrieval beyond automatic quotas. Assistant provider metadata records injected durable-memory and prior-session counts without duplicating their content.

Plan and Build use relevant supplied context. Saved memories and conversations outside the current project require explicit user retrieval intent or a reference to those sources; missing context alone is insufficient. For the current coding task, relevant sessions in the same project may be inspected when needed using `context_search(scope="sessions", all_projects=false)` and `session_read`, not a broad memory search or a routine scan of every session. Existing permissions and model-trust boundaries still apply. Required retrieval for explicitly requested memory mutations remains allowed. The shared runtime instructions are visible in the profile editor and also reach inherited and delegated profiles.

These profile instructions also govern retrieval hints in supplied references; they do not change automatic context injection, tool availability, or runtime permissions. Changes to this static prompt contract intentionally invalidate affected provider prefixes so current instructions apply; historical turn snapshots, schema order, and cache routing remain unchanged.

## Durable Memory

A durable memory stores canonical content, category, audience, source provenance, revision, evidence links, seen state, and `pinned`. Categories remain `context`, `fact`, `goal`, `identity`, and `preference`; dated experiences use `fact`, not a separate event category. Sources are `manual`, `tool_call`, and `dreaming`. Provenance describes origin, not whether automatic mutations are permitted. Normalized content hashes prevent case- and whitespace-equivalent duplicates.

Pinned records are supplied in full on every allowed model request. Any unpinned record can appear automatically as a relevant short snippet regardless of whether its source is `manual`, `tool_call`, or `dreaming`; full details remain available through `context_search` and `memory_browse`. MatoLoop does not expire or delete memories because of age, non-mention, weak relevance, capacity, exposure, or usage counts.

`memory_write` persists explicitly requested durable information and durable first-person context stated directly in the latest user message. It excludes temporary situations, hypotheticals, quotations, transformation source text, and incidental facts about third parties. An explicit request to always consider the information can pin the result; ordinary remember wording does not pin. Updates and explicit forgetting require an injected or retrieved memory ID and revision and recheck ownership, visibility, and stale-write protection.

`context_search(query, scope="all", session_id=None, all_projects=False, include_private=False, limit=3)` searches durable memories and indexed conversations together. `scope` may restrict it to `memories` or `sessions`; supplying `session_id` restricts the call to that exact conversation and cannot be combined with `scope=memories`. Conversation passage and title searches default to the current project when selected. A concrete cross-project need can use `all_projects=true` or an exact session ID without requiring a separate user confirmation; empty local results alone do not justify widening. Neither option widens ownership, trust, permissions, or durable-memory audiences. Public models search public sessions by default. Including private sessions in discovery or searching a known private session requires `session.read_sensitive` (category `read_sensitive`), as does reading another private session with `session_read`. Private models use ordinary read permissions for either classification. `include_private` also applies to `session_browse` and legacy `session_search`; it never widens durable-memory audiences. `limit` is capped at ten results per source. Memory results contain the full content, ID, revision, category, audience, pin state, provenance, and timestamps. Conversation results contain the matching indexed passage, its message and session IDs, source project ID, observation time, and exact reading arguments. Explicit search may return several passages from the same conversation. Automatic retrieval retains its distinct-session ranking and quotas.

Explicit conversation queries use PostgreSQL's native web-search parser, preserving dotted addresses and quoted phrases when embeddings are unavailable. Owner-filtered title matches remain discoverable even without a matching message passage; those results contain the title and reading arguments, not invented conversation evidence. The title lookup is shared with the authenticated global search.

The response keeps `memories` and `sessions` separate. Its `sources` map distinguishes `searched`, `unavailable`, and `denied`; an unavailable or denied source is not an empty successful search. Each source uses its existing `memory.read` or `session.search` policy and source-specific tool switch. The legacy `memory_retrieve` and `session_search` configuration entries retain those switches and historical direct-call compatibility, but are not offered to models. Delegation freezes the allowed search sources alongside the existing tool and action ceilings. Historical memory results, including nested context-search results, are audience-filtered again when projected to another model trust level.

Already-authorized sources are resolved before requesting additional approval. Refusing the additional memory request therefore does not cancel an independently allowed conversation search; the refused source remains blocked.

`memory_browse` lists memories chronologically using the existing paired cursor and optional category filter. `memory_write` remains separate; an ordinary search does not start a required-write workflow. Once a write is attempted, its existing repair and outcome guards remain active. Summary retrieval introduces no new model tool, search index, or permission capability.

The authenticated Memory UI retains full search, filtering, create, edit, pin or unpin, and delete access even when model-facing Memory or Dreaming is disabled. Every update and delete uses the record revision so a stale UI action cannot overwrite or delete a newer version.

## Prior-Session Index

`message_search_chunks` is a derived index of completed, non-error, nonempty user text and final assistant text without tool calls. Tool messages, tool output, reasoning, attachment data, runtime-error responses, and incomplete assistant output are excluded; eligible text accompanying an attachment remains searchable.

Chunking is deterministic and paragraph-aware. Each chunk has generated PostgreSQL FTS and a local E5 vector tied to its content and embedding profile. Persistence replaces eligible message chunks in the same transaction, making FTS available immediately; vector generation remains asynchronous. Undo and session deletion remove derived chunks through canonical-message cascades, and reconciliation repairs missing or stale index data.

Automatic hybrid ranking selects at most one primary anchor per source session; explicit context search may return multiple passages. Authenticated global search remains owner-wide, including standalone sessions. UI search may include the current session and all memory modes, while automatic retrieval requires other `full` source sessions within the applicable project boundary and explicit session tools retain their permission checks.

## Dreaming

Dreaming processes completed messages from top-level chat sessions with `memoryMode=full`. Child sessions, incomplete messages, errors, and host-generated tasks or follow-ups are not fresh human evidence. A clear, useful personal statement can qualify on first mention: relationships and useful dates, profession and skills, lasting circumstances, possessions and setups, general preferences, and committed personal goals. Project work, tests, purchases as events, permissions, and maintained profile fields do not qualify. The host checks the original quote and subject against a new human message; the model checks meaning and proposes the stored wording. The five existing categories organize entries, not source eligibility.

An incidental but potentially durable statement requires two supporting human messages from two other eligible sessions. The worker searches a bounded set of older original passages for at most five incidental candidates per batch. Summaries, assistant responses, existing memories, and reprocessing the same source do not count. All three messages are linked. Uncertain interpretation or missing search hits can leave an otherwise useful statement only in the transcript. Repetition does not make a task-local statement eligible.

The owner's `dreamingInstructions` can customize relevance, topics, and detail level. They cannot widen source eligibility, owner/project scope, permissions, evidence requirements, or privacy boundaries. These extraction-contract changes intentionally invalidate the affected isolated helper prefix without rewriting retained chat envelopes. Session summaries, project indexing, and original-message search remain independent and unchanged.

Extraction and model reconciliation check source support before novelty: questions do not establish committed goals, repeated task instructions do not establish general preferences, and assistant-provided details are not independent user evidence. Reconciliation can skip an unsupported candidate even when an existing record contains the same assertion; skipping does not delete that record. Repository coordination and artifact requirements remain searchable project/session history rather than personal memories. Prompts use invented examples only; private evaluation excerpts and reports remain outside repository fixtures. These are model instructions, not a semantic guarantee from citation-ID validation.

The host retrieves matches and plans changes in bounded model batches before acquiring write locks. The model compares candidates within a batch and against earlier planned results within the input budget. The host rejects repeated target IDs and duplicate normalized results, then checks source state, settings and target revisions under lock before committing the changes and checkpoint together. Candidate selection combines exact matching, OR lexical matches, and the existing hybrid retrieval service before its ten-record and 40,000-character bounds. Owner and audience filters apply before retrieval; ordinary project-session retrieval is unchanged. An isolated exact duplicate becomes `unchanged`; other normal candidates enter reconciliation, including unmatched ones so unclear references can be skipped. Reconciliation receives the original human evidence with observation times and the bounded earlier context. Paraphrases and combinations of already known independent facts do not establish new knowledge. A specific statement does not replace a generic possession unless the source identifies the same subject. A removal candidate can target only one normalized exact record; unmatched or unsupported removals are skipped. The action set is:

- `create`: create an independent unpinned durable memory.
- `unchanged`: retain the matching record and add evidence.
- `update`: replace one record's canonical content and category.
- `merge`: combine two to fifty records transactionally.
- `remove`: permanently delete one exact matching record.
- `retire`: remove records that exclusively describe an explicitly ended current state, subject to the removal policy. The event remains in the session and is not saved as a replacement memory.
- `skip`: make no change for an unsupported or unresolved candidate, or a combination already covered by independent records.

One explicit correction can update a known personal fact. A sale can remove the matching device and its attributes without removing unrelated records. An internal owner- and trust-scoped subject/time marker prevents an older statement with the same subject from recreating the ended state. A newer observation can establish a new state. Protected entries and the default `ask` policy require approval before removal. Explicit forgetting still uses the exact-target path. The rules do not bulk-reclassify old memories or purge conversations.

Observation time comes from original message timestamps and existing evidence links, not mandatory dates or "as of" text in canonical memory content. No new temporal database columns are needed. Model-facing memory references distinguish `sourceMessageAt` from `memoryCreatedAt` and `memoryUpdatedAt`. When dated evidence is available, `sourceEvidence` contains at most ten newest `{messageId, observedAt}` references; `sourceEvidenceHasMore` appears only as `true` when that list is truncated. These timestamps date individual source messages, not every clause in merged content. A new evidence link, retrieval, or lifecycle update does not confirm that all content remains current; old evidence must not revert a newer known state.

Extraction and reconciliation retain original source times in the existing chat timezone, Europe/Berlin. For explicit whole-word `heute`, `gestern`, `vorgestern`, `übermorgen`, `morgen`, `today`, `yesterday`, or `tomorrow`, the host additionally supplies optional `calendarDays` references relative to that message's local date, never the processing date. This is a bounded calendar aid, not a general natural-language date parser or automatic discovery of an event. The model still judges whether the expression describes an event, a validity period, or something else, and leaves unclear dates imprecise.

Project events and personal experiences remain searchable in their sessions. Owners can still explicitly save them through manual Memory controls; the automatic restriction does not change the available categories or remove existing records.

Every newly created Dreaming memory is unpinned. Updating or merging records preserves existing pins but never promotes an unpinned record. The source session's current trust determines new memory audiences: public creates `both`, private creates `private_only`. The configured Dreaming model processes either classification without an additional release approval. Session trust is revalidated before mutations and when approving pending changes. Changing session trust does not reclassify existing memories or reset the Dreaming checkpoint. Dreaming never creates `public_only`. With model distinction disabled, sessions are effectively private for Dreaming without overwriting saved classifications. Explicit memory writes also use session trust for the source audience, independently of model trust.

Automatic Dreaming is off by default. Manual and scheduled Dreaming both require an eligible `full` source session, enabled owner memory, and a suitable tool-capable model. Failed work retains its checkpoint and follows bounded retry behavior.

`dreamingReasoningEffort` in model defaults applies to extraction, reconciliation, and session summaries, independently of agent reasoning. Personal defaults inherit the instance value. Without a supported explicit or inherited value, the model/provider default applies, as for the agent model; there is no forced off level. Unsupported inherited levels also fall back to the model/provider default. Changing the selected level changes subsequent provider requests, not stored memories or historical chat envelopes.

The owner UI calls this shared worker **Verarbeitung**. `memoryExtractionEnabled` defaults to true for existing and new settings; `sessionSummariesEnabled` defaults to false. Both procedures can be enabled independently. Manual and scheduled starts run only enabled procedures; with neither enabled, processing is unavailable. Disabling extraction preserves existing memories and its checkpoint, skips queued extraction work, and is rechecked under the settings lock before mutations. Pending extraction approvals expire when extraction is disabled. The shared automatic switch controls scheduling only. Model selection stays in its existing model settings; schedule, message limit, manual start, and run history remain shared. Existing Dreaming API identifiers and URLs are unchanged.

### Session summaries

`sessionSummariesEnabled` is independently off by default. Enabling it records an owner-bound activation time; automatic and unscoped manual work considers only sessions with completed activity since that activation, after the existing idle interval. There is no historical bulk backfill. Explicitly selecting an owned eligible session permits its initial summary regardless of age. Existing durable-memory extraction keeps its source eligibility.

The first summary consumes a bounded original-message prefix. Updates consume only the prior summary and the next bounded completed-message batch, using the same Dreaming model and worker. Each item carries original-message evidence and distinguishes decisions, implementation, verification, superseded statements and open work. The host validates the schema and allowed evidence IDs, and sets the exact coverage watermark. Memory extraction still receives only original source messages, never the summary.

Summary and memory work commit their own progress. Retrying a failed summary does not reapply completed memory mutations, and completed summaries survive a later memory-step failure. Manual retries attach newly prepared summary work to reused extraction runs without replacing completed summary snapshots. Existing bounded run retries apply; unchanged failed summary sources are not automatically restarted indefinitely. Undo/history deletion clears summary snapshots and increments a source revision, invalidating cached and historical model context. Disabling summaries stops generation and automatic use without deleting saved UI-visible results.

The owner UI retains a short recent-run list, with paginated history and a separate run-detail page. New runs store only applied memory changes and their before/after content plus the produced summary, not a general memory-version archive. Pending proposals remain separate and link to existing approvals. Approved later changes append details and update counters in the approval transaction. Older runs retain their existing counters without invented historical details. Explicit memory deletion redacts associated change content; merge carries prior change associations to its survivor so later forgetting also redacts that history. Session deletion cascades run details.

## Policies and Approvals

Automatically extracted records are automatically managed by default, subject to the owner's saved policies. Manually created or owner-edited records always require approval before Dreaming changes, merges, or removes them, including records originally extracted automatically. This protection is independent of source provenance and cannot be bypassed by setting both policies to `auto`. Protected records remain eligible for matching, deduplication, and proposals; they are not hidden from reconciliation. Explicit owner edits and tool-write permissions remain separate.

The persistent `user_managed` flag covers manual and explicitly requested tool writes, owner category/audience/pin changes, and edits made when approving a proposal. It survives automatic provenance changes and merges. Protected duplicate/unchanged paths do not mutate metadata. Migration backfills manual/tool records, pins, and recoverable owner edits in approval history; overwritten historical provenance cannot always be reconstructed safely.

`dreamingIncludeManualMemories` remains an API compatibility field, not an exclusion or protection switch. The UI no longer exposes it. Its value does not exclude protected records from matching or proposals and does not authorize automatic mutation of them.

Dreaming has exactly two mutation policies, each with `disabled`, `ask`, or `auto`:

- `dreamingUpdatePolicy`, default `auto`, governs updates of existing records.
- `dreamingRemovePolicy`, default `ask`, governs removals. The host verifies the evidence source and exact target; whether the wording warrants removal remains a model judgment.

A merge requires both update and removal permission. If either policy is `disabled`, the merge is skipped. If neither is disabled and either is `ask`, one merge approval is created. Only `auto` plus `auto` can apply a merge without approval, and only when no target requires owner approval. Explicitly stored `disabled` and `ask` restrictions remain in force; the new default does not reset them. Creation has no separate policy.

An `ask` decision creates a persistent `memory_change` approval that survives backend restart. Its payload stores exact target IDs, revisions, content, category, audience, pin state, evidence hash, source evidence, proposed result, and both policy snapshots. Approval locks and revalidates the source session, direct evidence where removal requires it, current policies, visibility, and every complete target snapshot. Any stale invariant expires the request without partial mutation.

New Dreaming approvals use the owner's ordinary personal assistant chat as their `ApprovalRequest.session_id`, created or reused in the source transaction without starting an agent run. `payload.sourceSessionId`, `sourceDreamRunId`, and evidence message IDs retain the actual source; communication routing does not change provenance or validation. No existing approvals are copied or moved. In-app and web-push `memoryApproval` targets include the optional decision `sessionId`; legacy targets without it resolve an owner-scoped pending approval and offer a controlled chat link. Run history also exposes each proposal's decision session. Memory settings retain the manual editor, processing controls and history, not a second approval list.

Pending-approval and notification reads reconcile owned Memory proposals with the same side-effect-free validation used before approval. Invalid proposals become `expired`; notices for resolved or missing Memory proposals are removed in the same transaction, including legacy notices. Memory and evidence mutations publish approval invalidations through the existing change stream, so connected clients reload and reconcile. Decisions also reconcile overlapping proposals and remove resolved notices before committing. Final approval still repeats validation under locks; reconciliation never applies a proposed mutation or grants permission.

The owner can edit content, category, audience, and pin state when approving an update or merge. Editing alone writes nothing: the chosen result is applied only with approval, in the same transaction as the approval decision and Dreaming counters. The original proposal and target snapshots remain immutable and must still pass every validation; edits cannot rescue a stale proposal. Accepted edits are recorded separately as `ownerEdit` in the resolved approval payload. Audience and pin changes are explicit owner overrides, including `public_only`, widening visibility, pinning, or unpinning; they do not extend model or automatic Dreaming capabilities. Normalized duplicate protection remains owner-wide across all audiences, including the final chosen audience.

Merge locks all targets in deterministic order, preserves evidence and existing pinning, computes a safe audience, and updates one deterministic survivor before deleting redundant rows in the same transaction. Dream runs report `createdMemories`, `updatedMemories`, and `removedMemories`; approved later mutations update the originating run counters in the same approval transaction.

The redesign migration expires pending approvals created under the retired memory approval contract. Retired merge and pin settings do not carry forward; the current update and removal defaults apply when their new fields are absent.

## API

The authenticated `/api/memories` API provides owner-scoped CRUD, paginated FTS and filters, acknowledgements, Memory settings, and Dreaming runs. JSON fields use camelCase and errors use the central stable error contract.

Create accepts `content`, `category`, and `audience`. Update accepts those fields plus `pinned` and required `expectedRevision`. Delete requires the `expectedRevision` query parameter. Responses include `revision`, pin state, audience, provenance, and timestamps.

`POST /api/approvals/{approval_id}/decisions` accepts optional `memory_edit` alongside `decision: "approve"` for `memory_change` requests with action `memory_update` or `memory_merge`. The edit object requires `content` (trimmed, 1 to 20,000 characters), `category` (`context`, `fact`, `goal`, `identity`, or `preference`), `audience` (`both`, `private_only`, or `public_only`), and Boolean `pinned`; unknown edit fields are rejected. An edit on denial, a removal, or any other approval type is rejected with `validation.invalid` and field `memory_edit`. Omitting the edit or sending null retains the original proposal, safe audience calculation, and existing pin-preservation behavior. Invalid input uses the central safe validation error contract; stale proposals and duplicate conflicts expire with `approval.targetChanged` without applying edits.

Memory settings accept `enabled`, `automaticDreamingEnabled`, `memoryExtractionEnabled`, `sessionSummariesEnabled`, `dreamingInstructions`, `dreamingIntervalMinutes`, `dreamingIdleMinutes`, `dreamingMaxBatchMessages`, `dreamingMaxCandidates`, `dreamingUpdatePolicy`, `dreamingRemovePolicy`, `dreamingIncludeManualMemories`, `automaticMemorySnippetLimit`, `automaticSessionSnippetLimit`, `recentSessionSnippetLimit`, and `automaticContextMaxTokens`. Settings responses additionally expose effective Dreaming availability fields. Partial updates reject null and unknown fields; the summary activation timestamp is host-controlled.

`GET /api/memories/dream-runs` accepts `offset` and `limit` (1–100, default 20), returning `items`, `total`, `offset`, and `limit`. `GET /api/memories/dream-runs/{id}` returns owner-scoped step state, applied `changes`, proposal references, and the summary produced by that run. Failed or invalidated summaries never expose an unfinished source manifest as summary content.

The authenticated `/api/user-profile` API provides owner-scoped `GET` and partial `PATCH`. Changes are merged under the user-scoped settings lock; explicit null removes a value. The optional `phoneNumbers` list contains `{label, number}` entries. A supplied list replaces the previous list; an empty list or null clears it. Phone numbers are not included in model context or exposed to profile tools. The six audience-specific profile facts remain available to normal model requests when Memory is disabled. The host-controlled `update_user_profile` operation changes those facts only after an explicit latest-message request. Its separate `settings.user_profile.update` policy follows the saved trust preset's `write` category unless overridden; the tool resolves the current model to its private or public trust scope and targets both scopes only when explicitly requested. Profile writes have no revision contract; the last completed settings-lock write wins.

## Ownership and Availability

Durable memories, deduplication, Dreaming state and runs, approvals, and prior-session retrieval are scoped by authenticated owner. Memory APIs provide no administrator override into another user's records. Account deletion cascades canonical memories and derived embeddings. Model and session trust plus durable-memory audiences are release classifications inside one owner's data, not user authorization.

Infinity is internal local infrastructure using the pinned multilingual E5 profile. pgvector stores vectors beside canonical data, so no external vector database is required. Separate durable-memory and prior-session workers generate vectors asynchronously with bounded retries and reconciliation. PostgreSQL FTS keeps automatic and explicit retrieval operational while Infinity is disabled, unavailable, or returning invalid data.
