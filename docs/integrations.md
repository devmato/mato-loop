# Integration adapter reference

Integrations extend the host registry without bypassing the normal runtime, ownership or authorization loop. This page defines adapter and product contracts. For setup, use the German [integration guide](user/integrationen.md); for adding categorized actions, use [tool-permissions.md](tool-permissions.md).

## Contribution Types

Each integration instance has a stable UUID, enabled state, typed adapter configuration and encrypted credential reference. The compiled adapter registry is the catalog. Backend adapters support `full`, `instance_only` and `disabled`; owner-bound Agent adapters support `full` or `disabled`. Disabling retains configuration and permits deletion.

An adapter may contribute host-implemented tools, values for explicitly extensible host fields, static tool prompt fragments, or a protected profile while enabled. Each tool declares a typed input, German UI metadata, categorized security actions and host authorization factory. Duplicate names and undeclared configuration contributions fail registry validation. Configuration values do not automatically become model arguments.

Keep each product's adapter/client/service inside `integrations/<product>/`; the root owns shared coordination only. Product identity is independent of transport: SonoBin is a product adapter even though it uses MCP. Generic connectors remain separate fallbacks, not containers for product profiles.

Persisted configuration and remote responses cannot supply handlers, capabilities, matchers, authorization logic or prompt instructions. The bounded MCP tool-schema exception below supplies no execution authority. Approval labels and resource names are display data, never matcher identities.

## Control Center Integrations

An integration may ship one compiled frontend view per type, registered by inert ID, German label, icon and component. Instances stay inside that view and use typed authenticated APIs/stores. Stored settings cannot supply component paths, JavaScript, remote bundles or routes.

Session layout stores bounded app/tab IDs, validated file targets and explorer positions, not editor content. Unknown IDs never load code. Notifications are a global source-linked view, not integration session state; reading or dismissing one does not resolve its source action.

## Execution Locations

`backend` adapters execute inside MatoLoop and cannot be assigned an Agent. `agent` adapters bind exactly one owned Agent, require its selected live connection and a statically known advertised operation. At most one instance of an Agent-adapter kind exists per Agent. A separate authorized computer-switch call may change the run binding between model steps; integration arguments cannot choose a different executor.

Deleting a stored integration requires authorization for its settings scope, not a live or still registered Agent.

The backend owns validation, policies, credentials, approvals and canonical results even when the Agent performs the operation. There is no automatic failover, backend fallback, retry or redelivery after an uncertain effect.

## Resource Policies

Adapters declare static actions and optionally one resource level. A resource loader returns only host-safe stable keys, untrusted labels, applicable declared capabilities and optional presentation groups. It receives validated configuration/credentials, not a database session. Remote ACLs may restrict declared actions but cannot add or enable them. Read-only metadata preflight may establish resource existence and rights before approval; content is not released at that stage.

Each connection owns private/public capability and resource rules. Global connections accept administrator overrides for global profiles; personal connections accept owner overrides for accessible global/owned profiles. Selected-profile rules merge over the baseline; resource entries override capability entries. Missing rules use the declared action default or saved preset. Global built-in tool overrides do not cap integration permissions.

Sparse, trust-independent `resourceAvailability` disables a resource without deleting rules. Profile entries override connection availability. Selection by profile, tool loading and action permission are independent. Resource discovery, aggregate results, execution and delegation apply the same live restrictions.

Permission writes validate ownership, current resource catalog and binding revision. Rebinding clears connection/profile action/resource rules and resource availability while retaining explicit profile connection selection. Deletion removes the instance maps. Grants use connection UUID, revision and resource, not remote labels or operation tokens. [Reusable approvals](tool-permissions.md#reusable-approvals) defines category coverage.

## Effective Tool Set

One immutable effective set belongs to one model request. Schema export, validation and execution share its bindings, allowed instance IDs and host options. Execution reloads live connection state/revision before effects and after approvals, including nested file requests and aggregate resource handlers. A stale call cannot silently change provider or revive disabled access.

`integrationsEnabledByDefault` supplies profile selection; a connection's profile availability overrides it, with the base profile's connection value inherited where needed. Adapters marked `native_tool` provide an existing built-in tool rather than independent integration tools: Jina supplies `webfetch`, SearXNG supplies `web_search`. Their availability and permissions come from that tool, not integration profile selection or loading overrides. Delegation ceilings, connection enablement and administrator adapter restrictions still apply. Their integration editor links to tool settings, and permission writes reject separate integration overrides. Agent-operation readiness and remote ACLs remain independent hard bounds.

### Tool loading

Profiles support `integrationToolLoading=on_demand|native|all`. Allgemein defaults to `native`; other shipped profiles to `on_demand`. A connection's `toolLoading` resolves from selected-profile entry, base-profile entry, connection default, then profile default. Built-in tools remain directly offered.

`search_tools` searches the already eligible catalog and loads at most five definitions; it executes no external action and grants no rights. Its search index is built on the first call and reused within that offered tool set; each call still checks current integration availability. Discoveries persist with ordinary tool messages in the session, independently of the selected profile, and rebuild in stable order after the current compaction boundary. Current availability, permissions and delegation ceilings determine which discovered tools can be offered or executed. A temporarily excluded discovery can become available again without another search. Compaction/context pressure may expire old discovery metadata without deleting results; tools can be searched again. Delegation freezes the eligible catalog, not just already discovered tools. Stable offers aid prefix caching but do not guarantee hits.

## MCP

Generic MCP uses separate `/mcp` settings while sharing integration persistence and permissions. Personal servers require an administrator gate and are disabled by default. Streamable HTTP supports no authentication, encrypted Bearer credentials or OAuth. HTTP exposes traffic/credentials on the wire; use HTTPS outside trusted networks.

Discovery persists validated tools, schemas and untrusted display metadata under a 32 MiB aggregate budget and 32 MiB response bound. One deadline covers initialization and all pages: normally 30 seconds, five minutes including interactive OAuth. Tool responses retain a separate 1 MiB limit. External schema references, excessive nesting, non-finite data, repeated cursors, oversized payloads and cross-origin redirects fail closed. Failed refresh keeps the previous catalog.

Repeated JSON Schema meta-validation reuses up to 4,096 process-local SHA-256 fingerprints of successful checks, retaining no schema contents, credentials or authorization state. Only exact JSON types are eligible. Depth, reference, finite-JSON and input-object constraints remain checked on every use; changed schemas require a new check. Eviction or restart only causes revalidation and does not change offered schemas or their order.

Each discovered tool gets a stable model name and hashed resource key. The host owns the handler and coarse `mcp.call` write action; remote annotations do not prove read-only behavior. Calls retain argument validation, revision fences and post-approval revalidation. Endpoint changes reset policies; catalog refresh removes rules/availability for disappeared tools. Each call uses a short-lived session, never automatically retries and reports uncertain post-dispatch failures as such. Prompts, resources, sampling, elicitation, stdio and server-provided executable code are unsupported.

### MCP OAuth

OAuth uses Authorization Code with S256 PKCE, discovery, dynamic registration or an explicitly configured client, resource binding and persistent refresh. Browser-only SSO/ForwardAuth is insufficient: the server must publish MCP metadata and accept issued Bearer tokens. A pre-registered client supports `none`, `client_secret_basic` or `client_secret_post`; register `<origin>/api/mcp/oauth/callback`.

The saved public origin takes precedence over `MATO_LOOP_PUBLIC_BASE_URL`, then the trusted incoming origin. It contains no path. With HTTPS and server support, the SDK may use MatoLoop's public credential-free Client ID Metadata Document; HTTP uses dynamic registration. Provider callback restrictions remain independent; TLS verification stays enabled.

Login attempts are process-local, one per initiating session and at most 32 globally, expiring after five minutes. A public callback checks one-use state and redirects only to fixed settings; it cannot persist a connection. Authenticated finish verifies the initiating owner/login-session, live access and original revision before committing credentials and validated catalog. Failure preserves the old connection. Backend restart requires restarting pending login, not saved credentials.

Encrypted credentials retain client details, expiry, issuer and resource binding. Refresh occurs only after persisted expiry under a PostgreSQL credential-row lock, in a separate transaction. Missing replacement refresh tokens preserve the old token. Transient failures retain credentials; rejected refresh requires reauthorization. Upstream authentication failure never causes request replay. Explicit reauthorization replaces credential identity and clears policies; rotation retains identity. Disconnect removes credentials/policies, not catalog/configuration.

During initialization only, an unsuffixed endpoint returning 404 may be retried with `/`, subject to the same resource/credential binding. Tool calls are never replayed by that recovery. OAuth secrets and provider error bodies stay out of UI/logs; reverse proxies must redact callback queries too. Global OAuth deliberately shares the authorized remote account under instance policy; personal credentials remain owner-only.

Tests live in `apps/backend/tests/test_mcp_oauth.py`. Its opt-in `MATO_LOOP_MCP_DB_TEST=1` case verifies rotating-token refresh using isolated development PostgreSQL data. Use the existing [development stack](development.md), not production data.

## CalDAV

One account is one HTTPS instance with an encrypted password/app-password credential. Discovered event calendars and task lists receive stable separate resource keys/actions, including mixed collections. DAV privileges remain hard action limits. Models receive opaque resource keys and encrypted binding-scoped tokens, not DAV URLs, ETags, credentials or raw iCalendar.

Creates use host-derived deterministic UIDs and `If-None-Match`; updates/deletes require observed ETags with `If-Match`. Recurring, scheduling-bearing or otherwise unrepresented properties make mutation unsupported rather than losing data. Timed values are UTC instants; all-day values remain dates. Results supply DST-correct Europe/Berlin local timing. Up to ten relative reminders are supported.

Standard calendar/task-list selection is separate from permissions. Calendar tools always require explicit `integration_id` and `calendar_key`; the configured default is supplied only as model context for requests without another named calendar, and only when effective action/resource policy allows it. Missing calendar targets are rejected, never filled automatically. Approvals show the selected calendar and account, using remembered resource names when available.

Task-list tools still fill fully omitted targets with the configured complete pair before validation/authorization; an explicit complete pair wins. Partial targets never mix with defaults, and stale/disabled defaults fail closed. Task operations support title, note, due date/time and completion; unsupported recurrence/relationships/alarms remain readable but not editable.

`tasks_create_many` adds at most 50 tasks under one approval, skipping case/whitespace-normalized open-title duplicates. It never deletes, rewrites or synchronizes the existing list. Tokens may be projected as short session-bound result references; resolution still validates original binding, ownership, policy and ETag.

## Mail

One IMAP/SMTP account stores non-secret endpoints/sender in configuration and an encrypted password. Only verified implicit TLS or mandatory STARTTLS is supported. Bounded blocking clients run outside the event loop. Account actions distinguish reading, drafts, sending and deletion; folders are navigation targets, not policy resources.

An optional account signature becomes editable plain text in new messages. Signature-only settings updates preserve permission rules. Send approvals expose editable subject/body defaults to the owner without copying server-loaded draft text into model history; only approved owner edits enter the tool arguments.

UID-based message/draft tokens and pagination bind account revision, folder, query and `UIDVALIDITY`. Special-use flags, not folder names, define Sent/Drafts/Trash. Short model references resolve back to authorized session results before normal token checks. Forks remap recognized references, never arbitrary message text.

The Control Center reads live mail without a local synchronization database, suppresses remote HTML content and preserves attachments when editing drafts. Lossy/unsupported draft edits are rejected; UID-scoped deletion is required and global `EXPUNGE` is never used.

SMTP dispatch reserves a persistent owner/account idempotency record. A replay returns its recorded outcome, never another send. `sent` means SMTP acceptance, not recipient delivery; `sentCopyConfirmed` separately records archival. Missing/unknown Sent confirmation is a warning, not send failure, and preserves the source draft. Never resend automatically or delete that remaining copy. SPF/DKIM/DMARC remain the mail operator's responsibility.

## Microsoft 365

The personal-only `microsoft_graph` adapter uses delegated Microsoft Graph `Mail.Read` and `offline_access` for the signed-in user's own Exchange Online mailbox. It contributes account discovery, paginated folder navigation, message listing/KQL search, basic conversation overviews, plain-text message details, and attachment downloads under the existing `mail.read` action and connection/profile policies. Listing and search default to the inbox; other folders, including sent mail, require an explicit `folder_id`. Conversation overviews deliberately span mailbox folders, including sent mail, using the conversation ID resolved from a bound message reference; pages have no guaranteed chronological ordering. Graph search returns at most 1,000 matches; individual message and event bodies are bounded to 100,000 characters with explicit truncation.

`m365_get_message` selects message, conversation or attachment-list views. Only returned regular-file attachment references can be downloaded, with both metadata and streamed bytes capped at 20 MiB. Downloads additionally require `session.files.write` for an explicit new session-relative path; the existing file service enforces boundaries and refuses replacement. Attached Outlook items and cloud-reference URLs are not followed. Document extraction uses the ordinary file tools, not automatic attachment execution.

Agent collection results include basic fields: mail subject/participants/date/state/importance, event subject/start/end/location/state/organizer/availability/importance, and task title/status/importance/due date/attachment presence. Mail searches, conversation pages and calendar views also return Graph's plain-text `bodyPreview`, locally capped at 255 characters when available. Previews are not full content; an empty or missing preview does not prove an empty rich-text body. Task summaries report `hasNotes`: `false` confirms empty text/HTML notes, `true` indicates text or linked/embedded media, and `null` means unavailable. HTML whitespace alone is empty; image-only notes are not. `isRecurring` reports whether a returned recurrence value is non-null; absence means unknown.

Use the returned fields and previews when sufficient for the request, including counts, dates and priorities. Do not fetch every listed item's details or reread known-empty notes. Full bodies, notes, raw resource IDs, versions, attendee lists and recurrence rules remain outside collection results. Load needed missing details through `m365_get_message` with `view=message`, `m365_get_event`, or `m365_todo` with `operation=get`. These summaries use the existing collection requests, not extra Graph calls or specialized overview tools. A model-side detail read is not a prerequisite for mutation: mutation tools still perform their own authorized inspection and post-approval version checks. To Do child collections return only their basic fields. Collections retain explicit `nextCursor`; a partial page is not a complete account overview. The model sees short `mail:`, `event:`, `task:` and `attachment:` result references through the existing harness projection. Canonical encrypted tokens remain in their originating session messages; resolution checks the source session/type/index before normal current binding, permission and mutation-version validation. No process-local reference cache or new persistence layer is used.

Mail writes are independently opt-in: `allow_drafts` enables `m365_draft`/`m365_reply` under `mail.drafts`; `allow_send` enables `m365_send` under `mail.send`; `allow_delete` enables `m365_delete` under `mail.delete`. All three require delegated `Mail.ReadWrite` instead of `Mail.Read`; sending additionally requires `Mail.Send` because larger sends stage a draft. Composition accepts To/Cc/Bcc, plain-text body and optional session-file attachments. Attachment reads require independent `session.files.read` authorization and remain within the current session tree. Both UI and agent uploads enforce the instance's per-file, total-byte and file-count limits; signature images count toward total bytes, not the regular-file count. Outgoing bytes additionally have a 150 MiB safety bound; the Exchange mailbox may impose a lower message-size limit. Small messages use bounded JSON requests. Larger messages stage a draft and add files separately: under 3 MiB by attachment POST, otherwise by sequential upload-session PUTs below 4 MiB. Upload URLs are accepted only from Graph responses for HTTPS `outlook.office.com/api/`, without redirects or bearer headers; their credential-bearing URLs are excluded from httpx request logs. Upload sessions are not resumed or automatically retried.

`m365_draft` can also update a returned `message_token`. Omitted fields and existing attachments remain unchanged; supplied session files add attachments. HTML bodies require explicit `body_format=html` rather than a lossy plain-text replacement. Updates require an approved, rechecked draft `changeKey`. Multipart Control Center updates similarly require `expectedVersion`; retained attachment tokens must belong to that draft, and inline images are always retained. Edits never append another signature. Multiple Graph writes are not transactional: a failed follow-up or refresh reports an unknown outcome and requires inspection in Outlook before another attempt.

Draft/reply/send tools always require their mail action. Their declared `session.files.read` action is optional only when no session-file attachments are supplied; actual attachments still require independent authorization before reading files. Configured signature images do not require session-file access.

An optional formatted HTML signature supports email tables, legacy font markup and bounded inline styles for colors, typography, spacing and borders. Outlook/Word paste removes Office metadata and unsupported formatting; missing local, CID or external image sources produce an explicit notice instead of network requests. Embedded PNG/JPEG/WebP images accept ASCII whitespace in clipboard Base64 and are stored canonically (200 KiB each, 400 KiB total, at most eight, 2048 pixels per side); external image URLs, SVG, active content, positioning, CSS URLs and dynamic CSS functions are rejected. Outgoing composition escapes plain text, appends the signature once, and converts its images to CID-linked inline file attachments. Existing drafts are sent unchanged, preserving their HTML and attachments without appending another signature. Reply creation first calls `createReply` without replacing its body, then prepends the response and signature to Outlook's quoted original message, retaining its HTML and embedded-image references. Recipients and attachments are added to that native reply draft; a failed follow-up leaves a possibly partial draft and reports an unknown outcome, never success.

Send/delete approvals show concrete recipients (including Bcc), subject, text, attachments or deletion target. Existing draft/message actions recheck Graph's `changeKey` after approval; external concurrent edits are not locked atomically. Sends reuse the persistent `MailSendOperation` reservation before remote effects, with account/user/key and draft identity guards. Graph's empty `202 Accepted` means submission only, not confirmed delivery or a verified Sent Items copy. Transport failures and uncertain effects are never automatically replayed. Inspect Outlook after uncertain writes; a draft creation may already have succeeded. Deletion uses Graph's ordinary DELETE, not permanent-delete; deleting from Deleted Items may nevertheless be irreversible.

`read_calendar` independently enables `m365_calendar` and `m365_get_event` under `calendar.read`. It lists own calendars and uses `calendarView` for recurring instances within an explicit offset-aware interval of at most 366 days. The default is the primary calendar; returned times are UTC. Event results include owner/revision-bound `eventToken` references. `write_calendar` enables event creation and sparse updates under `calendar.write`; `delete_calendar` independently enables deletion under `calendar.delete`. Reads request delegated `Calendars.Read`; either write option requests `Calendars.ReadWrite` instead. Explicit timezone-aware start/end values are converted to the supplied IANA timezone; all-day events require local midnight boundaries and an exclusive end. Native event bodies, attendees and recurrence remain unchanged unless explicitly replaced. Replacing an online-meeting body is unsupported to preserve its native join information; other fields can still be updated. Updating/deleting a series master requires explicit `confirm_series`; individual occurrence tokens affect that occurrence. Meeting writes can send invitations, updates or cancellations, which approval cards disclose. Creation uses a call-bound Graph `transactionId`; mutations are never automatically retried after uncertain outcomes.

Microsoft To Do uses independent `read_tasks`, `write_tasks` and `delete_tasks` options and the existing `tasks.read`, `tasks.write` and `tasks.delete` actions. Read-only access requests `Tasks.Read`; either mutation option requests `Tasks.ReadWrite`. `m365_todo` paginates lists, tasks, checklist items, linked resources and attachment metadata, and reads individual returned references. Create/update/delete tools cover lists, tasks, checklist items and links; deletion also covers attachments. Task fields include escaped plain-text notes stored as HTML, progress/completion, importance, start/due dates, reminders, existing Outlook categories and patterned recurrence. Null explicitly clears optional dates/recurrence; omitted fields stay unchanged. Completing a recurring task may generate its next occurrence. List/task deletion cascades to children and is disclosed before approval. Linked URLs are stored/read as untrusted data and never fetched automatically. My Day, list-sharing administration and Outlook-category administration are not exposed by these tools.

Task listing defaults to open tasks using Graph's server-side `$filter=status ne 'completed'`, so completed tasks do not consume result pages. Task collection requests omit `$select`, which this To Do endpoint rejects; basic-field projection happens locally. Explicit `include_completed=true` includes completed tasks; individual reference reads remain available regardless of status. Summaries omit normal importance and `hasAttachments=false`; missing values retain those documented defaults. The completion filter is part of the cursor binding and must remain unchanged across pages.

Calendar and To Do mutations inspect the concrete resource before approval and compare its typed snapshot again before effects, including Graph versions when provided. Supplied ETags are passed to supported task mutations, but this is not a universal atomic lock against external edits. References bind the owner-selected connection and its revision; To Do references also retain resource type and parent path. Cursor references bind the entire query. Disabled options and hard policy denials cannot be turned into approval requests.

`m365_todo_attach` reads one independently authorized session file; `m365_todo_download` writes only to a new independently authorized session path. Both respect instance upload limits and a 25 MiB Microsoft file bound. Uploads also enforce the existing task's attachment count and total bytes against instance limits. Attachment inspection finds the exact ID in paginated collection metadata, which excludes `contentBytes`; individual attachment JSON can embed the entire file and exceed the separate JSON response limit. Downloads then stream the raw `/$value` content. Small files use bounded JSON; larger files use upload sessions and sequential chunks below 4 MiB. Unlike Outlook mail upload URLs, To Do sessions must remain on the exact HTTPS Graph origin and match the selected list/task path; PUTs append `/content` and require the Graph bearer token. Redirects and cross-origin/different-task upload destinations are rejected. Session URLs are excluded from httpx logs; no automatic retry/resume is performed. Remote attachment bytes are streamed with a hard size bound. File content is never executed. Shared mailboxes, delegated access to other users and local synchronization remain unsupported.

Account discovery includes enabled features and the configured automatic signature's text/image count. Compose tool descriptions reuse this information when already returned, otherwise request discovery, and tell the model to omit the signature's closing, name and contact details from its body. Signature content remains untrusted turn-local tool data, not a changing system-prefix fragment; no heuristic removes user-authored text. Reusing account information never replaces current connection and permission checks.

The existing Control Center mail app uses the same Graph client through `/mail/accounts` and the account-specific mail routes. Enabled owner-bound Microsoft 365 connections appear alongside IMAP/SMTP accounts with explicit UI capabilities. It supports paginated reading/downloads and opted-in draft editing, sending and deletion, including Cc/Bcc and local attachment uploads. Existing HTML drafts expose their original source in a text field, never an executable HTML editor; unchanged bodies are omitted from the update to preserve exact markup. Truncated bodies or incomplete attachment pages block editing until completely loaded. Sending from the editor saves changes first, then sends the saved version through the persistent reservation; the detail action sends drafts unchanged. Message and cursor references retain integration/revision/query binding using a digest rather than embedding large signature data. Uncertain writes block resubmission in that editor. Manual user API operations do not use the agent approval loop.

Each connection selects a tenant UUID, application UUID and either device-code or confidential web authorization-code login with S256 PKCE. The fixed public-cloud endpoints cannot be supplied by models. Browser callbacks use `form_post`, one-use random state and `<public-origin>/api/integrations/microsoft365/oauth/callback`; they only stage a code. The initiating authenticated owner/login-session must complete the login. Device polling respects Microsoft intervals and `slow_down`. No application-wide mailbox permissions are requested.

Both flows request only the configured delegated scopes and validate required scopes on token exchange and refresh. Changing any access option invalidates saved tokens and grants, requiring a new login; a stored browser secret is retained when tenant, client and flow are unchanged. Signature-only changes preserve tokens and do not require login. No optional capability is enabled implicitly.

Login attempts are process-local, at most 32 globally and one per initiating login session, expiring after ten minutes (browser) or the provider's device-code lifetime. Restarting the backend requires a new pending login. Saved credentials survive restarts. Secrets and access/refresh tokens are encrypted in `credentials`; the settings API exposes only credential-presence/status flags. Expired tokens refresh under an owner-scoped credential-row lock in a separate transaction; rotation preserves a missing replacement refresh token. Rejected grants require login again, transient errors preserve credentials, and Graph calls are never automatically replayed.

Authenticated completion checks current adapter availability and the full original connection revision before replacing credentials. Reauthorization, binding/secret changes and disconnect rotate credential identity and clear connection/profile policies. Name/enabled changes alone preserve credentials. Disconnect removes MatoLoop's tokens, not the Entra consent or client secret; revocation is performed in Microsoft. The UI records a confirmed disconnect before refreshing settings, so a failed refresh cannot leave the account shown as connected. Encrypted message/attachment references and cursors bind the connection revision and cursor arguments; continuation URLs must retain the exact HTTPS Graph origin and collection path. Responses, mail, calendar and attachment content remain untrusted data.

Setup is documented in the [handbook](user/integrationen.md#microsoft-365-postfach-lesen). Focused coverage lives in `apps/backend/tests/test_microsoft365.py` and `apps/frontend/tests/microsoft365-login.spec.js`.

## BookStack

Each HTTPS installation uses encrypted token ID/secret and book-level read/write/delete resources. Books, chapters, pages and shelves are supported; content is Markdown. Models receive binding-scoped opaque keys/tokens. Operations recheck current book membership so a moved page cannot reuse old book authority.

Page replacement requires an immediate full read and matching observed revision. Missing/changed revisions fail closed; oversized content is rejected rather than truncated for writeback. BookStack lacks conditional writes, so a race between check and save remains possible. Renaming alone has no content-revision requirement. Creation has no remote idempotency guarantee; unknown outcomes require inspection.

Search/listing filters denied books. Resource discovery rejects accounts with more than 500 visible books rather than retaining incomplete policy state. Shelves are organizational containers, not independent policy resources: replacements preserve inaccessible books, incremental/full replacement forms cannot be combined, and shelf deletion retains books.

Attachments inherit the page's book policy. Sources are a URL, managed file, computer file or plain link. Downloads reuse Webfetch authorization/network checks; local sources retain independent file-read permission. Uploads are capped at 32 MiB and the shared response bound. Failed downloads retain controlled causes; a link may be used instead, not a speculative failure explanation.

## Mealie

Mealie uses a configured base URL without `/api` and an encrypted bearer token. HTTP is supported for trusted local installations. Requests stay on that origin/deployment path, reject redirects, ignore proxy environment variables and bound responses. Recipe and meal-plan tokens bind connection revision and observed content; update/delete must first read details and reject changed snapshots. No conditional remote write exists, so a final check/save race remains.

Recipe search is paginated with bounded exact filters. Creates may perform name creation followed by content update; failure can leave a partial recipe. Updates preserve omitted fields but replace supplied ingredient/instruction lists completely. Authorized ingredient replacement may create missing food/unit records; later failure is an uncertain outcome, never an automatic retry. Meal plans accept same-binding recipes or bounded free text.

When developing new recipes, the agent reuses supplied or known context and asks for missing servings and relevant preferences together through `question`. Adopting a recipe from a URL, text, PDF or photo needs no extra questions when the source and task suffice. Missing source facts must not be invented; only blocking gaps require clarification.

`recipe_set_image(integration_id, recipe_token, image)` replaces a recipe's main image. The image is a `FileReference` from session storage or the selected computer (`files`/`computer` in model-facing tools, internally `session`/`workspace`). Shared image validation applies. Source-file read permission is independent of the existing `recipes.write` permission. After source authorization, the action revalidates the integration binding and recipe-write authorization without another approval prompt, checks the current recipe snapshot before upload and returns a fresh recipe token on success. An uncertain upload outcome requires inspection, not a blind retry.

Recipe/plan actions have separate read/write/delete permissions. Native shopping lists and organizer administration are not exposed. Shopping requests compose normal Mealie reads with additive CalDAV task creation; compatible quantities may be combined, without a durable synchronization table or destructive list reset.

## Arcane

One backend instance uses a configured manager origin/path and encrypted `X-Api-Key`. Environment resources and scoped read/write/delete rules supplement Arcane's own RBAC. Models cannot supply arbitrary endpoints/methods or execute containers. Bulk prune and Arcane administration are excluded. Requests reject redirects, ignore proxy environments and bound responses.

Tools expose allowlisted resource summaries, bounded logs, lifecycle operations and project configuration. Compose/environment reads can contain secrets: they use sensitive-data policy plus central provider/model pseudonymization, not integration-specific masking. Original authorized content may persist in conversation; disabling pseudonymization permits unchanged model transmission. Detection is not complete.

Project save updates only supplied fields and supports protected value references. The encrypted snapshot carries a digest and scope, not a secret/content copy. Changed configuration is rejected before save, but Arcane PUT is not conditional and retains a final race. Included files are read-only. Clearing an existing environment or removing an override additionally requires delete; a secret resolving to empty text cannot silently authorize clearing.

Saving does not deploy. Deploy/pull NDJSON requires Arcane's `done` event to confirm success. Verification failure is separate from a confirmed mutation and never triggers blind redeploy. Container logs are bounded, may be truncated/incomplete and may contain private data. Unknown mutation outcomes require inspection, not automatic retry. Key/endpoint rebinding invalidates stale bindings and rules.

## OpenCode

OpenCode is a personal-only backend adapter. Its client probes the configured server, rejects changed roots, cross-origin targets/redirects and oversized responses/events, and keeps credentials encrypted. Public/model-facing identities are relative projects, workspaces and paths, not remote absolute roots.

A MatoLoop project binds one remote project/workspace, adjustable until its first saved plan. Changing it clears model/variant selections and queue state. Analysis returns repository findings; MatoLoop writes the canonical plan. Plan creation snapshots analysis selection, while enqueue freezes exact plan revision, execution model/variant and directory. Null variant delegates to the model default; explicit variants must still be advertised before dispatch.

Execution is persistent FIFO with at most one active job per project. External remote activity pauses the queue, permission requests require explicit decisions, and cancellation is best effort. Unknown post-dispatch outcomes are never replayed automatically. The Control Center is read-only for files and offers plans/queue/decisions, not an editor, terminal, Git or automatic retry surface.

## tbs.Desk

This personal-only backend adapter stores encrypted credentials and uses bounded authenticated requests on the configured origin. A customer hint triggers ERP lookup; otherwise the active call may identify candidates. Customer selection must come from the current persisted result set and enters as a separate user message.

The transient protected Support-Assistent profile exists only while its connection is available. Ticket queries inject the selected customer server-side and detail reads verify returned customer ownership. Stored selection contains bounded summaries, never ticket bodies. Connection disablement removes offered profile authority.

## Git via Shell

Git is not an integration. Model Git uses the selected Agent's ordinary shell, policies and OS credentials. Read-only browser diff inspection is a separate owner-authenticated operation, not a model permission bypass. [commands.md](commands.md) owns worktrees, branch management, remote targets, publication safeguards and cancellation. Older installations may need [targeted cleanup](user/aktualisierung.md#removed-git-integration).

## OpenSCAD

One personal Agent instance binds a startup-verified canonical OpenSCAD executable. The model supplies source/project references, not executable, environment, camera or arbitrary CLI arguments. Source uses ordinary authorized file tools; rendering is a separate write action, ordinarily asking under shipped presets.

Bounded project staging rejects unsafe paths. Fixed direct execution retains time/resource/output limits and executable identity checks, but inherits Agent-account OS/network authority, not a sandbox. Stronger isolation belongs to deployment policy.

After material edits, render the exact entrypoint/project and inspect geometry diagnostics plus six views. Source dimensions remain authoritative for numerical claims. OFF geometry and inspection PNG/contact sheets are ephemeral, not managed revisions; explicit STL exports are durable outputs. An isolated vision helper checks views against up to seven current references, or marks the result visually unverified. A visual pass never proves hidden geometry, fit, wall strength or printability; uncertainty cannot be promoted to pass. Historical dependency-based previews show source only.

## Browser

The personal Linux/Windows Agent adapter binds one owned computer and disposable browser per chat/computer. Ordinary use includes website JavaScript; unrestricted Python has separate permission and worker-account OS authority. Build-based profiles default to automatic browser use outside `ask_all`; other profiles ask. Python defaults to ask everywhere. Explicit overrides remain authoritative.

Model tools do not require an open viewer. Native setup is explicit; containers contain the shared runtime. [browser.md](browser.md) owns isolation, input fencing, grants, transfer, cancellation and deployment limits. Upgrade effects are linked from the [upgrade guide](user/aktualisierung.md#browserrechte-und-alte-websiteprofile).

## Web Search

`web_search` accepts a compact `query` and optional web/image type; the host selects the provider. Results contain canonical host-derived IDs, titles, URLs, snippets and optional publication dates. The shared research policy uses sufficiently detailed snippets directly for ordinary low-risk answers, without fetching every result or adding a generic preliminary disclaimer. External content remains untrusted data, never instructions; absent facts must not be invented, and an unfetched page must not be presented as read.

Fetch original sources when snippets are insufficient or materially conflicting, for high-stakes or consequential precise claims, or for explicit thorough research or source verification. When fetching is needed, use the known exact URL rather than searching the same candidate again. Cite snippet-supported claims with the returned search title and URL; fetched citations still require `citationEligible=true`. Image hits require fetching the exact image URL before use.

No-key search uses bounded off-loop `ddgs`; queries leave the installation for the selected public search service. SearXNG and Jina are instance-only, with one host-selected provider per tool. Missing, disabled or delegation-excluded providers make the tool unavailable, not silently changed. SearXNG may recover unresponsive engines once within the same instance; no automatic cross-provider retry exists. [webfetch.md](webfetch.md) owns direct/Reader networking and retrieval limits.
