# Integrations and Tool Contributions

Integrations extend the MatoLoop harness without bypassing the provider-neutral agent loop or permission boundary. A persisted instance names an integration type and a host-known adapter. The adapter validates its configuration and normally produces only statically implemented contributions. The bounded MCP exception is described below.

The adapter registry is the availability catalog. Registered adapters default to `full`; administrators may set backend adapters to `instance_only` or `disabled`, while owner-bound agent adapters support only `full` or `disabled`. Availability changes retain configured instances, and deletion remains possible when other operations are blocked.

## Contribution Types

Follow [Tool permission declarations](tool-permissions.md) when adding or changing
actions. Every `ToolAction` requires an explicit category; shared capabilities must
use the same category. Existing connection and resource policies remain authoritative.

An adapter can:

- contribute a new tool with a stable name, Pydantic input model, and host handler,
- add values to an explicitly extensible host configuration field of an existing tool,
- provide a static host-controlled prompt fragment for a tool that is actually offered.
- contribute a protected, non-persisted agent profile while its effective integration is enabled.

Every contributed tool declares its host-controlled group, German UI metadata, and security actions. A configurable action requires a host-side authorization factory that creates typed permission requests from validated arguments. Integration configuration and remote responses cannot provide groups, capabilities, resource matchers, or authorization behavior. MCP discovery may provide only validated tool schemas and untrusted display metadata; MatoLoop supplies the group, capability, resource key, handler, and authorization behavior.

Authorization factories also provide the German approval title, concise action summary, and resource display from validated host data. The frontend renders this common permission metadata and does not interpret integration-specific tool arguments. Display text never participates in authorization matching.

Persisted configuration and external responses must not provide handlers or prompt instructions. Except for the bounded MCP tool-schema contract below, they also cannot provide JSON schemas. Duplicate tool names and contributions to undeclared configuration fields are programming errors. Host configuration values never become model arguments merely because an adapter contributes them.

## Control Center Integrations

An integration implementation may ship one Control Center view per integration type. Its inert ID, German label, Material icon, and Vue component are registered in the compiled frontend manifest. Multiple configured instances remain inside that one view. It uses normal typed MatoLoop APIs and stores; runtime settings require explicit authenticated backend contracts with the same ownership and effective-state rules as other settings.

Control Center session metadata stores only bounded inert app and resource-tab IDs, their order, the active tab, panel visibility, separate managed and computer explorer positions, and validated file targets. It stores no editor content. The unified global **Benachrichtigungen** view is not session metadata. Persisted integration configuration and external responses cannot provide component paths, JavaScript, HTML, routes, form schemas, or remote bundles. Unknown IDs never cause code loading. Independently installed frontend plugins would require a separate signed and isolated plugin platform and are not part of the integration contract.

**Benachrichtigungen** is one chronological notice list. Request notices open their source session, where approvals and questions are answered; Dreaming notices link to Memory proposals. Reading or deleting a notice does not resolve its source action. Badges count unread notices only. Granted session permissions remain in the **Session** app.

## Execution Locations

Every adapter declares one static execution location. `backend` adapters execute inside MatoLoop and cannot have a MatoLoop Agent assignment. `agent` adapters represent local operations, require one configured MatoLoop Agent, and contribute only host-declared tools whose operation names and schemas are compiled into MatoLoop. Configuration and the agent's operation advertisement cannot add executable schemas or permission behavior.

An agent-bound integration is offered only when its configured agent matches the current run's selected agent, is connected, and advertises the static operation. Multiple MatoLoop Agents are supported, with at most one instance of an agent adapter kind per agent. A separately executed `select_execution_agent` call can change the run binding between model requests, subject to its configured policy and grants; integration tools never select a target per call. There is no automatic failover, backend fallback, retry, or redelivery. The backend still validates arguments and results and owns policies, approvals, credentials, and canonical tool results; the selected outbound MatoLoop Agent performs the local operation.

## MCP

MCP is managed under its own settings menu but reuses the integration persistence and permission core. The client supports Streamable HTTP with no authentication, one encrypted static Bearer token, or OAuth. All modes allow HTTP or HTTPS; the UI warns that HTTP sends MCP data and credentials unencrypted. Personal MCP servers are disabled by default and require a dedicated administrator setting; MCP does not appear in the normal integration catalog.

Product integrations are identified and presented by their product or service, not by their transport protocol. They use a normal catalog adapter, product-specific configuration routes, capabilities, labels, and policy defaults even when they reuse the MCP client internally. The generic MCP connector remains a separate escape hatch for servers without a dedicated MatoLoop adapter; a product must not be configured in both places as one logical integration.

Creating, updating, or refreshing a server performs paginated tool discovery without fixed tool-count, page-count, description-length, or individual schema-size limits. MatoLoop persists validated tools with their names, descriptions, input and optional output schemas, and standard annotations. Discovery has a 32 MiB aggregate serialized-data budget (tools and pagination cursors) and a 32 MiB per-response transport budget, with one deadline covering initialization and all pages (30 seconds normally, five minutes including interactive OAuth). Tool calls retain their separate 1 MiB response limit. Model tool-count and context limits are independent of connection setup. Descriptions and annotations remain untrusted display and model data and never weaken a policy. External schema references, non-finite data, excessive nesting, oversized arguments or responses, repeated cursors, and cross-origin redirects fail closed. A failed discovery leaves the previous catalog unchanged.

Every discovered tool receives a stable model-facing name and a stable hashed resource key. The host owns its handler and the `mcp.call` action. Since remote MCP tools may have side effects, reusable session grants use the write class and bind to the exact tool resource, server, and binding revision. Each server owns private/public capability and per-tool resource permissions. Personal servers may add profile-specific overrides. Resolution follows the independent integration policy described below; global tool/profile capability defaults do not impose an MCP ceiling.

Calls use the normal effective-tool snapshot, argument validation, revision fence, approval flow, and post-approval revalidation. Changing the endpoint clears server and tool policies; catalog updates remove policies for tools that disappeared. Each call opens a short-lived MCP session, does not retry, and reports failures after dispatch as an uncertain outcome. MCP prompts, resources, sampling, elicitation, stdio, and server-provided executable code are outside this contract.

SonoBin is a normal `music` integration with the `sonobin` adapter. MCP Streamable HTTP is only its current transport implementation. The adapter supplies the product-specific `sonobin.call` capability and host-controlled German labels while reusing the bounded MCP machinery. All discovered tools currently share its `write` category and inherit the saved base preset. Connection and resource policies, including profile-specific branches, may override it. Creation does not seed fixed rights or resource labels into tool settings.

SonoBin takes its HTTPS base URL and derives the `/mcp/` endpoint automatically, preserving an installation path. Existing `/mcp` and `/mcp/` URLs are also accepted. Personal Bearer tokens are created in SonoBin account settings and use the account's current permissions; legacy static tokens require `SONOBIN_MCP_BEARER_TOKEN` and an active administrator in `SONOBIN_MCP_USER`. Normal users can search music, manage their playlists and local likes, import remote tracks, and inspect their jobs. Recording, asset, and metadata administration requires administrator privileges; diagnostic reads additionally require enabled SonoBin system diagnostics. `get_mcp_context` reports the effective account permissions and asset-download readiness. Download links require administrator privileges and `SONOBIN_MCP_PUBLIC_BASE_URL`. Endpoint changes retain the normal policy cleanup behavior.

The adapter labels all 52 current SonoBin tools, including provider discovery, playlist and like management, remote imports, individual metadata candidates, and runtime/integration/player/generator diagnostics. It uses the host's coarse `mcp.call` write category and does not seed per-tool permission rules when creating a connection. Saving an existing SonoBin connection discovers the current catalog and schemas without overwriting retained tool policies. Newly discovered tools without stored overrides follow the saved trust preset. Input schemas, descriptions, and results come through the existing bounded MCP machinery, so compact/full responses and mixed-playlist arguments need no product-specific DTO conversion.

Music lists and search default to 25 items and `detail="compact"`; track, recording, asset, identification, and metadata-change details also default to compact responses where supported. Request `detail="full"` for additional metadata and follow the returned pagination cursors. `list_providers` exposes provider IDs and capability readiness without credentials. Mixed playlists accept either local `track_ids` or ordered `playback_targets` copied from search/list results, never both; playlist removal can use outer entry `item_ids` for remote tracks. Playlist mutations do not download media. `import_remote_track` imports a remote playback target without an existing recording or a new like. Follow a queued import with `get_acquisition_status(job_id)` until a terminal result; completed downloading alone does not confirm a library import. Large diagnostic payloads support bounded JSON chunks through `offset` and `limit`.

### MCP OAuth

OAuth uses Authorization Code with S256 PKCE and the installed MCP SDK for protected-resource and authorization-server discovery, dynamic registration, and the initial token exchange. A pre-registered client is supported with `none`, `client_secret_basic`, or `client_secret_post` token endpoint authentication. Optional requested scopes override discovery defaults. Registration requests advertise only grants supported by the discovered authorization server. The server must publish MCP authorization metadata and accept the issued Bearer access token; a browser-only SSO or reverse-proxy ForwardAuth login is insufficient.

Configure the public origin, without a path, under **Administration → Grundeinstellungen**. The saved URL takes precedence over `MATO_LOOP_PUBLIC_BASE_URL`; otherwise MatoLoop uses the incoming server address with the ASGI server's trusted proxy handling. Saving applies to new OAuth logins immediately. The settings API returns the effective origin and its source. Callback detection is independent of CORS and does not read arbitrary forwarded host headers. Register `<origin>/api/mcp/oauth/callback` for a pre-registered client. Both prepared Compose stacks retain the environment variable as a fallback.

For providers advertising Client ID Metadata Documents (CIMD), the MCP SDK uses `<origin>/api/mcp/oauth/client-metadata` when MatoLoop has an HTTPS origin. This public, credential-free document lists MatoLoop's name and exact callback URI. With an HTTP MatoLoop origin the SDK instead uses dynamic registration, even if the provider also advertises CIMD. MatoLoop allows HTTP callback addresses, including LAN addresses; the provider decides whether to accept them. HA-MCP's webhook-specific registration endpoint requires HTTPS or HTTP loopback callbacks and rejects HTTP LAN callbacks. Explicit client settings take precedence. HTTPS certificate verification remains enabled.

The personal settings tool advertises all three MCP authentication modes and directs interactive OAuth setup to `/settings/mcp`. Its writable credential fields remain static Bearer references; it does not perform browser authorization or receive OAuth secrets. Reading an existing MCP connection includes its authentication mode. During initialization only, an HTTP 404 for a URL without a trailing slash permits one retry with the slash, preserving encoded path segments. Successful discovery persists the resolved endpoint. For an existing OAuth connection, the current credential binding and resource authorization must permit the recovered endpoint; the connection and encrypted credential endpoint are updated in one transaction without expanding the authorized resource. Tool calls are never replayed by this fallback. Missing endpoints, rejected credentials, connection failures, and timeouts use distinct controlled error codes.

The MCP dialog prepares the login and provides an **Anmeldung öffnen** link. The callback returns to `/settings/mcp`, where the frontend polls only this login interaction and requests an authenticated finish. Login attempts are bounded to 32 globally and one per initiating session, expire after five minutes, and are cancelled at shutdown. They are intentionally process-local; a backend restart requires restarting a pending login, while saved OAuth credentials survive. The callback does not need MatoLoop's `SameSite=Strict` cookie, cannot persist an integration, validates one-use state, and redirects only to the fixed settings page. Finishing verifies the initiating user and login-session hash, current administrator or personal-adapter access, and the original integration revision. No transaction is retained while waiting for a browser. Failed authorization, cancellation, or failed tool discovery leaves the previous connection and catalog intact.

Credentials contain the client information and secret, access and optional refresh tokens, absolute expiry, issuer, token endpoint, and MCP resource binding in the existing encrypted credential payload. Non-secret client settings are additive config fields; existing Bearer configurations need no migration. Reauthorization replaces the credential ID and clears old integration/profile policies. Disconnecting deletes the credential and clears policies while retaining configuration and catalog for reconnection. Global OAuth connections intentionally use the administrator-authorized remote account for all permitted users; personal credentials remain owner-only.

All discovery, refresh, activation and tool-call paths prepare credentials through the same resolver. Refresh runs only after the persisted access-token expiry, respecting providers such as Rauthy that reject early refresh. A PostgreSQL credential row lock prevents concurrent use of a rotating refresh token. A separate transaction persists refreshed credentials without committing pending caller changes. An omitted refresh token preserves the previous token. A rejected refresh requires browser reauthorization; transient service failures retain credentials. An upstream authentication rejection marks the used credential as requiring authorization without replaying the request. Token rotation retains the credential ID; explicit reauthorization changes it. Secrets and token responses never enter UI payloads; the OAuth callback query is removed from backend access logs and raw SDK OAuth exception logging is suppressed. Reverse proxies must likewise omit or redact callback query parameters in their access logs.

Homarr publishes its own OAuth discovery and registration endpoints; it may issue no refresh token, in which case expiration requires a new login. A Rauthy-backed MCP server must advertise the Rauthy issuer and validate the MCP resource audience. For a static Rauthy client, configure the exact callback URI, PKCE S256, required scopes, allowed MCP resource, and the desired authorization-code/refresh grants. Dynamic Rauthy registration additionally requires enabled DCR and appropriate allowed scopes/resources. Supporting these standard flows is not a claim that every Rauthy version or browser-SSO setup is interchangeable.

Focused coverage lives in `tests/test_mcp_oauth.py`, alongside the existing MCP tests. The opt-in `MATO_LOOP_MCP_DB_TEST=1` case verifies concurrent refresh against migrated development PostgreSQL, creates one isolated credential row, and removes only that row afterward. Run it through `./scripts/dev.sh compose exec -T -e MATO_LOOP_MCP_DB_TEST=1 backend uv run --no-sync pytest tests/test_mcp_oauth.py`.

## Resource Policies

An adapter may declare host-controlled integration actions with an optional asynchronous resource loader. Actions without a loader expose account-level policies only. Resource actions must exactly match actions of a tool contributed by that adapter and that tool must have an authorization factory; tool-option integrations are unsupported until their built-in tool explicitly binds resource policy targets. A loader receives the validated integration instance and an optional decrypted credential payload, but no database session. It returns only stable adapter-generated keys, display labels, an optional subset of adapter-declared capabilities that apply to the resource, and an optional `groupKey`. Capabilities allow one account to expose distinct resource domains without showing irrelevant policy controls. `groupKey` only groups related resources for presentation; it has no policy inheritance or security semantics. External services never define capabilities, policy modes, matchers, or prompt text. Resource keys and group keys use a bounded host-safe character set, and labels are rendered only as untrusted UI text.

Each integration instance owns private/public capability and resource permission branches alongside its connection configuration. Global connections accept administrator-managed overrides for global profiles; personal connections accept owner-managed overrides for accessible global and owned profiles. The selected branch merges over the instance baseline; a resource entry overrides the corresponding capability entry. Missing entries use the action's explicit default or the saved private/public base preset by category, just like built-in tools. `resourceAvailability` is a trust-independent sparse map on the connection permissions and each profile override. Missing entries inherit; false disables every action of that resource without deleting any configured policy. The normal resolver applies the effective availability before grants, including delegation ceilings and aggregate resource enumeration. Integration rights remain independent of global built-in action overrides and the personal-profile/tool-right gates. The integration access endpoint stores only CalDAV standard calendar and task-list selections, not permissions.

The permission page and runtime use the shared action-default calculation and resolver. Connection and profile views show only explicit rules; deleting one model branch restores inheritance without touching the other branch. Integration selection by profile controls availability, not action permission. Technical tool/resource availability, disabled integrations, ownership, remote ACLs, and delegation ceilings remain hard limits. Remote ACLs can make statically declared actions unavailable but cannot define or enable actions.

Tools declare policy actions independently of tool names. Multiple tools may share one action when they have the same security meaning, for example calendar create and update both using `calendar.write`. A concrete permission request keeps its policy target, integration plus resource, separate from its exact session-grant scope.

Resource discovery supplies controlled keys and labels to connection permission pages. Permission writes validate the current catalog, owner, and binding revision, including resource availability keys. Rebinding resets connection and profile action/resource permissions and resource availability, while preserving explicit profile connection availability. Deleting an instance removes its permissions with it. MCP catalog refresh removes disappeared tools from connection/profile resource rules and resource availability, plus cached labels. The profile editor owns only default integration availability. Per-connection exceptions are edited on the connection. Data-only migration `9cee124e2dfb` transfers old assignments within the same owner scope without replacing existing connection availability overrides. It removes personal-profile assignments to shared connections and stale references. The old profile fields, API writes, and runtime fallback are removed; administrators still cannot target personal profiles through the global connection editor.

## Effective Tool Set

Before every model request, the registry combines built-ins, session mode, model capabilities, tool policies, and active integration contributions into an immutable tool set. This object exports provider schemas and validates returned calls. A provider therefore cannot execute a tool that was not offered for that request.

A binding also records allowed option values and the associated integration ID. Immediately before external access, the handler reloads the current integration state. Deleted or disabled instances are therefore ineffective even if they were offered in the preceding model request.

The binding also records a canonical revision of the source instance. Configuration, credential, or identity changes invalidate the stale call rather than executing its captured handler. Provider options selected by host settings are normalized before binding and must still resolve to the same values at execution time.

Adapters with multiple active instances may contribute one stable shared tool set. The effective binding contains only the instances offered for that model request. A validated instance argument can select only one of those host-bound instances; aggregate discovery tools receive the complete immutable bound set. The selected binding is checked before authorization and again after approval.

## CalDAV

The CalDAV adapter is the first production user of shared integration tools, integration and resource defaults, and sparse agent-profile overrides. Each account is one integration instance with one encrypted basic or app-password credential. Discovered `VEVENT` collections become `calendar:<hash>` resources with `calendar.read`, `calendar.write`, and `calendar.delete`. Discovered `VTODO` collections become `tasklist:<hash>` resources with `tasks.read`, `tasks.write`, and `tasks.delete`. A mixed collection exposes both logical resources while retaining one remote collection and credential.

The adapter discovers calendars live and maps DAV privileges to hard unavailable host actions. Models receive only integration UUIDs, opaque calendar keys, and encrypted event tokens, never DAV URLs, ETags, credentials, XML, or iCalendar source. Every returned event includes its integration UUID and calendar key so later update or delete calls can reuse the exact authenticated token binding without discovery. Timed values are canonical UTC instants at the CalDAV boundary; all-day dates remain date values, and ambiguous remote timed values are rejected. Timed event results additionally contain host-derived `localTiming` for `Europe/Berlin`, including DST-correct offsets and weekdays, so models do not perform calendar arithmetic for user-facing output. Events support up to ten distinct relative `DISPLAY` reminders from the start time. Creates use a host-generated deterministic UID and `If-None-Match`; updates and deletes use ETags with `If-Match`. Event-token versions prevent pre-change timing snapshots from being reused after serialization semantics change. Recurring or scheduling-bearing events and events with unrepresented properties are not mutated.

The CalDAV integration settings may select one account and calendar resource as the standard for the current instance or personal scope. The effective query and create schemas then allow the model to omit both target arguments, and the system prompt requires this path unless the user explicitly names another calendar. Discovery tools are not used only to choose a target when the default applies. The bound host inserts the configured pair before validation, authorization, and live resource resolution. A complete explicit pair always wins; partial target arguments never mix with the default. Disabled or stale targets fail closed, and changing or deleting the selected integration removes the setting.

The same integration settings independently select a standard task-list resource for the current scope. The host binds it by default to `tasks_query`, `tasks_create`, and `tasks_create_many` when target arguments are omitted; an explicit complete target wins, with the same validation and fail-closed behavior as the standard calendar.

Shared integration schemas enumerate the active host-bound integration UUIDs. Runtime binding and revision checks remain authoritative when a model or provider ignores that schema constraint. Calendar create idempotency is derived from the persisted assistant message and tool call instead of being supplied by the model.

Task tools list task collections, query one collection, and create one or a bounded batch of tasks; update, complete, reopen, and delete remain single-task operations. They support a bounded title and note plus an optional `DUE` date or aware timestamp. Queries exclude completed tasks unless explicitly requested. Canonical results retain encrypted task tokens instead of remote hrefs, UIDs, or ETags. Model context projects those tokens as short references to their owner-, session-, and trust-scoped result messages; the host resolves a reference before normal token, binding, permission, and ETag validation. Mutations require the reference or token, account, and task-list key from the same result. Event tokens use the same projection. Creates use deterministic UIDs, updates and deletes use conditional ETags, and completion writes a UTC `COMPLETED` timestamp. Recurrence, relationships, alarms, and properties outside this initial field set remain readable but make updates unsupported.

Validated resource discovery stores bounded resource labels with the scoped integration defaults for later approval display. CalDAV approvals combine that label with the configured account name and summarize the requested event fields and timing. Missing labels fall back to the stable opaque resource key; labels remain display metadata and never replace the key in policy or grant matching.

CalDAV data remains subject to ownership, integration access, and the configured calendar action policy. Selecting the active model is the provider-release decision; public models do not require an additional session-wide release.

The `tasks_create_many` tool creates at most 50 tasks in one selected `VTODO` collection under one `tasks.write` approval. It reads the current open titles as a mutation precondition, compares whitespace-normalized titles case-insensitively, and skips matching existing or repeated requested titles. Completed tasks do not block a new item. Each created task retains a deterministic host-generated UID. The operation is additive only: it neither deletes nor rewrites existing tasks and therefore needs no synchronization state.

## Mail

The shared folder parser preserves IMAP special-use flags for Drafts, Sent, and Trash. Folder names alone do not assign roles. Mail search and the Control Center use the same server-side, per-folder full-text search and UID-based pagination. An omitted query lists messages by descending UID. Continuation cursors are encrypted and bound to the account configuration, folder, query, and `UIDVALIDITY`; changed bindings require a fresh search.

Send results distinguish SMTP acceptance (`sent`) from confirmed Sent-folder storage (`sentCopyConfirmed`). A false confirmation means that no Sent copy was confirmed, not that SMTP failed; null means the stored historical result has no copy status. This result is persisted with the existing send operation and returned on replay without sending or archiving again. Missing or failed Sent storage never triggers another SMTP send and is shown as a warning in the mail UI. SMTP acceptance does not confirm recipient delivery.

Generated Message-IDs use the configured sender domain rather than a local harness domain. The deterministic per-send identifier and persistent idempotency checks remain unchanged. SPF, DKIM, and DMARC are the mail server administrator's responsibility.

Sending a saved draft deletes the original only after Sent-folder storage is confirmed, including replay cleanup. A false or unknown confirmation preserves the draft as the sender's remaining mailbox copy; it does not authorize another SMTP send.

The IMAP/SMTP adapter represents one mail account per integration instance. IMAP and SMTP endpoints, TLS modes, username, and fixed sender address are non-secret configuration; the shared password or app password is stored as one encrypted owner-scoped credential. Only implicit TLS and mandatory STARTTLS are supported. The blocking standard-library protocol clients run in bounded worker-thread operations with verified TLS and controlled errors.

Mail policies are account-level actions: `mail.read`, `mail.drafts`, `mail.send`, and `mail.delete`. All support `disabled`, `ask`, and `auto`; defaults follow the saved trust preset by category. Sending and deletion support matching run or session grants, scoped to the account, binding revision and capability family. IMAP folders are live navigation targets, not policy resources. Mail tools release private untrusted data, use UIDs rather than sequence numbers, and return encrypted message and attachment tokens bound to the integration revision, mailbox, `UIDVALIDITY`, and UID.

Model context projects message and draft tokens as short references to canonical tool results, using the same session-bound resolver as calendar events and tasks. Resolution precedes normal account binding, token validation, and authorization; references never grant permission. Persisted tool arguments preserve only recognized short resource references, while full tokens and credentials remain redacted. Model history restores legacy redacted mail-read arguments from their paired successful result; other redacted resource arguments are explicitly marked as omitted and require a current reference for new calls. The same handling applies to provider function-call replay. Session forks remap recognized references in stored calls, edited arguments, and provider replay to the copied message IDs without rewriting ordinary text. Canonical history and the Mail HTTP API remain unchanged; no migration is required.

The compiled `mail` Control Center view is offered only after at least one effective enabled account has loaded. It reads folders and messages live, stores drafts through IMAP, sends through SMTP, and transfers attachments directly without a local mail database. HTML-only messages are reduced to bounded text, remote content is never loaded, and downloads are forced with private no-store responses. Draft edits preserve server-side attachments and reject messages that cannot be changed without loss. Draft replacement and deletion require UID-scoped deletion support; global `EXPUNGE` is never used. SMTP sends reserve a persistent owner- and account-bound idempotency record before dispatch. Replayed successful requests return success, while in-progress or uncertain results are never dispatched again automatically. This provides local at-most-once execution, not an SMTP delivery guarantee. Failure to create an optional Sent-folder copy does not turn an accepted message into a failed send.

## BookStack

The BookStack adapter is a knowledge integration. Each BookStack installation is an integration instance and each visible book is a resource. The static actions are `knowledge.read`, `knowledge.write`, and `knowledge.delete`; page, chapter, and book creation as well as page, chapter, and book updates share the write action. Book and chapter updates change name and description only; shelf membership is managed from the shelf side. API token ID and token secret are encrypted separately from settings and are sent as `Authorization: Token <id>:<secret>` over HTTPS only.

Content is exchanged as Markdown. Reading a page prefers the stored Markdown source and falls back to the Markdown export when the page was authored in the WYSIWYG editor. A page whose Markdown exceeds the readable limit is reported as an error rather than truncated, because a shortened copy could be written back as if it were the full page. Remote text is treated as untrusted data.

Page updates replace the whole page, so the model must read the page immediately before updating it. The observed revision travels inside the page token, and a Markdown replacement is refused when either the observed or current revision is missing or they differ. BookStack offers no conditional update API, so this is best-effort protection: an edit that lands after the revision check and before the update can still be overwritten. Renaming a page carries no revision requirement. A successful update reports only that BookStack accepted the request; the model must read the page again when it needs the stored result.

Models receive only integration UUIDs, opaque book keys, and encrypted page and chapter tokens, never raw BookStack IDs, URLs, or credentials. A token carries the integration ID and the binding revision, so a stale or foreign token is rejected instead of executed. Page, chapter, and attachment operations additionally re-read the current book of the resource they touch, so a resource that was moved out of an approved book cannot be edited through a token minted while it still belonged there.

Search and book listing are integration-wide discovery tools without a book key, analogous to calendar discovery. Because a resource key is what binds a call to a per-book policy, these tools apply the book policies themselves: books whose `knowledge.read` policy is disabled are dropped from search results and book listings, and shelf tools refuse to name them. A full shelf replacement keeps such books in place instead of unfiling them. Listings report `moreBooksExist` or `moreShelvesExist` when BookStack holds more entries than were returned, so a shortened list is not mistaken for a complete one. Resource discovery fails closed when the BookStack account can see more than the 500 books returned by one API request; otherwise unseen books could retain stale policy state.

Shelves are organizational containers, not resources. Shelf tools therefore take a plain `shelf:<id>` key instead of an encrypted token and are governed by the integration-level policy plus the book policies described above. Book creation accepts shelf keys so a new book is filed immediately, and book listings and reads report the shelves a book belongs to. BookStack does not expose shelf membership on the book endpoint, so the adapter derives it by scanning the shelves; when that scan fails the field is omitted instead of failing the whole call. Shelf updates support a full replacement as well as incremental add and remove lists, which avoids dropping books the model never saw. Combining both forms in one call is rejected. Deleting a shelf never deletes the books it contains.

Attachments belong to pages. The adapter can list, create, and delete them and returns encrypted attachment tokens bound to the same integration, binding revision, and book key as page tokens. An attachment is created from exactly one source: a URL that is downloaded and uploaded to BookStack, a managed session file, a file on the selected computer, or a plain link stored without transfer. Uploading a computer file requests the same `filesystem.read` permission as a direct model file read, so the upload path cannot bypass the per-computer filesystem policy. Managed files are read by the backend; computer files are exported from the bound MatoLoop Agent through a one-use transfer ticket. Downloads reuse the webfetch pipeline and shared `web_access` settings, so the configured address restriction, redirect handling, content type, and size protections apply, the configured webfetch policy is enforced, and a URL approval is requested whenever a direct webfetch would need one. Uploads are capped at 32 MiB and at the shared response limit, whichever is smaller.

BookStack offers no idempotency API, so creation tools do not ask the model for an idempotency key. A required key that nothing evaluates would cost tokens on every call and suggest protection against duplicate creation that does not exist.

A failed download reports the underlying webfetch code, such as a timeout or a rejected request, instead of one opaque failure. The model then sees why the host refused and can fall back to a link attachment rather than guessing at an unrelated cause. Servers that label documents as `application/octet-stream` are accepted when the file name still names a supported type; the extension then decides the type, and image payloads are still signature checked.

## Mealie

Mealie is a backend recipe and meal-planning integration. Each configured server is one integration instance with an encrypted long-lived bearer token. Its fixed tools list accounts; search, read, create, update, delete, or import recipes from a URL; and read, create, update, or delete household meal-plan entries. Multiple active servers share one stable tool set and require an explicit integration UUID after account discovery. Mealie does not require or use a MatoLoop Agent. Users create a token in their Mealie profile at `/user/profile/api-tokens` and configure the server's base URL without `/api` in MatoLoop.

The adapter accepts HTTP and HTTPS because private self-hosted installations commonly expose only HTTP. Requests remain on the configured origin and deployment path, append only fixed `/api` routes, reject redirects, ignore proxy environment variables, and bound streamed JSON responses. Operators are responsible for using HTTPS when the bearer token crosses an untrusted network.

Recipe search accepts a page number and returns `page`, `total`, `totalPages`, and `nextPage`, with at most 50 recipes per call. The agent follows `nextPage` using the same query, filters, and limit. An explicit ID tie-breaker keeps equally ranked results in a stable order. Remote pagination URLs are never followed. Filters require all supplied exact tag, category, and structured food names, using host-built Mealie query expressions. The parser does not support quoted-string escapes, so filter names containing quotes, brackets, backslashes, placeholders, or control characters are rejected by the client when building the expression. Unparsed ingredient text can be searched with the normal query. Meal-plan reads remain limited to 100 entries per call.

Models receive encrypted recipe and meal-plan tokens instead of Mealie recipe UUIDs or numeric plan IDs. Tokens bind the remote identity and observed fields to the integration UUID and canonical configuration revision. Recipe detail reads and writes return a token containing a hash of the complete remote recipe, including fields omitted from the model projection. Recipe update and delete require this detail token; search and meal-plan recipe references must first be passed to `recipe_get`. Before update or delete, MatoLoop reads the current object and rejects a changed snapshot; Mealie offers no conditional write, so a race after that check remains possible. Failed mutations with an uncertain remote outcome are not retried automatically.

Manual recipe creation uses Mealie's name-only create endpoint and then patches supplied content. If a follow-up fails, a partial recipe may exist and the result is reported as an unknown outcome. URL import uses Mealie's scraper; Mealie fetches the source URL shown in the write approval. Recipe updates use PATCH and send only explicitly supplied fields, preserving other data such as tags, images, notes, settings, and extras. Ingredient and instruction lists are complete replacements when supplied; quantities, food/unit names, ingredient notes and sections, instruction text, servings, yield, description, and time fields are supported. Returned recipes remain usable for meal planning. Native Mealie shopping lists and organizer management are not exposed.

Before sending replacement ingredients, the client resolves food/unit names, plurals, aliases, and unit abbreviations through the selected account's group-scoped API. Missing records are created as part of the authorized recipe write, as shown in its approval. Only IDs and canonical names are sent in the ingredient references; unrelated food/unit metadata is not overwritten. Each replacement ingredient gets a persisted `referenceId`, preventing Mealie's read-time fallback UUIDs from invalidating recipe snapshots. Resolution reuses repeated names within the write and reads at most 100 pages of 100 records per distinct name; names unsupported by the filter grammar use an exact local match over bounded pages. A later failure after food/unit creation is also reported as an unknown outcome.

Recipe and meal-plan data is private untrusted integration content. Search and detail results bound text and collection sizes. Meal-plan writes accept recipe tokens from the same binding or bounded free text. The static actions are `recipes.read`, `recipes.write`, `recipes.delete`, `meal_plan.read`, `meal_plan.write`, and `meal_plan.delete`; defaults follow the saved trust preset by category. Recipe permissions use the existing owner-bound `recipes` resource area and separate read/write/delete category grants. Credentials and rebinding invalidate these grants and outstanding references.

MatoLoop composes Mealie with CalDAV through the normal agent tool loop rather than a direct service bridge. For a weekly shopping request, the agent reads the plan and recipes, combines only compatible ingredient quantities, and calls `tasks_create_many` on the configured CalDAV shopping task list. No cross-integration table or durable synchronization marker is stored.

## Arcane

Arcane is a backend Docker-management integration. Each instance stores its HTTP or HTTPS manager URL and one encrypted `X-Api-Key` credential. The key's Arcane environment permissions remain a hard bound independent of MatoLoop's profile permissions. HTTP is suitable only on a trusted network. Multiple instance or personal connections share static, host-controlled tools; the model cannot supply an endpoint, HTTP method, arbitrary request body, or Arcane credential.

The tools list accessible environments and paginated containers, projects, images, volumes, and networks; read selected resource summaries, project runtime and image-update status, and bounded container logs; run named container and project lifecycle actions; pull or tag an image; create a basic container, volume, or bridge network; connect or disconnect a container from a network; rename volumes; configure container auto-update; and delete a selected resource. Environment IDs are discovered live and used as resource-policy keys. All actions inherit the saved private/public preset by their `read`, `write`, or `delete` category, including account discovery. Explicit connection, profile, and resource overrides remain authoritative. Sysadmin retains its existing profile selection and overrides: Arcane is offered only when enabled for that profile, and the profile's filesystem/shell read rules do not override Arcane permissions. Arcane's own RBAC checks every request. The adapter deliberately excludes Arcane administration, container exec, arbitrary standalone container configuration, and bulk pruning. Remote responses are untrusted and projected to allowlisted summary fields.

`arcane_project_config` reads a project's Compose, environment, override, and included Compose content. It returns authorized content without integration-specific masking. As with other tool results, original content may be stored in the conversation; the central provider/model pseudonymization setting controls protection of recognized secrets before model transmission and restoration in returned tool arguments. Disabling pseudonymization permits authorized content to reach the model unchanged. This is not a guarantee that every environment value is detected as a secret.

The encrypted `snapshotToken` contains only the configuration digest and its session, connection, environment, project, and binding identities. It carries no configuration copy or secret mapping. Old masking-based snapshots must be refreshed. `arcane_project_save` creates a project using Arcane's multipart project/manifest contract or updates only explicitly supplied fields. New secrets use the existing protected-text `value_ref` contract. After resolving references, the adapter refreshes its binding and rechecks required permissions without opening another approval. Included files are read-only. Approval shows the proposed replacement fields, with protected references unresolved. Before updating, the adapter rereads the configuration and rejects a changed digest. Text is limited to 80,000 characters per field and the projected configuration to 256 KiB of serialized JSON, including Unicode escapes; the prospective configuration is checked before writing. Full configuration read/update responses have a separate 2 MiB transport budget for Arcane's derived details. Arcane's project PUT has no conditional-write contract, so an edit between that check and PUT remains a race.

Saving does not deploy; use `up` separately. Project `up` and `update_services` authorize a read as well as the mutation and return a bounded runtime/health snapshot. Failed verification is reported separately from the confirmed mutation and must not trigger a redeploy retry. Services whose health is still starting can be checked again with `arcane_get`'s runtime view.

Project configuration reads, including the consistency read before updating an existing project, set the existing `sensitive_access` flag. They therefore also honor `sensitive_data.access` and the preset's `read_sensitive` category. Normal status and resource summaries retain ordinary read behavior; Sysadmin does not bypass the sensitive-data guard.

Clearing an existing environment file or removing its Compose override additionally requires the existing `arcane.delete` capability for that project. These operations use explicit empty text; protected references that resolve to empty content are rejected for updates, so resolving a secret cannot silently turn an approved write into a deletion. Creating an empty environment file remains a write.

Container logs use Arcane's non-following WebSocket endpoint with server-side `tail` (200 lines by default, at most 500), a 32 KiB output bound, a 256 KiB capture/message budget, and a 30-second capture deadline. Large lines within the message budget are shortened instead of rejected. A larger message ends capture with explicit truncation; the deadline retains already captured lines and reports `captureComplete=false`. The endpoint does not emit an end marker or close its hub after finishing; capture therefore also stops after an idle timeout and reports `captureComplete=false` rather than claiming completeness. Output truncation is explicit. Logs may include private application data. WebSocket requests reject redirects before following them and ignore proxy environment variables. Project creation, configuration fields, and log framing were checked against the upstream Arcane `v2.15.1` API contracts.

Requests stay on the configured origin and deployment path, ignore proxy environment variables, reject redirects, and bound responses. Long-running deploy and pull endpoints are NDJSON streams; only Arcane's `done` event confirms success, and raw progress logs are not sent to the model. A failed or interrupted mutation is reported as an uncertain outcome and is never retried automatically. Rebinding or replacing a key invalidates existing profile overrides and in-flight tool bindings.

## OpenCode

OpenCode is a personal-only backend coding integration. One instance stores a canonical HTTP or HTTPS base URL, username, discovered server root and version, and an optional encrypted Basic Auth password. The client ignores proxy environment variables, rejects redirects and cross-origin targets, bounds responses and SSE events, and maps upstream failures to controlled errors. Every use probes the server and rejects a changed root. Browser and model contracts expose only relative project, workspace, and file identities.

A MatoLoop project may connect one OpenCode project and workspace from the Control Center. The binding may change or disconnect until the first plan is saved; changing it clears model selection, model variants, and queue pause state. Separate live-discovered models drive read-only analysis and plan execution. Each model may advertise opaque variant names; MatoLoop exposes only those names, stores separate optional analysis and execution selections, and omits `variant` from the OpenCode request when the model default is selected. OpenCode analysis returns repository findings; the MatoLoop agent authors and persists the canonical Markdown plan. Plan creation snapshots the configured analysis model and variant, while enqueueing snapshots the exact plan plus the execution model and variant before processing records serially in FIFO order. Existing remote activity pauses execution, remote permission requests require an explicit response, cancellation is best effort, and uncertain post-dispatch outcomes are persisted without automatic retry. The Control Center provides binding management, model and variant selection, read-only files and status, plans, queue state, cancellation, and permission decisions; it has no editor, terminal, Git, download, reorder, or retry surface.

## tbs.Desk

tbs.Desk is a personal-only support integration. It stores an HTTP or HTTPS base URL and username as configuration and the password as an encrypted owner-scoped credential. Requests authenticate with a short-lived bearer token, ignore proxy environment variables, reject redirects, bound response bodies, and expose only controlled errors.

Customer lookup uses the tbs.Desk ERP search when the initial message contains a customer hint; otherwise it checks the active call first. Results are persisted in the session and shown as a normal Markdown table with host-validated prepared-reply links. Selecting a customer sends a separate user message without consuming the current composer draft or its attachments. The backend accepts only ERP customer numbers from the current persisted result set. Ticket searches use the selected ERP customer number, and ticket details are released only after a customer-scoped filter confirms ownership.

Each enabled account contributes a transient protected **Support-Assistent** profile bound only to that integration. The profile disappears when the account is disabled, deleted, or administratively unavailable. Customer selection is persisted as bounded session state before ticket tools become usable. Ticket search always injects the selected customer server-side, ticket reads verify the returned customer ID, and persisted state contains summaries but never ticket bodies.

## Git via Shell

Git is not an integration. Git operations use `shell_run` on the selected, connected MatoLoop Agent with Git installed. Repositories remain on that computer; the backend does not clone repositories or provide a Git fallback.

The Git Control Center app separates **Änderungen** (the session-workspace change list and agent actions) from **Einstellungen** (mode and repository configuration). Individual files open the existing editor's read-only Git comparison. The overview and editor use an owner-bound browser API, not a model tool or Git integration. **Computer-Dateien** remains a filesystem tree. See [the architecture contract](architecture.md#matoloop-agent-boundary).

Project settings discover repositories on the selected computer and configure a
target branch and default workspace mode. The Git Control Center app controls the
session mode and remote target, with explicit adoption after address changes.
Sessions can use an owner-bound managed worktree from the committed local target
branch, or a freshly fetched target when a remote is selected.
Shared WebUI/Telegram coding commands start ordinary agent flows for initialization,
remote setup, review, merge/publication, pull requests and project synchronization. See
[the command system and managed worktrees](commands.md).

Git commands follow ordinary shell inspection and permissions: recognized actions require read, write and/or delete. Normal consent is computer/category-bound rather than workspace-bound. Read/write prefix rules remain optional and cannot approve delete. Hard computer zones, ownership, sensitive-data and revision checks still apply. Read classification is not a guarantee of side-effect-free execution. See [the shell policy contract](architecture.md#matoloop-agent-boundary).

Shell Git runs with the agent operating-system user's access, without the removed integration's Git-specific isolation or network policy. Operators manage Git configuration, credentials, and host filesystem and network restrictions on that computer. See [upgrade cleanup](user/betrieb-und-datensicherung.md#removed-git-integration).

## OpenSCAD

OpenSCAD is an agent-bound computer integration. One instance selects one owned MatoLoop Agent and the canonical OpenSCAD executable discovered and validated when that agent starts. The model does not submit executable paths, camera values, environment variables, or arbitrary OpenSCAD arguments. It creates or edits `.scad` source with the normal file tools, preserves an explicit safe `.scad` basename exactly, and otherwise chooses a descriptive filename. Unless the user chooses a path, each new model gets a dedicated directory under writable session files and that directory is passed explicitly as the render project. Projects should use only OpenSCAD built-ins or relative dependencies stored inside that directory.

CAD rendering uses the `write` category, which requires approval under the shipped private/public presets. The selected base preset, scoped connection rule or profile override may permit it automatically. Filesystem policies, project bounds, disabled integrations, and MatoLoop Agent availability remain independent hard limits.

Generated source treats unspecified dimensions as millimeters and keeps important dimensions and fabrication clearances as named parameters. Describing a part as printable does not authorize unrequested tolerances, chamfers, fillets, other features, or unused parameters. Holes are cutters inside a boolean difference rather than separate positive geometry. Source avoids zero-thickness or coincident boolean geometry, and through-cutters extend past both sides without applying their epsilon to the outer solid or any stated dimensions. Requests for one printable part additionally target connected closed geometry and check wall thickness and fit without altering stated dimensions. After each material source change, the model renders the exact entrypoint and project directory. The MatoLoop Agent produces one OFF model and labeled front, back, left, right, top, and bottom PNG views; the backend validates them and persists one internal 2x3 contact sheet. File-explorer previews request only OFF, and source PNGs remain transfer intermediates. The backend derives triangle count, bounds, dimensions, component count, and open and non-manifold edge counts from OFF. These topology values are evidence rather than automatic failures because multi-part output can be intentional. An explicit export produces one binary STL. After every preview, an isolated tool-free vision request inspects the sheet with up to seven current reference images. It uses the active model when that model can receive the images safely; otherwise it uses the configured general vision model. The active vision model also receives the sheet through normal image projection in the following agent request. Without an eligible vision model, the render remains successful but is marked visually unverified. Render success, matching bounds, and a visual pass do not prove hidden geometry, fit, wall thickness, strength, manifoldness, or printability.

Session projects cross the backend boundary as bounded ZIP archives; computer projects are copied through no-follow directory descriptors. The agent extracts or copies them into a private staging directory and starts the canonical OpenSCAD executable directly, without a shell, with fixed arguments and a private environment. The executable path must still match the canonical device and inode recorded at agent startup. Resource limits, timeouts, bounded diagnostics, and output validation remain in force. These controls are not an operating-system sandbox: OpenSCAD inherits the agent user's filesystem and network access, so deployments that require stronger isolation must run the MatoLoop Agent in a suitable container, VM, dedicated account, or equivalent host policy. Rendered artifacts live in the disposable, size-bounded agent cache until the backend imports returned exports as revisioned managed files.

The file browser keeps `.scad` editable as UTF-8 source and offers an explicit 3D view when a matching integration is connected. Binary STL files use a client-side interactive viewer with fixed byte and triangle limits, orbit, pan, zoom, and standard camera positions. Oversized models remain downloadable instead of being parsed in the browser.

## Browser

`list_execution_agents` includes the enabled, profile-visible integrations bound to each owned computer, even before a computer is selected. This is configuration metadata, not a readiness check or permission grant; browser use still requires selecting the computer and following the existing tool-loading and authorization rules.

Browser is a personal-only, Linux agent-bound integration with one immutable instance assignment per owned MatoLoop Agent. It reuses global adapter availability, profile integration selection and trust-scoped policies. `browser.use` covers all ordinary browser actions and website JavaScript; `browser.code` adds unrestricted Python execution. Both use the `write` category and distinct grant resources. Browser use defaults to AUTO for Build-based profiles except in `ask_all`, and ASK otherwise. Python defaults to ASK in every profile. Explicit connection/profile rules remain binding. Native and container agents offer the same headless browser and optional viewer. Model tools do not require an open viewer. Plan, Build, and Sysadmin exclude the integration by default unless enabled through the existing profile settings.

Optional native setup runs only from the integration's dedicated interactive setup dialog using the fixed packaged script; agent images already contain the runtime. Disposable website profiles are isolated per chat/computer binding. See [Browser architecture and operations](browser.md) for actual Compose security settings, viewer lifetime, clipboard/file transfers, and action snapshot limits.

## Web Search

`web_search` accepts a compact `query` and optional `search_type` (`web` by default or `images`). Image hits add `imageUrl`; fetch the exact URL before using the image. The host selects one provider; model arguments cannot override it. No-key metasearch is catalogued as `no_key` but is not an integration. Every active SearXNG instance adds `searxng:<uuid>`; display names never change that identity.

Each normalized result contains `sourceId`, `title`, `url`, `snippet`, and `publishedDate`. Only the host derives `sourceId` from the canonical URL; providers cannot supply it. Results with the same canonical URL are deduplicated. Snippets are untrusted discovery data, not verified page content. Invalid provider JSON produces a stable integration error rather than technically successful empty evidence.

SearXNG and Jina connections are instance-only, including for administrators. One provider per tool is configured through `/tools/configuration` under **Administration > Tools > Einstellungen**, linked from the integration editors. Existing global primary selections are retained; legacy fallback values and stored personal search connections and overrides are ignored, not promoted. When SearXNG returns no results and reports unresponsive default engines, MatoLoop retries once through the same instance with `bing`, `mojeek`, and `presearch`. There is no automatic cross-provider retry. Missing, disabled, or profile-excluded configured providers make the tool unavailable rather than silently changing its selection. See [Webfetch](webfetch.md) for networking rules.

The built-in no-key metasearch uses the Python `ddgs` client with automatic backend selection and runs the synchronous call outside the async loop with a bounded timeout. Different public search services may respond depending on current availability. The persisted legacy key `duckduckgo` is normalized to `no_key` when loaded. Search queries leave the installation and are sent to the service in use.
