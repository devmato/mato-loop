# Architecture

Use the [documentation index](index.md) for the full contract map. Memory/Dreaming boundaries live in [memory.md](memory.md); central file-backed Agent Skills packages, scoped registry storage, computer working copies and building in [skills.md](skills.md); model assignments in [session-templates.md](session-templates.md); protected input and questions in [questions.md](questions.md) and [protected-tool-text.md](protected-tool-text.md). This document summarizes cross-layer boundaries.

MatoLoop is a provider-neutral monorepo. FastAPI provides REST and SSE interfaces; the Quasar PWA consumes only this API.

## Layers

- API: HTTP contracts, authentication, and dependency injection
- Services: transactions and application logic
- Agent: provider-neutral model and tool loop plus host policies
- Execution: outbound MatoLoop Agents for selected filesystem, process, and static local-integration operations
- Providers: replaceable LLM and search transports
- Memory: current-session context plus audience-filtered durable and owner-scoped prior-session retrieval
- Embedding: local Infinity transport and asynchronous durable-memory and episode vectors
- Persistence: SQLAlchemy models, Alembic migrations, and settings documents
- Frontend: presentation, user interaction, and localization

MatoLoop is a modular monolith, not a collection of internal microservices. Backend API
routes retain HTTP schemas, dependencies, status codes, and controlled error mapping. The
`sessions` and provider settings services own their application workflows, while the API
workspace service owns reusable HTTP context and dispatch rules. Transaction and
filesystem compensation boundaries stay in those application services. Provider adapters,
the agent runtime, integrations, and MatoLoop Agent operations expose explicit module-level
contracts and do not depend on FastAPI routes.

The agent package separates the run lifecycle, turn loop, prompts, projections,
summarization, and title generation. Model-facing tools live under `tools`, policy
and approval workflows under `permissions`, and reusable web, file, and media
operations under `web`, `files`, and `media`. Tool handlers own their definitions;
the catalog assembles them explicitly in stable order. See [Module ownership and
dependencies](modularity.md) for the module map and executable import boundaries.
SQLAlchemy models are split by aggregate and re-exported through `models`; Alembic still sees
one metadata graph. The frontend groups pages, components, stores, and helpers
by domain under `features/`. Its existing `stores/*` and moved `utils/*` imports
are stable, stateless re-export facades. Application layout and Control Center
composition live under `app/`; shared presentation remains under `shared/`.
Standard content pages use `shared/ui/AppPage.vue` for their page container,
title, description, and optional header actions. The shell reserves space above
these pages for its floating navigation button, using the same size and inset
variables as the button and including the device safe-area inset.
The standalone implementation lives in `apps/matoloop-agent` under the `matoloop_agent`
package. It has no backend package or database dependency.

## Authentication and Ownership Boundary

`UserAccount` is the stable internal principal and is independent of a login method. The first local setup account is an active administrator; upgrades promote the earliest existing account. Administrators can create local accounts, reset passwords, activate or deactivate users, assign administrator status, and delete deactivated users. The last active administrator is protected. The role grants account administration and instance-settings mutation only: every content API still applies the authenticated owner's ID, there is no impersonation path, and an administrator cannot inspect another user's sessions, messages, files, memories, credentials, personal settings, approvals, or MatoLoop Agents.

Local username and password authentication is currently the only implemented provider. Usernames retain their entered spelling but are compared and constrained case-insensitively. `AuthenticationProvider` and `UserAuthIdentity` persist the foundation for external login providers, and provider subjects are unique only within a provider. No external provider transport, callback route, or login/linking UI exists yet. A future provider may independently enable just-in-time creation of a non-administrator account. Existing authenticated users must self-link explicitly; MatoLoop never links accounts from a matching username or other mutable profile value, and unlinking cannot remove the final login method.

Sessions own messages, runs, approvals, grants, notifications, and internal session storage. Optional projects group owner-bound sessions and own coding executions, but do not merge their managed files or plans. Memories, credentials, personal settings, and `ExecutionAgent` records carry the same user boundary. Workspaces are ordinary absolute paths externally owned by MatoLoop Agents. Owner checks apply in services and queries before trust or retrieval filtering. Instance-scoped providers, models, integrations, integration resources, and tool policies are deliberately shared configuration and are not another user's personal content.

The embedded debug MCP is a read-only production-diagnostics path, not administrator impersonation. One personal switch issues a revocable token and enables bounded diagnostic recording for that active administrator. Owner-bound tools derive their owner from the token and filter supplied identifiers by that owner. The `get_backend_logs` tool additionally grants active administrators read-only access to instance-wide backend application logs, including entries related to other users. Losing administrator status, account deactivation, token rotation, or deactivation immediately removes access. Diagnostic events retain the effective model context and schemas, timing, controlled errors, and tool execution metadata for 14 days with a one-megabyte event limit. They never contain credentials or unfiltered provider responses. The MCP depends on a working backend and database; infrastructure failure diagnosis remains outside this boundary.

Backend application logs are also written as JSON lines to the fixed `<data_dir>/logs/backend.log` path using Python's rotating file handler (one MiB per file, one backup). Only the `mato_loop_backend` logger and its children are captured; external SDK and HTTP access logs are excluded. Messages are capped at 8,000 characters; tracebacks record the exception class and last twelve file/function/line frames without exception values, source lines or local variables. `get_backend_logs` reads both files oldest first, returns the latest matching entries, supports logger-prefix and minimum-severity filters, and caps replies at 50,000 characters. Log reads are best-effort during concurrent writes and rotation. MCP OAuth failures log the current phase, controlled error code, exception/cause classes and validation fields/rules without validation inputs or context. These logs are diagnostic data, never model instructions.

Unexpected exceptions caught by the tool executor record a `tool.failed` event before returning the controlled `tool.executionFailed` result. The event links the owner, session, run and tool call, and includes the exception class and the last twelve traceback frames as module, function and line number only. Exception text, source lines and local variables are excluded. Existing diagnostic MCP queries expose these events under the same access and retention rules; recording does not establish whether a tool's external effects completed before the error.

## Projects and Coding Boundary

Projects are optional owner-bound session groups; standalone sessions remain valid. A project may connect one personal OpenCode binding from the Control Center containing only the integration ID, remote project identity, relative workspace identity, separate analysis and execution model keys with optional model-specific variants, and queue pause state. The binding may change or disconnect until the first plan is saved; model selections, variants, and queue pause state reset when it changes. Remote absolute paths remain backend-only, and OpenCode is a backend integration rather than an LLM provider or MatoLoop Agent.

A project may store one owned MatoLoop Agent and normalized absolute working directory as defaults for new chat sessions. They are copied when a session is created, then remain ordinary independently editable session settings; changing the project or moving an existing session does not synchronize them. Saving and applying the defaults reuse the normal agent ownership, availability, path, and filesystem-policy checks. The project itself receives no directory grant; the existing session-scoped grant is created only when a new session adopts the defaults.

OpenCode performs read-only repository analysis. The MatoLoop agent uses those findings to author the canonical persistent Markdown plan. Plan creation snapshots the configured analysis model and variant; enqueueing snapshots the exact plan revision, text, execution model, variant, and working directory. A null variant delegates to the OpenCode model default, while an explicit variant must still be advertised by that model before dispatch. Executions are persistent FIFO records with at most one active execution per project. External OpenCode activity pauses the queue; restart or an uncertain post-dispatch failure records `outcome_unknown` and is never replayed automatically. OpenCode permission requests remain visible and require `once`, `always`, or `reject` before execution continues.

## Chat Submission Boundary

The browser keeps unsent chat submissions and their attachments in an owner-scoped IndexedDB outbox and drains each session in FIFO order. Follow-up messages wait while a run, approval, question, or conflicting mutation blocks them; direct messages may join their matching active run. Every entry has one browser-generated UUID, reused as the requested `AgentRun` ID for a new run or as the direct-message ID for a continuation. Existing-session entries also snapshot the chosen agent profile. The message endpoint applies that profile to the session and the new run in the same transaction, after the previous run finishes; the active run keeps its original profile. Session creation and message endpoints return the canonical persisted session, input message, and run when that owned UUID already exists; a UUID tied to another owner or session remains a conflict. This makes retries after an unknown HTTP outcome safe without turning persisted run state into a resumable backend execution queue. Failed sends remain paused in the browser until the user retries, and logout or account replacement clears the previous owner's outbox before reloading.

During an active run, the composer defaults to sending directly into the current run. Its round main button stops the run while the draft is empty, then sends once text or attachments are ready; during a microphone recording it finishes the recording and sends only after the attachment is accepted. The small menu appears when a message can be sent and switches to sending after the run until the user switches back. A direct submission is persisted in the outbox before delivery and uses its stable UUID as the new message ID. The owned continuation endpoint accepts it idempotently while the run is active. An in-flight model request is cancelled, its visible partial output is persisted, and the same run rebuilds context with the new message; active tool work finishes first. A persisted direct message supersedes a pending approval in that run: the request expires, the waiting call and remaining calls in its batch receive `tool.superseded` results, and the same run replans with the new instruction. Completed effects remain recorded; a new instruction grants no permission, and replanned actions require normal authorization. If a direct message arrives between a tool call and its result, model context places the matching persisted results before the message; prior results of the same active run remain current evidence subject to ordinary context budgets. Database chronology stays unchanged. Legacy redirected cancellation also waits for an active tool batch to persist its results before stopping the run, while an explicit stop still cancels immediately. Previously queued submissions remain separate FIFO follow-up runs. After a backend restart, an unaccepted direct message stays in the outbox until a new run can accept it. The original run profile remains in effect for all in-run messages; profile selections made during that run apply to later runs.

Session settings remain editable during active runs. Before committing the first runtime-setting edit, the session update service retains the previous model overrides, session profile, reasoning effort, memory mode, and web-search policy in the process-local runtime state for the active run. This state is shared by tool rounds, approvals, and direct-message continuations and is removed when the run finishes, fails, or is cancelled; it is not stored in the database or restored after a restart. Runtime reads retain that snapshot and the run's computer, directory, and agent bindings without writing frozen values back to the session. New runs use the newly saved settings. Instance availability and permission policies remain live; project moves remain blocked during active runs. Background refreshes do not disable settings or close the directory picker unless its session or computer changes, and grant refreshes keep their loading indicator silent after the initial load.

## PWA and Push Boundary

The production frontend is an installable PWA. Workbox precaches its generated HTML, scripts, styles, fonts, icons, and manifest as one revisioned application shell; same-origin application navigations use that shell, while API and documentation requests remain outside it. A newly installed service worker waits until the user chooses to update. The page sends `SKIP_WAITING` directly, without an additional confirmation or unsaved-data check. App windows running this update flow reload once when the new worker takes control; the initial worker installation does not reload them. Update reloads bypass the ordinary `beforeunload` warnings, so unsent in-memory data can be lost by choosing to update. A failed or stalled activation leaves the update button retryable; a late takeover still reloads open windows. The stable `/sw.js`, manifest, and network HTML entry point are served without HTTP caching. Update checks run at startup, when the app becomes visible, after connectivity returns, and hourly while visible.

An administrator configures Web Push as an instance setting; the installation key remains under `/data/secrets`, and users grant permission per browser or installed PWA only after a direct user action. Browser subscriptions are owner- and device-bound, their endpoint and key material are encrypted with the credential key, and delivery accepts only the built-in HTTPS origins for the Google, Mozilla, and Apple browser push services without redirects. Re-registering a browser endpoint atomically transfers it to the currently authenticated owner so an expired prior login cannot keep receiving notifications on a shared browser. Focused app clients renew a short process-local user presence lease; while any lease for the user is active, all Push delivery is skipped on every device without affecting canonical messages or in-app actions. Presence expires after missed heartbeats and clears on backend restart, so uncertain presence fails open. Producers dispatch versioned, host-validated payloads only after committing canonical notifications, messages, approvals, or questions. Delivery is best effort and can never roll back those records; stale subscriptions are removed only after a terminal push-service response.

## Configuration Boundaries

Bootstrap and infrastructure values come from environment variables. Operational settings are stored as typed Pydantic documents in the PostgreSQL `settings` table.

Additive settings fields have Pydantic defaults. Settings documents declare instance or user scope. Instance documents use `settings.user_id IS NULL`; user-scoped documents are loaded and stored with an explicit `user_id`. Partial unique indexes enforce the two namespaces separately. Background processing derives user scope from persistent session ownership and never uses an implicit request user. API keys and OAuth tokens are referenced by ID from the separate `credentials` table instead of being stored in settings JSON. Credentials carry the same nullable owner convention: null means an intentionally shared instance credential, while a user ID means personal and owner-only. Credential payloads are encrypted; the Fernet key is created under `/data/secrets/credential.key` on first use.

The model-facing `customize_matoloop` tool exposes only owner-scoped profile, active-persona, memory, variable, and connection settings; it never patches arbitrary settings JSON, UI preferences, or instance settings. It reuses existing identity rules, variable persistence, and the product services for personally configurable SearXNG, CalDAV, IMAP/SMTP, tbs.Desk, BookStack, Mealie, Arcane, SonoBin, OpenSCAD, OpenCode, browser, and MCP connections. The UI and tool share service-level validation and persistence for search selection and CalDAV resource defaults, including discovery, resource labels, and selection ownership; HTTP and tool responses only map controlled errors and payloads. Integration services retain discovery, execution-agent ownership, encrypted credentials, and cleanup rules. Product connection mutations from the agent use a separate database session, so service commits and failure rollbacks cannot invalidate live agent objects. API resource reads leave the caller's transaction intact; permission writes retain their revision and ownership checks after discovery. `secret_input` is available without a shell and returns opaque run or session references usable by shell commands, variable storage, and integrations; stored personal-variable IDs can also be resolved after owner-bound access approval. Values are resolved only inside the backend and never returned to the model. Reads and writes use separate runtime policies; approvals precede mutations, and policy and integration availability are checked again after approval.

Personal variables are owner-bound credential rows with case-insensitive unique names. Ordinary values may be returned to the owning user or an authorized model, while secret values are omitted from every read response. The model receives only credential IDs as value references. A protected host question collects direct `variable_write` writes without persisting or returning the submitted plaintext. `secret_input` keeps newly submitted plaintext only in the active run or session's memory and returns an opaque reference to the model. `shell_run` and explicit `customize_matoloop` variable or integration configuration use the same backend resolver for owned variable IDs and temporary references. The resolver releases plaintext only to the executing backend handler; persistence still uses the existing credential services. `shell_run` keeps its independent command classification, approvals, and process environment behavior. Resolved environment values apply only to the executing process. Run-local references are discarded when the run ends and cannot survive a restart. Persisted arguments retain references, and process output is redacted before publication. Environment injection makes shell inspection incomplete because process behavior may depend on arbitrary variable names, but preserves the inspected read/write classification. Protected environment names, secret-access approvals, disclosure checks, and incomplete-analysis boundaries still apply. Output redaction removes exact values but is defense in depth, not containment against a command that transforms or persists a value. There is no reference cache or temporary secret record to recover after a restart.

Only administrators mutate instance settings. Administration contains global profiles, tools, integrations, and MCP servers; Settings contains the owner's personal configuration. Administrators separately gate personal providers, personal profiles, personal profile tool overrides, and integration adapter availability. Personal providers and personal tool-right customization default to disabled; personal profiles, personas, and skills default to enabled. Missing fields use these defaults without materializing former implicit allowances; explicitly saved values remain unchanged. Administrators may use personal configuration despite personal-setting gates; a technically disabled adapter remains unavailable. Each integration adapter is `full`, `instance_only`, or `disabled`, with `full` as the default except for hidden adapters with dedicated APIs. Agent-executed adapters support only `full` and `disabled` because their instances are owner-bound. Availability changes preserve stored configuration. Agent-bound instances must reference an `ExecutionAgent` owned by the current user.

Tool settings contain instance-wide availability, technical parameters, private/public permission defaults, and shell prefixes. Administrators may customize built-in access settings through the existing `builtin_access_overrides`; removing an override restores the shipped baseline. Ordinary users cannot override built-ins directly. Global and personal custom profiles inherit their selected core base and store sparse action rules, tool availability, and optional shell prefixes. Profile availability overrides the base map, but cannot enable a globally disabled tool. The personal tool permission gate also controls personal availability and prefix overrides; when disabled, stored personal changes are ignored and the base rules apply. Profile-content updates preserve access settings and reject permission changes. Integration and resource permissions belong to each integration instance and are edited there. Personal instances may override their own permissions and availability by accessible global or owned profile ID, independently of the personal-profile gate. Global integrations accept administrator-managed overrides for global profiles only. Global tool availability, network restrictions, integration enablement, ownership, remote ACLs, and delegation ceilings are hard bounds.

Infinity is host-controlled local infrastructure, not a selectable LLM provider. It is reachable only inside the Compose network and computes query, durable-memory, and prior-session message-chunk embeddings with a pinned multilingual model. pgvector stores this derived data in PostgreSQL beside canonical memories and messages. Backend availability does not depend on Infinity and falls back to PostgreSQL FTS. Ownership, current-session exclusion, source-session mode, and durable-memory audience filters are applied in SQL before vector limits; the local embedding service never grants visibility.

The authenticated global search reuses the same message-chunk FTS and embedding index instead of maintaining a separate UI index. Project names and session titles use owner-filtered substring matching; message results use hybrid lexical and cosine ranking and remain available as lexical results when Infinity is unavailable. Like model-facing prior-session retrieval, direct owner search spans all of that owner's projects and standalone sessions. Eligibility still differs: UI search may include the current session and sources in any memory mode. It may return both message trust levels because the authenticated session API already exposes that owner's canonical transcript. Every search lane applies the owner filter before ranking and limits.

## Memory Boundary

Normal project memory context has four layers: canonical current-session context, every visible pin in full, a compact project-session index, and bounded automatic snippets from relevant unpinned memories and prior sessions. The separate owner-scoped user profile is projected independently of `memoryMode` between assistant persona and project context. Its six maintained fields support shared and trust-specific values, are not embedded or searchable, and suppress exact normalized duplicates from every memory retrieval path. Current user statements override the profile, which overrides durable and prior-session memory. Every eligible turn builds one latest-message or short-follow-up query and shares one embedding across both automatic search lanes, with PostgreSQL FTS fallback. Fixed configurable quotas default to two memory snippets, three relevant-session snippets, and two recent snippets for bootstrap or explicit recent-session overviews. The fully serialized automatic payload defaults to 1,024 tokens and is capped at 10% of usable input. Pins are outside that budget; projection retries without automatic snippets but fails safely if the complete visible pins cannot fit.

Automatic relevant and recent source sessions must be `full`, must belong to the same owner regardless of project membership, including standalone sessions, and must not be the current session. Project requests receive up to ten recent eligible sessions from the same project ordered by their latest eligible message; the bounded index contains titles and exact `session_read` arguments but no message content. The project-session index and project sidebar remain project-local. Project requests then spend the remaining automatic budget on relevant snippets from distinct owned sessions before non-overlapping recent snippets and unpinned memories of any source provenance. A semantic session reference carries only the strongest topical anchor. Optional project instructions remain the authoritative place for deliberately maintained project rules; they complement rather than replace session evidence. Receiving `full` and `read_only` sessions may use the context; `disabled` sessions receive none. Authenticated UI search and explicit permission-controlled session tools continue to cover owned `read_only` and `disabled` sessions. Persisting eligible messages creates deterministic search chunks and FTS transactionally, embeddings remain asynchronous, and lexical retrieval remains available when embeddings fail.

Dreaming processes eligible completed messages from top-level `full` chat sessions. Automations now use ordinary visible chats; automation-origin metadata is not a blanket Dreaming exclusion. Child sessions and error/incomplete messages remain excluded. Extraction targets durable user-specific knowledge outside the maintained profile, not temporary work or implementation details. Reconciliation supports `create`, `unchanged`, `update`, `merge`, and explicit-evidence `remove`; uncertain identity creates a separate record, and age/non-mention never justifies deletion. New memories are unpinned; updates/merges preserve pins without promoting them.

Dreaming has only update and remove policies, defaulting to `auto` and `ask`. A merge requires both: either `disabled` skips it, either `ask` creates one approval, and only both `auto` apply directly. Persistent `memory_change` approvals store and revalidate exact target and policy snapshots under lock, and stale requests cause no partial mutation. Merge preserves evidence and pinning and deletes redundant rows in the survivor transaction. Durable memories, retrieval, approvals, and Dreaming runs are owner-scoped.

## Provider Boundary

Provider adapters transport model messages, tool schemas, tool choice, text deltas, and tool calls. They never execute tools or manage sessions and file permissions. Responses API function tools explicitly disable strict mode so provider-side schema normalization cannot turn optional host arguments into required model arguments; MatoLoop validates every returned call itself.

- `openai-codex` uses the ChatGPT device-code flow suitable for self-hosted interfaces and isolated Codex Responses and image-generation transports. Login requires neither a public callback URL nor a local callback port.
- `openai-compatible` supports Chat Completions and Responses API.
- `lemonade` uses Chat Completions and the native image, speech, audio, and transcription endpoints of a Lemonade server.
- `azure-speech` uses Azure Speech Fast Transcription for recorded audio only; it has no chat, live-streaming, or speech-generation transport.
- Every adapter implements the same internal provider contract.
- The direct ChatGPT Codex endpoint is not a public OpenAI Platform API and remains encapsulated in its adapter.

Technical provider responses are logged server-side and mapped to safe domain errors such as `provider.authenticationFailed`, `provider.rateLimited`, or `provider.unavailable`.

Azure Speech providers use an HTTPS resource or regional endpoint origin and an owner-scoped encrypted subscription key. Model synchronization verifies access through `GET /speechtotext/transcriptions/locales?api-version=2025-10-15` and exposes the fixed `azure-speech-fast-transcription` model with only `audio_transcription`. Enable that model and select it as the transcription default to use the existing voice-message, audio-tool, and video speech-analysis pipelines. Transcription uploads normalized WAV bytes inline to `POST /speechtotext/transcriptions:transcribe` using the same API version; no public audio URL, Azure storage account, or batch job is created. Without a language hint Azure uses automatic multilingual transcription. Explicit locales are checked against Azure's fast-transcription locale list; short language codes select the first advertised locale for that language. Use a full locale such as `de-DE` to select a particular regional variant. Multiple variants of the same language are never sent as language-identification candidates. MatoLoop retains its 64 MiB audio input and 1 MiB transcription-response limits and disables Azure profanity masking to preserve the transcript. Original audio is sent to Azure and cannot be text-pseudonymized, regardless of the provider's text pseudonymization setting. Azure resource, region, pricing-tier, and language availability remain service prerequisites; model synchronization does not verify every transcription quota or input limit.

Providers and models have a one-to-many relation in typed AI settings. OpenAI-compatible providers synchronize model IDs through `GET {base_url}/models`. ChatGPT Codex uses its OAuth credential with the private catalog at `GET https://chatgpt.com/backend-api/codex/models`; the adapter adds the native `openai-codex/gpt-image-2` media model with `image_generation` and `image_editing` and keeps the private Codex contracts encapsulated. Credentials never leave the backend. External OpenAI-compatible model IDs remain opaque strings; Codex slugs use the `openai-codex/` namespace. Newly discovered models start disabled except host-declared native media companions, while manually added models provide an explicit fallback.

Lemonade synchronizes installed models only, mapping documented labels/recipes to `chat`, `image_generation`, `speech_generation`, `audio_generation`, and `audio_transcription`. Image input, tools, and parallel tools are separate chat properties. Media resolution prefers an executable active model, then the configured purpose default; image generation/editing may first use the active provider's host-declared native companion. Editing reuses the image-generation default only when it supports editing. Media-only models are excluded from chat/helper selectors. Omni collections are not offered because their server-side loop would bypass MatoLoop permissions. Unknown recipes are not inferred from names. Unspecified size, steps, and CFG stay at server defaults, including Z-Image-Turbo. Media timeouts default to 300 seconds with controlled `provider.timeout` metadata.

Lemonade owns model residency and prompt-cache lifecycle. MatoLoop does not load, unload, or pin models because those operations reserve shared host RAM or VRAM and depend on the administrator's `max_loaded_models` policy. Administrators may preload a frequently used model through Lemonade and pin it against eviction; the number of simultaneously pinned LLMs must fit that policy. Residency avoids model cold starts, while llama.cpp prompt caching reuses common token prefixes only while the model remains loaded. MatoLoop requests standard streaming usage metadata from all OpenAI-compatible Chat Completions providers, including Lemonade, and persists any provider-reported cached input token count with the private assistant performance data. Missing cache metrics remain absent rather than being inferred as zero cache hits.

Every LLM provider has a required `public` or `private` trust level. A model can override it in either direction or inherit it with `null`. The instance's `GeneralSettings.modelTrustEnabled` defaults to true. When disabled, `load_effective_ai` normalizes runtime provider and model copies to private without modifying saved classifications or public permission branches. Permission, memory, profile and helper-model consumers use that same effective inventory. Authenticated UI state exposes the switch through the existing authentication responses; trust selectors are hidden and permission editors show the private branch as the common branch. Starting a run persists the model, effective trust, and independent pseudonymization snapshot; an existing run retains its snapshot when the switch changes. Selecting a model is the user's release decision for all content already authorized for that run, so changing to a public model does not add a second message, attachment, tool-result, file, or integration release approval. Ownership, project and root access, memory audiences, tool policies, grants, and approvals remain independent boundaries. Messages retain run trust as provenance; sessions have no aggregate trust level.

Local identifier and secret protection follows the provider's configured pseudonymization setting or the model's explicit override independently of effective trust. Explicitly selecting public trust in a provider or model form initially enables protection; selecting private trust or disabling model distinction leaves the setting unchanged. Private models can use protection and public models can disable it. The same independent setting applies to chat preparation, estimation and media text. Independent Presidio recognizers detect email addresses, IP addresses, phone numbers, IBANs, and credit-card numbers with checksums and specialized validators to limit false positives. `detect-secrets` adds structured API keys, tokens, secret assignments, and private keys. Free entities such as people, places, organizations, product names, and technical terms are not modified. Main-loop requests and their local estimates share one random 256-bit run key. HMAC-SHA256 over the exact entity type and original value produces an order-independent 128-bit marker identity. Each request has its own restoration map containing only detected values whose markers survive transport serialization; raw marker-looking input never grants restoration authority. Exact spelling is preserved, and conflicting marker mappings fail closed. New runs, child runs, and independent helper requests get fresh keys. Keys and maps remain in memory and are not persisted or logged. Text deltas and reasoning summaries replace unknown reserved markers with a controlled warning; unknown markers in tool arguments fail before execution. Restoration is single-pass so original text is not reinterpreted as another marker. The marker-preservation instruction is always included while protection is active, keeping the system prefix stable. Opaque continuation data is neither replayed nor persisted in this mode because it cannot be inspected locally. Images and binary data have no separate content pseudonymization. Detection is best effort and does not guarantee recognition of arbitrary confidential statements or source code. Disabling it deliberately sends released context unchanged to the provider.

Discovery does not replace local configuration. Known models keep their internal UUID, enabled state, and runtime values. Missing discovered models are marked `missing` and removed from effective selection, not deleted. Manual and discovered model configurations can be deleted; deletion clears matching model-default assignments and explicit session-wide selections, while a later synchronization recreates a still-advertised model with a new internal UUID. Model updates, enablement changes, synchronization, provider deletion, and Codex disconnection also remove default assignments that are no longer valid. Session resolution skips unavailable overrides and inherits the next available session-wide or default model without rewriting stored references. A failed synchronization leaves the last valid state unchanged. Effective model availability requires an active provider, an active model, current discovery availability, and an existing Codex connection where applicable.

Model configuration lives in global and personal `model-defaults` settings, separately from agent workflows. Session templates copy available agents, memory mode, and chat-model/reasoning overrides into new sessions. Per-agent session overrides win over session-wide overrides, personal defaults, and global defaults. Auxiliary requests use the configured default for their purpose and existing active-model fallbacks. Without a compaction model, compaction uses the session model and finally a deterministic summary. Titles use their configured model or the active session model; images may use the configured vision fallback. A failed model request leaves the locally derived title. See [Session templates and model defaults](session-templates.md) for persistence, scope, UI, and migration details.

## Integration Boundary

Integrations are configured instances of a capability and a host-registered adapter. Every instance has a stable ID, enabled state, optional credential reference, and typed provider-specific configuration in either instance `IntegrationSettings` or owner-scoped `UserIntegrationSettings`. The adapter registry is also the normal integration catalog; availability is stored by adapter type, so newly registered adapters appear without a second catalog list and default to fully available unless the adapter is explicitly hidden for a dedicated API. Instance integrations and their remote resources are intentionally shared with all users under instance tool policies. Personal instances and credentials are owner-only and enter the effective set only for fully available adapters. Configuration can activate only known adapters; external services provide no executable code or unchecked tool schemas.

Integration identity follows the product or service; transport is an adapter implementation detail. A supported product receives one normal catalog entry, product-specific API and UI, capability names, labels, and defaults even when it reuses a generic protocol client. Generic connectors remain separately managed fallbacks for unsupported services and do not host selectable product profiles. SonoBin therefore uses the `music`/`sonobin` adapter and `sonobin.call` while reusing the bounded MCP transport machinery.

HTTP Streamable MCP servers use the hidden-adapter exception and are configured through `/mcp`. Discovery stores a bounded, validated tool catalog; failed discovery preserves the existing catalog. Each discovered tool becomes an instance-bound contribution with a stable server-derived model name, its input schema, the shared `mcp.call` capability, and a stable per-tool resource key. Calls use the server's private/public instance and resource permissions, including a selected personal profile override where configured, the normal revision fence, and approval loop. Static tokens and OAuth credentials remain encrypted. MCP OAuth supports Authorization Code with S256 PKCE, server discovery, client registration, resource binding, and persistent refresh. Its process-local login attempts fit the single-worker harness. A public one-use state-checked callback completes temporary authentication; an authenticated request from the initiating login commits the connection and validated catalog. Ordinary calls cannot trigger browser authorization or OAuth replay. See [integrations.md](integrations.md#mcp-oauth). Prompts, resources, sampling, and server-provided executable code are not supported.

Every adapter has a static `backend` or `agent` execution location. Backend adapters cannot be assigned to a MatoLoop Agent. Each agent adapter is bound to one configured `ExecutionAgent` and is offered only when that agent matches the selected executor for the current model step and advertises the host-known operation. Multiple MatoLoop Agents and one local integration instance per adapter kind and agent are supported; integration calls never select an execution location themselves. See [integrations.md](integrations.md).

OpenCode is a personal-only backend adapter. Its HTTP client, remote sessions, repository reads, models, event stream, and permission replies remain adapter details; the project service exposes only the generic coding binding, analysis, plan, and execution contract.

An adapter can contribute statically known tools, controlled prompt fragments, or values for explicitly declared host configuration fields. Before each model request, available tools form an immutable effective tool set. The same binding snapshot exports the schema, validates returned calls, and executes them; calls not offered are rejected. Host tool options do not become model arguments. Security-relevant configuration is reloaded immediately before an external effect. See [integrations.md](integrations.md).

The integration policy core is domain-neutral. Adapters declare categorized actions and optionally one resource level. Each instance stores typed private/public permission branches and sparse profile-specific branches. Resolution merges the selected branch over the instance baseline and resolves resource entries over capability entries. Missing entries use the explicit action default or saved private/public base preset through `ToolAction.default_policy`, the same calculation as built-in tools. Adapters no longer declare separate trust defaults, and connection creation does not seed implicit rights as overrides. A sparse, trust-independent `resourceAvailability` map switches resources off without altering their policies; profile entries override the connection's availability. The runtime projects this map into effective tool permissions so discovery, aggregate operations, action execution and frozen delegation ceilings share the same denial. Global built-in action overrides do not cap integration permissions. Account discovery uses the integration baseline without resource overrides. Remote resources cannot add capabilities or override technical availability and ACLs. `disabled` denies, `ask` uses persistent approvals, and `auto` skips only that approval. Grants remain profile- and trust-bound. Deleting an integration deletes its permission maps with the instance. Delegation snapshots freeze resolved integration defaults and overrides. Backend restart terminates open runs and expires pending agent approvals, so historical delegation snapshots need no compatibility reader and are never resumed.

Profile-level integration selection is independent of these action policies and model trust. `integrationsEnabledByDefault` supplies the profile default; the connection's sparse `profile_permissions` map supplies explicit `available` overrides, followed by the base profile's connection override. Integration-provided profiles use their existing `integration_id` binding to include their own connection. Switching the default preserves connection overrides and does not mutate integration enablement or existing private/public resource permission maps. The runtime filters before resolving contributed tools, shared accounts/resources, host options, or project coding capabilities. This includes OpenCode, OpenSCAD, and option-only SearXNG. An excluded primary search instance makes `web_search` unavailable instead of silently selecting `no_key`; an excluded fallback is removed. Explicit `no_key` search remains independent of integration selection.

Integration schema loading uses the same profile and connection settings, independently of permission policy and model trust. All profiles support `integrationToolLoading` values `on_demand`, `native`, and `all`. Allgemein ships with `native`; other core profiles retain `on_demand`, and custom profiles inherit their base unless explicitly overridden. `native` immediately offers eligible registered product adapters, including native adapters that internally use MCP; generic MCP servers remain deferred. `all` offers every eligible integration schema immediately. A connection's optional `toolLoading` override resolves from the selected profile's connection entry, then its base profile's entry, then the connection default, and finally the effective profile default. Removing an override restores inheritance. Global and personal connections use the same owner-scoped settings APIs; no private connection IDs are written into shared profiles. Built-in tools, including integration-backed web-search options and project coding tools, remain direct tools. Mandatory host workflows may offer their required integration tool without a discovery round.

`search_tools` searches only the effective, availability- and delegation-filtered integration catalog by deterministic keywords over connection names, tool names, descriptions and schemas. It loads at most five matching definitions; search executes no external operation and grants no permission. Shared tool schemas expose only eagerly loaded or discovered connection IDs. Search results persist host-owned `toolDiscovery` metadata with the profile and concrete tool/connection IDs in ordinary session tool messages. Subsequent turns and runs rebuild the offered set from those records after the current compaction boundary, excluding omitted or expired discoveries and reapplying live availability and policies. Delegation freezes the eligible catalog rather than accidentally limiting children to already discovered tools; existing integration and tool ceilings remain binding.

The initial built-in/eager schema prefix and compact integration overview remain deterministic. Discovered tools append in persisted discovery order and remain offered across user messages; there is no per-message selector LLM, dispatcher, TTL, or opportunistic eviction. Prompt fragments follow the offered bindings and defaults. Compaction drops discoveries covered by its summary and rebuilds the offer before generation. If accumulated discoveries prevent context fitting, the host expires older discovery metadata once while preserving the latest search; canonical results remain unchanged and expired capabilities can be searched again. Pinned schemas are never silently dropped. Ordinary Chat Completions templates may put all tool schemas before conversation history, so adding tools can invalidate the server's prefix cache; stable offers reduce repeated invalidation but do not guarantee cache hits.

Selection, binding revisions, and resource policy remain revocable before effects and after approval, including nested directory approvals and aggregate resource reads. An approval never revives an excluded integration or revoked resource. Delegation freezes concrete enabled integration UUIDs and the intersection of offered and spawn-time permission ceilings, then applies stricter live policy. Newly configured or newly enabled integrations cannot widen a running child. Resource filtering reuses the existing sparse maps and typed matchers rather than introducing another permission store. See [harness.md](harness.md#tool-contract).

## Browser Boundary

Each chat/computer binding owns a disposable headless Chromium worker. Chats do not share tabs, cookies or website storage; no profile is restored after runtime close. Native Linux and container agents use the same optional CDP page stream and typed input through the existing private relay. Multiple authenticated views of one chat subscribe without takeover. Browser tools lazily start the runtime independently of app presence; there is no model attachment or handoff tool. `browser.use` covers ordinary actions and website JavaScript, including authenticated content. It defaults to AUTO for Build-based profiles except in `ask_all`, and ASK otherwise; explicit overrides remain authoritative. Authorization stays bound to the runtime and reviewed context. Each model action fences manual input, including approval reinspection, and restores it afterward without replacing the streams. The worker releases held input at input-source and epoch changes and rejects stale input. Viewer loss does not end the runtime; explicit close, access revocation, or Agent disconnect does. Existing runtime limits remain in force.

Browser runtime architecture and operations are documented in [browser.md](browser.md). Small `browser_*` tools retain the Python Playwright worker and execute transport. Browser use and Python execution (`browser.code`) use the existing `write` category. Python additionally requires its own reusable execution resource and defaults to ASK in every profile and preset; ordinary browser grants cannot authorize it. Website JavaScript needs only browser use. Other defaults follow the saved preset and scoped overrides. Grants bind the context, not transient viewers; queued calls bind the browser runtime. Actual approval waits retain page guards and post-wait capability checks; AUTO calls do not take approval snapshots. Unrestricted Python deliberately retains worker-account OS authority, not a per-chat sandbox, and requires external isolation or disabled code permission where that scope is unacceptable. The renderer sandbox, owner-bound checks and ephemeral screenshot lifecycle remain separate guarantees. Existing persistent profiles are not loaded or deleted automatically.

## Channel Boundary

Channels are owner-bound message ingress and egress endpoints, not integration instances. They do not contribute agent tools, prompts, policies, or resources. Administrators control global channel enablement and a separate allowlist of host-installed channel providers. Global enablement defaults to false, also for existing documents without the field; Telegram remains allowed by default. Effective channel availability requires both settings and applies to administrators too. Personal endpoint records, encrypted credentials, and provider allowances remain stored while channels are disabled. Administrators manage only global settings and provider allowances and cannot inspect another user's endpoints or credentials. **Administration > Kanäle** opens on **Einstellungen** for the global switch; **Verwaltung** lists provider allowances. Personal settings directly manage owned connections.

Every external event enters the normal persistent session, message, and agent-run flow through a deduplicated inbox. Messages retain immutable channel provenance, while sessions derive only a default reply channel and remain channel-neutral. External delivery uses a persistent outbox. Automation definitions may retain an owner-bound endpoint selection, but each run snapshots its effective destination; global or provider disablement at enqueue time falls back to the canonical MatoLoop app result. Pending external deliveries are terminated on either disablement and are never replayed after re-enabling. Both setting writes acquire the affected provider locks before loading settings, sharing the existing receive and delivery authorization fence.

Channel providers may project the existing provider-neutral run-event stream as ephemeral typing, compact activity, or response previews. These projections are best-effort, process-local acceleration and never replace the canonical persisted assistant message or persistent outbox delivery. Runtime events carry the same host-controlled German activity labels used by the frontend and channel projections. Tool calls also carry host-generated `toolDisplay` metadata with a family-level Material icon and channel emoji, the resolved German definition label, and an optional bounded summary derived only from allowlisted already-sanitized arguments. Provider metadata cannot supply it; legacy REST messages derive the same conservative presentation without a database rewrite. Telegram uses native private-chat drafts for public reasoning summaries, tool activity, status, and streamed response text. Tool results, raw arguments, process output, and metadata remain outside the draft. Telegram sends the final response only through the normal outbox.

Outbox text retains its canonical `plain` or `markdown` content format. A small channel-renderer registry converts that source into provider-specific, independently valid text parts only at preview or delivery time; limits, markup syntax, safe degradation, and splitting remain provider-owned. Missing renderers and legacy payloads without a content format use plain text. Telegram renders the supported Markdown subset as escaped Telegram HTML and degrades unsupported or oversized structures without changing canonical message persistence.

Run-bound endpoint approvals add a typed provider-neutral outbox envelope. Adapters render host-controlled summaries and decisions as native controls or exact UUID-token commands. Decisions require the paired owner/destination and locked revalidation of endpoint, input, session, run, delivered prompt, status, and available action. The shared service handles identical retries idempotently. Shell approvals use the ordinary isolated-process path. Skill build/edit approvals still require exact draft-revision review in MatoLoop; channels can only deny them.

Voice messages share one provider-neutral attachment/runtime pipeline across web and channels. Channel adapters classify recordings as `voiceMessage`; web requests use validated `voiceAttachmentIndices`. The original persists before automatic transcription through the configured transcription model default. Recognized text supplements the message within its length limit; failure preserves the recording and never inserts error text as user speech. Terminal transcription status prevents duplicate append on retries. `message.updated` accelerates canonical delivery. Marked recordings need no separate tool approval; model-initiated transcription retains normal permission checks. Ordinary audio uploads are not automatically transcribed.

Voice recordings remain playable and accessible through the existing attachment tools regardless of ingress provider. All audio entry paths, including ordinary uploads and generated or downloaded artifacts, persist only the original audio, without a new WAV companion or companion metadata. Ingestion still validates audio through the bounded processing pipeline. Transcription and browser playback fallback convert the verified original to transient PCM WAV on demand through that same pipeline, off the event loop; downloads retain the original format. Existing audio companion metadata and managed files are ignored for audio reads and model context, but left intact because other attachments, file actions, or revision references may still use them. No cleanup migration is required for compatibility; reclaiming legacy storage requires a separate reference-safe cleanup mechanism, not the transaction rollback discard helper. Text and document companions remain persistent. Web recordings are previewable before sending and use the existing attachment limits and persistent message outbox; unsent recordings are not server-side session storage. Telegram polling, media download, progress, callback acknowledgement, and outbox delivery release database transactions before Telegram API I/O.

Agent questions use a provider-neutral, versioned outbox envelope. Telegram projects it as a
sequential inline keyboard and accepts custom or free-text values only as direct replies to the
delivered prompt. Navigation changes only the envelope state; submit and reject use the same
question decision service as the HTTP API. Each interaction locks and revalidates the endpoint,
owner, originating input, session, active run, delivered outbox prompt, and pending request.

`Allgemein`, `Plan`, `Build`, and `Sysadmin` have stable IDs and protected names and workflow definitions. Both global and personal custom profiles inherit one core base and allow separately managed tool rights and settings. Removing action rules preserves tool availability and shell prefixes. Built-ins and custom profiles may be disabled. The configured instance default must always be active. Session templates choose a start agent and constrain the session's available agents without overriding instance availability. Disabled profiles remain stored and historical runs retain their provenance. Personal settings show only the owner's explicit profiles.

Static host-controlled prompts, repair instructions, prompt fragments, tool descriptions, schema descriptions, and model-facing markers use simple English. Contracts remain concise, explicit, provider-neutral, and free of redundant or contradictory instructions so medium-sized local instruction models and cloud models use the same text. Dynamic user, identity, memory, source, and tool data may use any language; exact German UI labels can appear as quoted product identifiers.

Protected-input results instruct the model to continue dependent work in the same run: a final answer ends run-local reference availability. Historical input markers do not restore credentials. Session-reading tools expose only temporary references still present in the current run or owner-bound session store and identify unavailable fields by name. Validation errors identify input paths rather than synthetic validation-union branches. A request to discuss, plan, review, or pause suspends earlier execution requests within the selected profile's constraints.

Process output uses one shared filter for normal and elevated shell tool results. It removes exact injected values and recognizable authentication-header lines, including cookie and CSRF headers. Live process events hold incomplete lines until they can be filtered; injected secrets remain buffered until completion. Historical shell output is filtered again before model retrieval and terminal replay. The shared prompt requests one compact search query for one information need, retaining essential relationships and exact identifiers rather than combining questions or synonym lists. Tool use is emitted in the same response, not merely announced. Current queries normally omit a year; a required freshness year comes from frozen run time. Explicit/historical identifiers remain unchanged. `web_search` describes `query` and optional `search_type`; MatoLoop never rewrites queries.

Plan and Build are shipped task-general profiles, not repository-only roles. Plan analyzes relevant evidence and returns an appropriately detailed plan in the conversation without implementing it. Requests to implement do not change the selected profile: Plan may continue read-only research and clarification, but explains that implementation requires Build. The model-facing contract prohibits mutations by their intended effects, including through commands classified as `shell.read`; this guides model behavior but does not replace the documented shell-policy boundary. Build implements a previously discussed plan only when the user requests implementation; newer user instructions refine the task within the selected profile, and switching profiles alone is not authorization. Sysadmin is a system-administration workflow that inspects actual state before changes, relies on the host approval flow for mutations, verifies approved changes, and avoids duplicate confirmation questions. The persisted conversation and its context summaries carry plans between turns, including current decisions and remaining work while distinguishing planned work from verified results. No separate plan artifact is created. Custom profiles may inherit and override these instructions. Applicable `AGENTS.md` instructions remain below host rules and the selected profile's workflow constraints. Delegated prompts supply self-contained goals and evidence without injecting the parent's full task workflow.

The profile field `repositoryInstructionsEnabled` controls automatic `AGENTS.md` loading. Plan and Build enable it; Allgemein and Sysadmin disable it. Custom profiles inherit it and may override it. Before each model request, the backend checks the selected computer directory through the owner-bound MatoLoop Agent. It discovers the nearest Git root, including a worktree's `.git` file, only through already authorized ancestors; without a verified Git boundary it stays at the current directory. Project rules and their directory scope enter the current model context directly, without model-generated search calls. Successful text-file reads, file actions, and deferred change targets retain their computer, current-directory, and absolute-path binding in existing tool-result metadata. Subsequent model requests also check `AGENTS.md` along those paths within that same current directory. Before native computer-file changes and commands with inspected file targets, the runtime checks relevant rules through the same authorized loader. Patches and copies/moves supply all resolved source and destination paths before any file effect; existing directory targets include their own rules. Newly discovered or changed rules defer the call and the remaining batch until the next model request includes the updated instruction context. Deferral is not a successful mutation or a failed-call signature, and the model must reconsider and reissue the action. Absent rules add no model round. Discovery and access statuses remain host-side; the model receives only loaded rule contents with their paths and directory scopes in stable order. Missing files and Git-boundary status changes do not change this instruction block, and no block is emitted when no rules are loaded. Context-budget omissions retain a controlled notice. Rules are deduplicated by path and rebuilt from current files, so compaction and backend restarts do not lose the discovery information or preserve stale instruction contents. Computer or directory changes exclude earlier bindings. Shell discovery covers only paths identified by the existing inspection; unknown program effects retain the documented shell-policy tradeoff.

Automatic loading uses the normal read authorization in check-only mode, including live policies, delegation ceilings, grants, and computer ACLs. Missing, approval-required, denied, and controlled failure statuses remain in the host's checked entries, separate from the model-facing rules. Symlinks and non-regular instruction files are not loaded. Loading is bounded to 64 directories, 32 KiB per file, and 64 KiB of rendered instruction contents; incomplete files are rejected rather than partially applied. The observed instruction baseline is separate from its budget-trimmed presentation: unchanged omitted rules do not repeatedly defer calls, but changed rules still do. Successful inspected shell targets retain their scoped discovery binding even when no rules exist yet, so the following model request can load rules created by that command. Instructions apply only below their directory, with more specific rules taking precedence, and cannot override host rules, profile constraints, or the latest user request. The shared prompt prefers file tools for supported reads, listings, searches and changes, reserving shell for builds, tests, Git, processes, unsupported operations and explicit shell requests; tool changes cannot bypass a denied action.

Temporary tool filtering for mandatory workflows or an exhausted tool-call budget does not change that switch. Automatic loading does not cause an additional model request or force extra conversation compaction.

## MatoLoop Agent Boundary

Both filesystem adapters use the Agent's `file_text` module for UTF-8 read formatting, text edits, patch parsing, and hunk application. Platform adapters retain path validation and actual file mutations. Windows writes, imports, and cache publication share one handle-bound staged-file publisher with failure cleanup.

Native `apply_patch` supports add, delete, update, and combined move/update operations in the Codex-style `*** Begin Patch` envelope. Update hunks use exact, unique context, optional `@@` on the first hunk, ordered `@@ exact-line` anchors, and an optional final `*** End of File` anchor. Pure-addition hunks append, including to empty files. Existing line endings and final-newline state are preserved for ordinary edits; pure additions append complete lines. This is a supported format subset, not compatibility with Codex's fuzzy matching, shell wrappers, or environment selection. Existing-file operations require the read SHA-256; add/move destinations must be absent and parents must exist. Combined moves reuse revision-checked writes before moving and therefore also require source write permission. Source and destination repository rules are checked before execution. Linux preflights all operations; Windows checks each operation before applying it, including the destination before a combined move's source write. Neither adapter promises whole-patch rollback: `file.patchIncomplete` identifies partial or uncertain effects and requires rereading affected paths.

The backend remains authoritative for provider communication, the LLM and tool loop, static schemas, argument validation, model policies, approvals, grants, sessions, memory, credentials, backend integrations, session storage, and canonical tool results. A standalone MatoLoop Agent belongs to exactly one user and connects outbound over the authenticated strict protocol v1. Its required hello fields are `agentId`, `agentVersion`, `computerName`, `platform`, `homeDirectory`, and `operations`. `homeDirectory` is a normalized absolute POSIX path on Linux or a canonical absolute forward-slash drive path on `win32`; path format must match the reported platform. The agent advertises no roots, root IDs, or root revisions, and there is no compatibility protocol. It receives bounded authorized operations, not the system prompt, chat history, provider credentials, or permission authority.

Native Agent installation owns a private `uv`, Python, environment, source, and cache below the user data directory; it does not modify shell profiles. On Linux a Python lifecycle manager and shell bootstrap install one systemd system service that starts at boot but runs as the installing user. On Windows a PowerShell bootstrap installs under `%LOCALAPPDATA%\matoloop-agent` and registers a startup Scheduled Task under the installing user's account; Windows Task Scheduler stores the account credentials, while Agent pairing credentials use owner-bound DPAPI. The default Windows workspace is `%USERPROFILE%\mato-loop-agent\workspace`, outside the managed installation. Uninstall preserves credentials by default, while an explicit purge removes the complete managed installation. Neither operation removes the workspace.

The portable connection, pairing, protocol, and dispatch core depends on one agent-local platform adapter. That adapter composes filesystem, process, terminal, search, browser, OpenSCAD, cache, credential storage, system inspection, and shutdown behavior and advertises only operations supplied by that composition. Linux and native Windows adapters share the connection core. The protocol accepts Linux normalized absolute POSIX paths and Windows canonical uppercase drive-letter paths using forward slashes. Both the backend permission scope comparison and agent validation use the same path components; drive paths are compared case-insensitively. UNC paths and Windows device paths are not supported. Linux-only browser, OpenSCAD, and POSIX terminal capabilities remain absent on Windows.

The hello also carries an optional, strictly validated `systemInfo` snapshot: operating system, distribution/version, kernel, CPU model, architecture, logical CPU count, and total RAM in bytes. Agents refresh it on every connection; omitted or null measurements are unknown. The backend retains it only on the live connection, replacing it on reconnect and removing it on disconnect or revocation. The shared model context includes these descriptive data only for the run-selected, owner-bound, non-revoked connected agent, including delegated runs, never from another computer or the backend. This static connection metadata requires no tool approval and grants no permissions; live `get_system_info` queries retain their existing permission checks. Reported system totals are not container resource limits. There is no persistent hardware inventory or periodic telemetry. Older agents may omit the snapshot; deploy the backend update before newer agents because older strict backends reject the new hello field.

MatoLoop Agents pair through a bounded one-time registration token. The agent generates its durable access key locally and submits only its SHA-256 hash; after pairing, only that durable key can authenticate WebSocket and transfer requests. Unpairing commits the credential removal before closing the live connection and revoking unclaimed transfer tickets.

The backend retains the stable implementation identifiers `ExecutionAgent`, table `execution_agents`, API `/execution-agents`, and foreign key `execution_agent_id`. They name the persisted domain aggregate and are not standalone product or deployment names.

Session creation provisions owner-bound internal storage. A new session has no workspace unless an explicit selection or project default supplies an owned Agent and directory. The Agent home is a selection suggestion, not an advertised root. Run creation snapshots the selected Agent, directory, and operations; `change_directory` updates run and session together. Retries use the session's current directory. Disconnects never fail over or replay dispatched operations. Offline computers do not block ordinary chat/backend tools, but supply no live computer operations.

The model can list only the owner's non-revoked MatoLoop Agents (`execution_agent.list`, category `read`). `select_execution_agent` requires a separate tool round and follows its configured `execution_agent.select` policy, category `write`. Both use the saved trust preset unless overridden. `auto` switches without a prompt; `ask` supports matching run and session grants scoped to the target computer; `disabled` denies. Delegated and automation runs cannot switch. Before execution the backend validates the new connection and starting directory, updates the session and active run together, and builds the next model request from the new agent's operations and integration bindings. Pending calls in the same tool round cannot cross that boundary. The current prompt identifies the selected agent by alias and ID; `session_read` attributes historical messages to their run and records an in-run switch without treating today's session preference as historical fact. The available-agent list is a tool result, not a changing system-prompt inventory. The session prompt-cache key remains stable; unchanged bindings produce unchanged computer identity text.

Recorded tool calls carry their historical selected-computer ID and alias on the projected tool result, never in assistant text or a growing system-prompt inventory. Shared provider preparation adds the reserved top-level `hostSelectedComputer` JSON field from host metadata after result shortening and browser projection, before token estimation and privacy protection; non-object results use a `result` wrapper. Tool-supplied values cannot set that field. Ordinary action policies still apply; external-directory policy additionally governs file tools. The policy is inherited, overridden and bounded during delegation through the existing permission resolver; it adds no model tool or schema.

New integration and coding grants reuse the same category on the same resource across capabilities. Historical capability-bound grants retain their originating capability family.

File roots retain one model-facing contract; internal persistence and permission code may translate these names to `session` and `workspace`:

```text

```

The backend mediates cross-root and user-facing file transfers with short-lived, owner-bound HTTP tickets. Both sides enforce size limits and validate byte count and SHA-256 before accepting content. The MatoLoop Agent's sparse session cache contains only files used by authorized operations, is size-bounded with oldest-file eviction, and validates size and SHA-256 on every hit. Local filesystem deletions do not read or transfer file contents and are independent of transfer byte limits. Linux deletion preflight enforces the operation entry limit and validates path types before removing any entries.

Every standalone filesystem operation is named `filesystem.*` and uses the selected agent's normalized absolute path format. The Agent operates with its operating-system user's rights. On Linux it traverses from an open `/` descriptor with `O_NOFOLLOW` on each component; on Windows it opens directory components with no-reparse, handle-relative calls and performs file mutations relative to those handles. Both prevent path links from redirecting file RPCs without creating an operating-system sandbox. The Docker image currently runs as root and has only `/data` and `/workspace` mounted, so mounted scope and deployment policy are the effective filesystem boundary. Agent history is reconstructed from the latest 50 canonical `shell_run` results for that exact owner, session, and computer. Every Linux model `shell_run` command is parsed with the Bash tree-sitter grammar before execution and model-policy authorization. Inspection reports `requiredCategories`: all recognized read/write/delete actions in the command list, including supported nested commands. Known removal and clearing operations such as `rm`, `unlink`, `shred`, `truncate`, `find -delete`, Git clean and explicit removal/prune subcommands require delete; Git reset `--hard` requires write and delete. Ordinary output overwriting remains write; explicit empty redirects such as `: > file` also require delete. Unknown commands retain the optimistic read classification. Curl `-o`/`--output` targets retain the verified host `/dev/null` discard exemption; `-` means stdout. Legacy `classification` and `readOnly` project all recognized mutations to write/false and do not imply absence of side effects. Syntax errors return `process.invalidSyntax`. POSIX `<>` remains a non-exempt write, including `<> /dev/null`. The categories participate in the inspection revision and are aggregated before command serialization limits.

`docker exec`, `docker container exec`, and `docker compose exec` classify inner argv with the same category rules after parsing known options and the container/service operand. Supported static `sh`/`bash`/`dash` `-c` payloads are parsed as shell source on the host and in containers; ordinary arguments remain data. Nesting is bounded to eight levels. Ambiguous exec options, privileged execution and unsupported nested forms retain the conservative write fallback; unknown program effects retain optimistic read classification. Container paths cannot be resolved on the host, so inspection remains incomplete and requires the external computer zone. Host arguments, substitutions and redirects retain hard path checks; container redirects cannot use the host null-device exemption. Exec units have no reusable prefix. Computer/category grants can satisfy normal shell consent but do not contain container effects. Explicit-environment and administrator commands retain exact consent. Revision checks bind the full original command.

Static `xargs` command targets use the same mutation rules, with argument-taking options distinguished from command argv and nesting bounded to eight levels. Its stdin-derived arguments keep inspection incomplete and its commands never propose reusable prefixes. Recognized `-a`/`--arg-file` operands are read targets bound into the revision, with ordinary no-follow checks; they are not accidentally treated as writes merely because the target command mutates files. Unknown host target effects retain the ordinary read-classification tradeoff; container targets retain the existing conservative shell-wrapper rules. This does not add effect analysis for arbitrary interpreter programs or resolve stdin-derived paths.

Known mutations include `shred` and curl's `--json` option. Git clean is read-classified only for a recognized non-interactive dry-run invocation; exclude-pattern values and post-`--` operands do not create a dry-run exemption. Unsupported option forms or a host `POSIXLY_CORRECT` setting keep the conservative write class rather than trust a partial GNU option parse.

Command-text, directory-enumeration, and target-count technical bounds return `process.inspectionLimitExceeded` rather than authorize a truncated inspection. Serialized command-node and token caps instead mark extraction incomplete and remove reusable prefixes; inspection still visits later commands for known writes and hard path checks. A missing literal target retains its normalized absolute path and marks analysis incomplete when existence was required. Missing targets are distinct from hard no-follow or access failures, which still reject execution. Shell target metadata inspection uses Linux `O_PATH` directory descriptors with no-follow checks, requiring search permission on ancestors rather than permission to list them. It does not read target contents or elevate the agent's privileges: an inaccessible ancestor still rejects inspection, including for a command containing `sudo`. The inspection result, target metadata, semantic token prefixes, and classification share one revision and are rechecked immediately before execution; changed inspection returns `process.inspectionChanged`.

The shell-only `discard` and `toolchain_metadata` target kinds remain inspection evidence, not permission grants. Static `/dev/null` output is non-mutating only after no-follow verification of the real character device `1:3`; input use, dynamic targets and `<>` are not exempt. Toolchain metadata covers bounded installed `ls` discovery in the fixed execution PATH with verified standard usr-merge aliases, restricted options and listing fingerprints. Ordinary content use takes precedence over metadata use. All targets still participate in hard computer-zone and revision checks. These helpers do not grant file access or provide a sandbox.

Normal shell consent defaults to an exact `shell_action` command/context scope; the shared approval-area selector can explicitly widen it to `shell_computer`, bound to the selected computer UUID. The category defines read/write/delete coverage, with write including ordinary read. Every category's concrete capability is checked before execution; mixed requests precheck denials and recheck all categories after approval. Shell does not use `working_directory.external`, which remains a profile-controlled file-access rule. File grants cannot authorize shell, and shell grants cannot authorize file tools. Read/write token-prefix allowlists remain optional policy inputs but cannot approve delete or override hard computer boundaries, sensitive-data policy, disabled capabilities or revisions. Explicit-environment and administrator commands retain command/context binding without the computer-wide option. Sensitive paths and possible secret output retain their existing additional, best-effort disclosure check and action-bound consent.

The optimistic `shell.read` classification is an accepted, intentional workflow tradeoff. It is a permission class, not a guarantee of side-effect-free execution. Unknown programs, tests, and builds may be classified as read operations to keep coding workflows usable. Complete effect analysis and an OS sandbox are not prerequisites for the native coding agent. Reviews should report concrete regressions in classification, approvals, revision checks, or enforced boundaries, rather than repeatedly treating this documented residual risk as an unresolved defect. Revisit this decision when new evidence or a changed deployment threat model warrants it; deployments may independently choose stronger isolation. Validated canonical executable paths preserve shebang script paths and `$0`. This is path-based execution: validation is not atomic with exec and does not pin executable identity through a descriptor. The working-directory protection must not be described as secure descriptor-based execution or an OS sandbox.

## Working Directories and Approvals

Standalone managed roots are `/data/sessions/<session-id>/{files,revisions}`; project-session roots are `/data/projects/<project-id>/sessions/<session-id>/{files,revisions}`. Attachments are managed files in these roots, with no separate attachment storage. Moving a session moves its complete managed tree and preserves root identity, file IDs, revisions, and references. A session cannot move or be deleted while another session references its files. Legacy project-level files migrate into an owner-bound chat session named `Übernommene Projektdateien`; its session ID equals the project ID so existing file-root references remain valid. The model-facing `computer` root is the current absolute directory on the selected owner-bound MatoLoop Agent.

Tools have one of three execution types: `backend`, `computer`, or `shared`. Backend Tools execute inside MatoLoop, Computer Tools execute through the selected MatoLoop Agent, and Shared Tools keep one model-facing contract while selecting the backend session store or computer directory from their arguments. `tool_type` is host metadata and is never a model argument.

The Shared Tools `read`, `glob`, `grep`, `provide_file`, `write_file`, `edit_file`, `create_directory`, `delete_path`, `copy_path`, and `move_path` are filtered by storage availability and effective policies, not by an agent mode. Backend managed-file mutations use `session.files.write`. MatoLoop Agent access first applies the home or external filesystem policy for the normalized absolute target; operation-specific write and delete capabilities remain separate. No approval can supply a missing current directory or unavailable MatoLoop Agent operation.

`read` reads a directory, UTF-8 text, or a supported image. Text uses one-based `offset`, bounded `limit`, and numbered file lines. Large text files are read in chunks, individual long lines are bounded, and tool output indicates continuation. Registered session images keep their existing file reference; other PNG/JPEG/WebP/GIF paths are read only after the ordinary path approval, decoded and validated within the image size limit, then sent as ephemeral model input without persisting a second attachment. `glob` searches file paths and `grep` searches file contents with fixed result, output, and time limits. Both searches use ripgrep without shell execution, configuration files, or symlink traversal; no matches is a successful empty result. Grep accepts directories and explicit regular files in both roots. Directory discovery retains the existing hidden/ignore rules; `include` applies only to directory discovery. Explicit files bypass discovery filters but not permission checks or `.git` exclusions. They are opened with existing no-follow regular-file validation and passed as stdin to ripgrep, never reopened by filename or widened to a parent-directory search. Results retain the requested file path. Detected binary files return no matches; detection is bounded by ripgrep's scan and the result/time limits, not a whole-file certification. Copy and move validate source and destination roots before effects; the destination path always names the exact new entry and never overwrites.

Configurable permissions use persistent approval requests. The agent run waits for `allow_once`, `allow_session`, or `deny`; the request remains an inline chat card until decided. The UI defaults to `allow_once`, labelled **Für diesen Lauf erlauben**. It persists the displayed resource scopes as grants bound to the executing run, profile and trust level. Later matching tool calls in that run reuse them; another run, including a separate child run, does not. `allow_session`, labelled **Für Session erlauben**, uses the same scope matching across runs until revocation or session deletion. Browser reload does not end either lifetime. The host persists selected resources atomically as `category.read`, `category.read_sensitive`, `category.write` or `category.delete` grants, derived from the declared ToolAction category. Approval scope payloads use `category`. This uses the existing table and resolver without a schema change. Sensitive or otherwise non-reusable actions instead use run-only consent bound to the exact tool arguments, permission target and reviewed content revision; edited actions are bound to their revalidated final values. Hard denials and execution-time revision checks still apply. Existing approval records are not retroactively converted into grants. Run grants are excluded from active permission listings after the run ends; session grants remain independently revocable.

Approval cards reuse existing tool arguments and `displayItems` to show action context without a technical-metadata panel. Resource-grant descriptions appear for both run and session consent and do not replace action previews. Memory proposals retain complete content; updates and deletion add the owned revision-checked target content.

Permissions use existing resource-specific matchers beneath the shared action categories. The central category matcher lets a reusable `write` grant satisfy ordinary `read` on the same resource and lifetime; delete and sensitive read remain independent. A write grant stays one row for listing and revocation. File grants explicitly store `recursive: true`, covering the selected path and descendants. Managed-file scopes retain root type and owner-bound identity and always use POSIX containment; computer file scopes retain the computer UUID and normalized absolute path. Normal shell approvals default to the existing exact command/context `shell_action` scope. Shared host-generated approval options can offer a file's direct parent or the existing computer-wide `shell_computer` scope. Integration scopes retain the integration UUID, binding-revision hash and stable account/resource key; grants can cover other capabilities within the allowed category coverage on that resource. The concrete capability's effective policy is checked on every call. URL access compares exact canonical URL hashes, session access compares UUIDs, and discovery uses a separate collection scope. Mixed shell calls authorize writing before ordinary reading to reuse its included read right, while retaining all pre- and post-approval policy checks. Separate shell-delete grants cover recognized destructive actions, not complete effects of arbitrary programs. Data migration `ab5df5b19220` resets all grants and expires pending agent-action approvals once; the matcher drops historical resource/access and capability-bound grant semantics. Navigation and exact run-action consent retain their current formats. Settings and memory proposals remain unchanged.

## Context and Compaction

Ten discovery tools opt into session-local tool snapshots through an explicit host-owned `ToolSnapshotPolicy`: the Arcane, Mealie, mail, BookStack, calendar, and task account lists, plus calendar lists, task lists, mail folders, and Arcane environments. Successful authorized calls persist only their validated arguments, observation time, and a hash of tool bindings, pin policy, and effective access settings alongside the canonical tool message. Projection reuses selected fields from that message; it does not execute tools, create memories, or copy results into a separate store. Account lists remain eligible while their bindings and access settings match; external directories expire after 30 minutes. Arcane environment snapshots contain only IDs and names, never live status. New successful results replace older results for the same tool and arguments, including when the new result is too large to pin. Failed refreshes do not advance observation time.

Snapshot context carries the source message ID, arguments, `observedAt`, and `expiresAt`, and is explicitly untrusted data. It is rebuilt from the session's canonical messages after compaction and omitted when the same result is already present in the current tool turn. Only currently offered opt-in tools with matching bindings and access settings qualify; snapshots grant no new permissions. Each complete snapshot is limited to 2,000 serialized characters, and the complete snapshot block to 8,000 characters and 5% of the usable input budget using the model's character estimate. Oversized entries are skipped, never silently truncated. The normal provider-aware context estimate counts the block, which can be dropped if required context would otherwise exceed the input budget. Explicit tool calls always execute normally and can refresh a snapshot early.

Agent identity uses instance-scoped `AgentIdentitySettings` and owner-scoped `UserAgentIdentitySettings`, separate from memory and profile permissions. Each scope has a reusable persona catalog and profile-to-persona assignments; global settings select one default. Personal assignments may reference global or owned personas for accessible global or personal agents. Administrative assignments target global profiles only. Resolution uses personal assignment, administrative assignment, then global default, without a personal default or base-profile persona inheritance. One gate controls personal personas, assignments, and the single account-wide display-name override. The identity tool never mutates global personas. Migration `7494cba04f61` directly moves existing profile persona references to scoped identity assignments while preserving catalogs. See [agent-identity.md](agent-identity.md).

The maintained user profile is a separate user-scoped `UserProfileSettings` document. The `update_user_profile` tool follows its own `settings.user_profile.update` policy in the `write` category and accepts only the six maintained fields plus a private, public, current-model, or both-model scope. The prompt contract permits calls only for explicit persistent changes in the latest user message and treats quoted, retrieved, remembered, web, and tool data as non-authoritative. The handler resolves current-model scope from the selected model trust level, acquires the user settings lock, and applies only supplied fields. Explicit null clears a field in the selected scope. Profile and persona settings deliberately have no optimistic revision contract; serialized writes use last-completed-write semantics and affect model context from the next run.

Complete message history remains canonical in the database. Before each model request, the context manager creates a transient projection from the stable host prompt with persona, user profile, and project context; an optional summary and older original history; a host-marked checklist checkpoint followed by current-turn memory metadata and untrusted memory references; and the latest user request followed by current tool rounds. The checklist checkpoint reflects canonical state before the latest user request, or through a later compaction boundary. Subsequent successful `todo_write` results replace it chronologically instead of rewriting the earlier prompt prefix. Empty checkpoints are included when prior checklist history exists; failed updates cannot replace successful state. Current checklist results remain exact and counted in the budget rather than silently shortened. The stable system prompt defines the assistant markers' trust boundary. Automatic memory snippets can be dropped to fit; pins remain outside their budget, and projection fails safely if required context and all visible pins cannot fit. Full unpinned memory detail requires `memory_retrieve`, and full prior-session detail requires `session_read`. Selecting the model is the release decision for already authorized messages, tool results, and attachments, so public model trust alone does not redact them. Ownership and session permissions still govern access, and durable memories retain their independent `private_only`, `public_only`, or `both` audiences. Local pseudonymization remains separate. Tool calls and results remain paired, interrupted calls receive terminal errors, and tools are never re-executed during projection. Older large tool results become retrievable references, while other current results share the available context budget and shortened search or webfetch envelopes remain valid. Canonical content and provenance remain unchanged.

Context window, Auto or manual output ceiling, characters-per-token estimate, and tool, parallel, streaming, and image capabilities are configurable per model. Context configuration accepts at least two tokens, but runtime safety and generation reserves still have to fit. Discovered models store the latest provider context value separately from the effective window. New discovered models follow that context value automatically; a manual context override stops automatic context updates and can later return to the provider value. If no provider context value exists, the fallback is 128,000 tokens. Existing persisted context overrides remain unchanged.

Adapters normalize context metadata for the selected endpoint, not a model-name catalog. Codex exports both its default `context_window` and allowed `max_context_window`; automatic discovery prefers the allowed maximum and falls back to the default when absent. Lemonade's configured server context still takes precedence over its model maximum. These are per-model values, not a global context ceiling. Existing provider-following models receive updated values on the next explicit provider synchronization; no live settings are rewritten by deploying the adapter change.

`maxOutputTokens: null` means Auto and is the default for new models; a strict positive integer is a manual ceiling. It is not clamped to a quarter of context capacity or rewritten on context changes. `discoveredMaxOutputTokens` is read-only and nullable: only OpenRouter's documented `top_provider.max_completion_tokens` currently supplies an authoritative output cap. Unknown output caps remain unknown, rather than being inferred from generation defaults, model names, or context size. Synchronization refreshes this cap for matching manual models as well as discovered models without replacing their manual output ceilings.

Data-only migration `49e718887770` switches all existing models in every instance and user `ai` settings document to Auto once, including explicitly configured manual output limits and legacy nested fields. It has no relational schema change and preserves context, reasoning, temperature, and other configuration. This is a destructive reset of old output ceilings without a backup. Downgrade removes output settings, including subsequently entered manual ceilings, to use older compatibility defaults; it cannot restore historical values. Normal use after upgrade preserves newly entered manual ceilings.

Large Webfetch results are projected before token estimation with a 15,000-character content window, approximately 75% head and 25% tail, plus an omission marker and an exact `session_tool_result_read` reference. This also covers results retained from the preceding turn; persisted content, source metadata, and attachments remain intact. Further pruning keeps the original reference. Other current tool output has no fixed token cap. After any required compaction, the context manager subtracts system prompt, tool schemas, summary, conversation, images, and historical tool references from the model-dependent compaction threshold and shares the remainder among current tool outputs. Markdown and text are shortened near block boundaries while search and webfetch envelopes remain valid. Session-read and shell-result envelopes retain metadata and shorten text in the middle with explicit truncation markers. Session message IDs and pagination cursors are unchanged; shell exit codes, timeout state, and upstream truncation flags are preserved. If metadata alone cannot fit, the entire result is explicitly marked as omitted instead of emitting broken JSON or a partial page. Canonical results are unchanged. Historical tool output keeps a separate compact reference budget.

Ordinary input projection reserves `R = min(2048, manual ceiling M, known provider ceiling H)`, ignoring absent ceilings, plus fixed safety `S`. For context capacity `C`, the raw estimate budget is `raw_input_budget(max(0, C - S - R))`, where `raw_input_budget(capacity) = capacity * 10 // 11`. The compaction trigger uses the same inverse 10% margin after subtracting reserves from its ratio-based capacity. This reserves a useful generation turn, not the entire manual or adaptive output allowance. Every request projection is checked against the effective window of the model frozen for the run. Switching to a smaller model therefore triggers compaction before the next agent request when needed. Compaction writes a persisted `context_summaries` generation over a contiguous completed prefix and may advance within a long user turn. It keeps the latest user request and at least the last two complete current-turn tool batches in the projection and never covers a pending or partially completed batch. A covered current user message is restored only as a projection anchor, not repeatedly added back to the summary source after reload.

ContextManager receives an async raw-estimate callback backed by the same local `ProviderService.prepare_request` path used for completion. Every whole-request fit decision includes media selection, pseudonymization, tool-schema conversion, scope-matching continuation, and protocol serialization. Run attachment filtering precedes reference deduplication and estimation. To distinguish oversized history from large protected tool results, the manager estimates a copied projection with only tool bodies after the compaction boundary shortened as far as the existing shortener allows and compacts only when that request still exceeds the trigger. A separate minimum with all current tool bodies shortened determines their final shared budget. Both estimates retain unavoidable markers, short results, and privacy overhead instead of subtracting untransformed tool sizes from transformed request estimates. Character-based tool sizing remains a shortening heuristic, followed by shared request re-estimation. Preparation uses fresh original candidates without loading settings or credentials, refreshing tokens, or calling the transport. It repeats local image/privacy processing without a cache, while final completion retains its own request-scoped privacy restorer.

For text-only OpenAI-compatible Chat Completions, agent context preparation optionally counts the first candidate and final request through the same provider's `/tokenize` endpoint with its prepared messages, tools, and chat-template options. The first count calibrates local estimates for intermediate budget checks. Counts are reused by the actual counting payload and provider/model/credential/trust/privacy binding, not internal projection metadata. An oversized final count runs the existing context and optional-catalog fitting once more with the updated calibration; at most three counting requests are made per model turn. Unsupported endpoints back off for one hour and temporary failures for one minute in a bounded process-local cache. Requests time out after at most three seconds and never follow redirects. Other protocols, media, and unavailable counting retain the existing heuristic and safety reserves. Performance diagnostics record `inputTokenSource` as `server`, `server-calibrated`, or `estimate`; no local tokenizer downloads or model-name mappings are required.

After the shared preparation, ProviderService uses a server count only when its fingerprint matches the final prepared counting payload and provider binding; otherwise it takes `I = max(raw projection estimate, raw final serialized estimate)`. It adds the proportional margin once as `guardedI = ceil(1.1 * I)` and computes `min(C - S - guardedI, M, H, explicit helper ceiling Q)`, ignoring absent caps. This allowance remains local when `M`, `H`, and `Q` are all absent: compatible transports omit their output-limit option and let the provider apply its default instead of presenting the remaining context as a claimed provider capability. A present cap is still reduced by the available context and transmitted. For unchanged inputs the two estimates agree. Final revalidation remains necessary for changes such as attachment availability between passes; nonpositive output or failure to fit the required generation reserve produces a controlled context error before generation transport. There is no recursive compaction at the provider boundary. Input media estimates reserve 2,048 tokens per image and 8,192 per audio/video item or unknown opaque continuation, not a hidden media output cap. For scope-matching Responses reasoning replay, valid source-response reasoning usage plus a 256-token opaque framing allowance replaces the fixed reserve, divided across that response's opaque items with upward rounding. Missing, malformed, negative, or output-inconsistent usage retains the fixed fallback. This accounting stays local; no reasoning is removed or accounting fields transmitted. These character/media/usage heuristics are not actual-token guarantees; large inputs may require a manual output ceiling or still receive a provider error.

Host output-budget diagnostics remain separate from provider usage. Normal assistant `_matoloop.performance` records the final estimates, reserves, caps, mode, and both `allocatedOutputTokens` and `transmittedMaxOutputTokens`. The former is the computed allowance, not necessarily a transmitted or enforced limit. Codex always omits generation options; compatible transports also omit their output-limit option when no manual, discovered, or helper cap exists. Both cases record a transmitted value of `None` (`null` in JSON). Adaptive allocation has no Qwen-specific rule and changes no existing reasoning or thinking behavior for any model. See [Model Context Settings](harness.md#model-context-settings) for the full allocation, helper, transport, and migration contract; this is not a live-provider validation report.

Summary input combines chat text with bounded allowlisted operational metadata and exact tool-result retrieval references, not arbitrary stdout/stderr or complete tool-result bodies. Already-authorized chat excerpts from `session_read` also enter the same request with a separate bounded allowance, deduplicated source IDs, and explicit attribution; nested tool bodies and references are never expanded. It retains relevant status, exit codes, counts, numeric results, paths, revisions, and failures as untrusted evidence with exact message/tool/call identifiers. A deterministic bounded evidence block is appended to each persisted summary, including coverage and earlier-history retrieval anchors. This preserves operational facts without treating successful execution as proof of task completion or promoting tool output to instructions. Full canonical results remain behind `session_tool_result_read`; projection and compaction do not re-execute tools or delete their output. See [Compaction](harness.md#compaction) for the bounds.

Compaction retains its bounded 256-to-2,048-token summary target under the helper model's manual and known provider caps, reserves the effective target in full, and uses the shared prepared-request allocation instead of a separate message-size preflight. Optional model reasoning is disabled when the existing reasoning profile supports it, and only a visible response with the required summary sections is accepted. An existing summary can be compacted again at the same boundary. The configured compaction model falls back to the active model and finally a marked deterministic summary. A single monotonic 20-second deadline (or the configured request timeout if shorter) covers all model attempts, transport retries, and backoff. Compaction uses a separate short-lived database session so cancelled credential operations cannot invalidate the run's transaction. Expiry cancels provider work and selects the existing deterministic fallback after session cleanup; external run cancellation still propagates. The transcript exposes every persisted generation and marks deterministic fallbacks with a warning. Projection and compaction never edit or delete original messages; only explicit undo or retry removes its defined suffix.

After the first message is persisted, the agent run and a separate tool-free title request start concurrently. The agent task is scheduled first; title generation uses only the first user message and never blocks the run. The title inherits that first user message's trust level dynamically; manual renames retain the same classification. `chat_sessions.title_generation_status` persists `pending`, `running`, `completed`, `failed`, or `skipped`. Only `running` with an unchanged local initial title permits final update. Manual rename sets `skipped` and wins races. Successful titles publish `session.title.updated`; status-based frontend polling remains a reconnect fallback. The first output line is limited to 80 characters. Title requests keep an explicit initial ceiling of 2,048 tokens rather than all Auto headroom. Empty or reasoning-only output receives one repair attempt up to 4,096 tokens; manual and known provider ceilings still apply. Reasoning is never used as title. Provider failures, invalid second output, cancellation, and orphaned `running` states found at startup end as `failed`; the local title remains. Existing sessions were migrated as `skipped`.

## Error Contract

API, SSE, tool, and persistent chat errors use one descriptor with stable code, controlled English fallback, and optional structured data:

```json
{
  "error": {
    "code": "validation.tooShort",
    "message": "The request contains invalid data.",
    "field": "password",
    "params": {
      "minLength": 10
    }
  }
}
```

Required fields and channels:

- `error.code`: stable code for program flow and localization
- `error.message`: controlled English fallback for channels without localization
- `error.field`: optional affected input field
- `error.params`: optional values for dynamic text
- HTTP status: general failure class and fallback

English fallback text comes only from the central backend catalog. Pydantic details, exception text, and external provider responses never reach clients. Unknown syntactically valid codes remain intact with a controlled namespace fallback, or `The action failed.` when no namespace fallback exists.

The frontend localizes codes centrally in `apps/frontend/src/utils/api-errors.js` and always prefers the German translation over `error.message`. An Axios interceptor displays API failures as negative Quasar toasts. Persistent agent failures use ordinary chat message content with Host attribution in the existing metadata row, without a separate error banner or duplicate domain toast. The backend-approved retry action is a red refresh button in that row. Unknown codes use a safe frontend fallback based on HTTP status. Other channels may use `error.message` directly or localize `error.code` and `error.params` themselves.

## Notifications

Persistent in-app notifications are owner-scoped records with a host-controlled kind, bounded display-source snapshot, producer-supplied deduplication key, and monotonic read timestamp. Producers create them in the same transaction as their canonical source state; the notification service never commits. Typed targets may reference a normal session, an automation run, or a Memory approval. Deleted optional session and approval references become null; automation-run notifications are deleted with their owning automation history. Arbitrary URLs, generic source payloads, delivery state, retention, and external channels are not part of this record.

Notification bodies retain up to 4,000 source characters, including Markdown block boundaries. The notification API and Web Push share a backend-only plain-text projection, including for existing snapshots: formatting markers are omitted, links retain their labels, and code retains its text. Whitespace is collapsed after parsing. Response previews and Push bodies are limited to 500 characters; other in-app bodies retain the 4,000-character limit. Truncated previews end at a word boundary where possible and include an ellipsis. The full formatted answer remains in its source session.

The Control Center exposes one global notification center with a single chronological list. Session approvals and questions produce `approval.requested` and `question.requested` notices through the same service, unless their source session is currently visible in a focused app client. Like response notices, they are stored only until read. Clicking opens the source session, where the contextual decision controls remain. Dreaming Memory approvals instead retain their read history and link to their proposal under Memory > Dreaming; that page lists all pending Memory proposals and reuses the existing approval controls. Reading or deleting a notice never resolves an action. Badges count only unread notices. The floating Control Center button replaces the separate notification bell and opens notifications when unread notices exist; otherwise it restores the last active app. Legacy approval links open this view. The migration backfills notices for existing pending requests.

Interactive and automated answers use the same session path. Each completed answer and each new canonical runtime-error message produces a `session.response` notice unless its session is currently visible in a focused app client or the source message has already been read. The source message ID supplies the deduplication key; its timestamp supplies the notice timestamp. Response notices are stored only until read: the existing through-message read watermark deletes only corresponding older response notices, and individual acknowledgement deletes that response notice. Bulk acknowledgement marks the current unread notices read and removes read response and session-request notices; newer unread arrivals remain. Other kinds retain their read history. The frontend reloads the authoritative list after bulk acknowledgement. Acknowledging an already removed or unavailable notice is an owner-scoped no-op so stale Push clicks can still open their target. Merely opening the notification center acknowledges nothing. There is no separate automation completion or failure-delivery workflow; the original chat messages remain unaffected. Project unread indicators are derived server-side from their unarchived top-level sessions, independently of notification deletion or pagination.

Opening a focused, visible session acknowledges its existing notices regardless of the chat's unread state or notification pagination. The session read endpoint deletes session-request notices created before acknowledgement, marks other durable notices as read, and deletes response notices only through the latest displayed assistant message. Without an assistant message, it still deletes session-request notices and acknowledges durable notices without advancing the message watermark. The frontend reloads the authoritative notification list and badge after acknowledgement. Reading notices never resolves their underlying approvals or questions. A one-time data migration removes previously read response notices while preserving unread notices, durable history, and canonical messages.

The `notify` tool creates an `agent.notice` through the same service, with a bounded plain-text title and body and an owner/session target derived from the runtime context. It is intended for requested alerts and findings. A successful `notify` or `silence` result stores a host-only `suppressResponseNotification` marker on its canonical tool message. Completion checks only markers from the same session and exact run; it never infers intent from response text or the presence of a notice that might have been deleted. `notify` replaces the automatic completion notice, while `silence` suppresses it without removing the final response or changing unread state. Both tools are available in ordinary chats and automations. The agent decides whether an automation finding needs attention; in ordinary chats it uses silence for requested quiet responses, not merely short answers. Runtime errors, approvals, questions, and explicit notices already created are unaffected. Explicit notices are retained even while the session is visible; session acknowledgement marks them read without deleting their history. Response and agent-notice Push payloads use the stored title, preview and session target; Push clicks acknowledge the notification ID through the normal owner-scoped read endpoint independently of navigation. No historical response backfill is performed.

Presence leases are owner- and tab-bound and include the currently visible session. Focus loss, hidden pages and session changes release or replace that tab's lease; missing heartbeats expire after fifteen seconds. A background tab, settings page, subagent inspector or mobile overlay does not acknowledge the underlying session. Any focused app tab still suppresses Web Push for that user, including notices from other sessions.

The Control Center keeps session settings, notifications, and a separated close button outside the horizontally scrollable app tabs, with 48-pixel touch targets. Tabs have no scroll arrows; a faded edge indicates overflow. Desktop additionally offers an open-tab menu when the strip overflows. Touch scrolling and keyboard navigation remain available, and selecting a tab brings it into view.

## Automations

An automation is an owner-scoped saved task attached to one ordinary, visible session. A session can have multiple independent automations, each with zero to fifty schedules. The Automationen Control Center app lists the session's tasks and opens one definition at a time; adding the app to a new conversation uses the normal empty-session creation path. The drawer's Automationen section links to these same sessions alongside their existing project or standalone entries. No separate execution view, runtime settings copy, output chat, or result-delivery retry exists. Model, profile, workspace, files, permissions, tools, live activity, questions, and follow-up messages use the normal session paths.

Saving an automation attaches its app without changing the current tab or opening the panel. Users can also add the app manually. Closing the app tab does not delete or pause the automation. The app starts with a compact task list. Details show the task preview and human-readable schedule rows, with one schedule editor open at a time; unusual time rules are disclosed locally. Configuration and controls include a compact last-execution row with start time, live agent-run status, and a link to its original result or error message (input while no result exists). A batched query derives this row from existing run records; skipped occurrences do not replace the last actual execution. The conversation is the complete execution log, without a separate history/detail view in the app. A task without schedules or event triggers runs only on demand. Skill instructions belong in the task and use ordinary skill selection, not an automation-specific binding or activation gate. Ordinary chat messages do not edit the saved task, although their context can influence later turns. Automation input is host-marked in history and model projection, with the task name captured at enqueue. Old configuration URLs resolve to the execution session and selected automation; run links resolve to the corresponding conversation message. Compact list polling does not replace unsaved form drafts, and revision conflicts require a reload. Manual starts use only the saved task.

A schedule is a five-field cron expression with an IANA timezone or an absolute execution time. An explicitly empty, required schedule list disables time-based starts; without event triggers the task is manual-only. Cron schedules may have an inclusive end time. Existing schedule presets, validation, and exact timestamp round-tripping are reused. Enqueue stores the task revision and triggering schedules; execution uses the session's current runtime configuration. The scheduler delegates to the normal AgentRuntime. A queued task waits while the session has an active agent run; the runtime rechecks this under the normal session lock. No second session concurrency model is introduced.

AutomationRun retains scheduling bookkeeping, definition snapshots, and skipped occurrences. Simultaneously due schedules are bundled; an occurrence while an automation already has queued or active work is recorded as skipped. Missed downtime occurrences are not replayed. One-time and expired schedules are disabled. Automations have an activation flag, not an archive lifecycle. Start failures are persisted through the normal agent-error representation in the session. The app's last-execution row links to original messages instead of duplicating results. Completed agent work is never automatically retried.

`agent_response` and `agent_error` triggers cover terminal normal runs belonging to the automation owner. Enqueueing is transactional with the terminal run state and deduplicated by automation, trigger and source run. Event context contains only source references; access to message content uses ordinary authorized tools. Optional conditions are natural-language task instructions evaluated by the triggered agent, without a host filter language or session/project selector. Persisted `AgentRun.automation_origin` propagates through retries and subagents and excludes automation-originated events independently of definition deletion.

Sessions and projects have independent archive timestamps. Effective session archival is the union of its own flag and its project's flag. The drawer hides archived conversations and links to a separate archive view. Read access, history, files, grants and running work remain; new starts, retries and continuations require restoration. Archival cancels queued automation work. Restoration advances overdue schedules without replay and retains activation settings and individual session flags. Former automation archive flags migrate to disabled definitions; former skill bindings migrate to explicit task instructions.

`request_session_permissions` is callable automatically at both trust levels. It validates proposed ordinary tool arguments and reuses the executor's authorization factories and existing permission requests without invoking handlers. Built-in file/session operations and inspected isolated shell commands use their normal permission constructors; integrations use declared authorization requests. Already permitted access is reported without prompting. Otherwise the existing approval flow offers session approval or denial only when the permission supports a session grant. Disabled policies, owner/profile/trust/resource boundaries and one-time-only restrictions remain enforced by the shared resolver. This tool creates no parallel permission model and executes no probe action.

Preparation errors identify the failed `requests.<index>` entry. Names outside the effective tool set produce `tool.invalidArguments` at `requests.<index>.tool`; target argument errors retain their code and parameters with an `arguments` field prefix. Other failures identify the target entry, including explicit user denials. Targets are processed in order; earlier grants may remain after a later failure, and no target action is executed. Unavailable preparation does not establish that execution is denied or that an approval will necessarily be required. The automation prompt requires correcting invalid requests, obtaining user acceptance of possible later approval waits before enabling work with unavailable preparation, and keeping work that depends on denied access disabled. This is workflow guidance, not a new host activation gate; execution still checks permissions normally.

Built-in automation tools use owner-scoped service operations and session-bound permission scopes. Exact scopes include the definition revision. Tool creation attaches to the invoking session; editing does not rebind it. Removing an automation deletes its definition, schedules, and scheduling history, but retains its session, files, grants, and running agent. Deleting the session or its project requires confirmation of dependent automation deletion through the existing impact-check path.

Automation creation uses the `write` category and `session_read` uses `read`, following the saved trust preset unless overridden and retaining their ownership and session boundaries. Listing defaults to the current session; `scope=all` uses the ordinary owner-wide read permission. Reading and editing a stored automation of the current session is automatic unless the capability is disabled. The permission policy verifies the actual stored owner, execution session, and revision; the invoking session in a request scope is not proof of the target's session. Other-session reads/edits retain their configured policy. Creating an automation does not authorize its future shell, file, or integration actions. Explicit creation/session-read overrides and profile restrictions remain effective.

Before each top-level model request, the host reads current owner-bound definitions from that exact session, including disabled tasks, revisions, schedules, triggers, and effective next scheduled starts. A fresh query updates the context after tool or UI changes. Definitions are added after the base conversation projection, using the same prepared-request input-budget check as repository instructions. Full definitions fall back to a compact catalog with task excerpts, schedule counts, and a count of omitted definitions; full details remain available through `get_automation`. If even a compact catalog does not fit, it is shortened or omitted rather than overflowing the conversation. Both optional context blocks share the remaining request budget. An empty catalog means no session automations only when its omitted count is zero. Definitions are descriptive data, not instructions to execute saved work or permission grants. Current-session configuration is regular session context; automation access follows the session-local rule above. Delegated sessions do not receive their parent's definitions implicitly.

Migration makes existing hidden execution sessions ordinary chats in place, preserving their IDs, transcripts, files, and grants. Historical output-chat copies remain, but new results appear only in the execution session. Legacy delivery configuration is removed, pending copied-result deliveries are retired, and redundant automation notifications are deleted. Historical delivery columns on run records remain for old message attribution and diagnostics.

## Frontend Interaction

The change stream rechecks the login and account before sending events whenever its fifteen-second authorization deadline is due, including under continuous traffic; invalid logins close the subscription. Tool-result-only message writes remain on the run stream and do not invalidate project or sidebar lists. Reconciliation waits for initial reads and reissues list reads invalidated by concurrent summary updates. Failed transient REST reads retain their affected invalidation and retry with exponential delay capped at thirty seconds; successful reconciliation stops retries, and new events do not wait for an old retry delay.

The application shell uses one authenticated, owner-scoped `/api/events` SSE connection per tab instead of periodic list and session polling. The backend's database sessions collect invalidation hints for tracked ORM and bulk writes and publish them only after the outer transaction commits. Hints contain resource names and optional session IDs, not content. PostgreSQL notification inserts record their hint explicitly. Global settings invalidate all connected owners; other changes remain owner-bound. Like run streaming, delivery is process-local in the supported single-worker backend, without Redis or a durable event log.

Subscriptions are registered before their initial full-reconciliation hint. The frontend reloads affected resources through existing REST endpoints, coalesces bursts, and reconciles again on reconnect and tab visibility restoration. A slow subscriber gets a bounded full-reconciliation hint rather than an unbounded backlog. SSE heartbeats detect stalled connections; there is no periodic REST fallback. Background tabs update notification badges but defer other views until visible. Presence keeps its separate heartbeat because a connected stream does not mean the user is viewing a session. Session refreshes retain at most one waiting follow-up so events arriving during a read are not lost; pending-approval reads no longer implicitly reload grants, and grant views refresh only while visible.

The desktop Home computer area shows clickable computer names with green online or red offline computer icons. Selecting a name updates the current new-session draft through the chat store, including the computer's home directory, and follows the same disabled state as the start options. The computer dropdown reflects that selection. Status is included in accessible names without extra visible text or tooltips.

The authenticated start route `/` opens Home, the overview state of the existing chat page. `/chat` remains an alias and `/dashboard` redirects to the same entry point, preserving query parameters and hashes. Home prioritizes resuming a conversation: a compact personal greeting, pending approvals/questions, six recently active conversations across projects, at most two upcoming effective automation schedules, and a compact computer-connectivity link share the scrollable area above the composer. On viewports below 600px, the recent-conversation section and computer-connectivity link are hidden; the greeting and other Home content remain visible. Conversation transcripts remain visible on mobile. The existing composer stays docked at the bottom in Home, new-session, and conversation views. Sidebar plus actions use `new=1` to open a blank new-session view without the overview; project actions retain their project scope. Both start views reuse the same draft, attachment, and send path. Opening either view alone creates no session; the existing send and session-bound Control Center flows create it when needed. Home does not autofocus the composer on desktop or mobile, while an explicit new-session action focuses it. Existing project-scoped drafts remain in the chat store when navigating away and back. Recent conversations use `sort=recent` on the existing owner-scoped session list, ordered by the latest visible message timestamp (or creation time for empty sessions) without pin priority; the sidebar retains pinned-first behavior. Pagination cursors are scoped to the chosen order. The existing visible-shell refresh updates recent conversations while Home is open. Unavailable data is distinguished from zero counts, and failed loads offer an explicit retry without a general refresh button.

New-conversation composers expose equal-width, equal-height dropdowns for session template, project, memory, and web search, in that order, in both Home and the blank new-session view. Below 600px, the four controls form a centered two-column grid; project creation appears in the project menu. The computer remains separately selectable. Only selected projects show a clear action. Once a session exists, computer, memory, web search, available agents, and model overrides are edited through Control Center > Session; agent, model, and reasoning remain in the composer. The sidebar and composer reuse the same project editor; its caller decides whether a newly created project starts a blank session or is selected for the current draft. Changing the project keeps the current view and moves unsent text, attachments, and recovery recordings only after navigation succeeds and only into an empty destination draft. Scope-specific settings stay with their project. If the destination already contains a draft or queued messages, users can open that existing state while retaining their source draft, or cancel. Draft transfer never overwrites an occupied destination. Project changes are disabled during pending sends, session creation, or settings changes.

Quasar components form the primary UI layer. Pinia stores hold server state; components coordinate presentation and user action.

Sidebar conversations use only pinned and recent groups, retaining the server's order. A shared minute clock updates compact activity timestamps, including pinned conversations. A leading status slot aligns titles with navigation labels and prioritizes required approvals and questions over active work and unread responses. Pinning is a direct row action: pinned conversations keep a blue pin visible immediately left of the right-aligned timestamp. Desktop hover, keyboard focus, or an open menu replaces the timestamp with right-aligned menu and pin controls without changing the title width; automation rows show only the menu. Touch layouts keep the timestamp and both controls directly available. The sidebar scrollbar appears automatically during interaction. Automations start collapsed with a persistent count and expand when their execution session becomes selected. Their list includes the execution session's latest user or assistant message time, falling back to session creation for empty conversations, without requiring the session to be opened. Routine automation status is available on the title rather than repeated as a second line.

Provider management separates instance and personal contexts. **Administration > Provider** opens on **Einstellungen**, which owns the personal-provider gate; **Verwaltung** is second and manages instance providers and models. **Einstellungen > Provider** directly manages only the signed-in user's personal providers, including for administrators. Administrators can access and load their own providers even when the personal gate is disabled. Settings open on personalization by default. Creation inherits the page's scope without an ownership selector. Disabling personal providers preserves their configuration and does not affect shared model availability in chat and agent profiles.

Administration edits global catalogs; Settings edits owner-scoped configuration. Two-tab sections open **Einstellungen** before **Verwaltung**, except direct editor/OAuth returns. Persona catalogs, assignments, and assistant name are under management. Profile editors hold workflow fields and links under **Weitere Einstellungen**, not model assignments. **Standardmodelle** and **Sessionvorlagen** own model configuration. Permission requests persist optional structured display items alongside their authorization snapshot. The backend supplies resolved domain values that cannot be reconstructed safely from sanitized tool arguments, while the frontend uses one presentation path for approval cards and ordinary tool history. Approval cards may select a compiled tool-specific presentation from a static frontend registry; missing or incomplete registrations fall back to the generic structured presentation. Administration > Tools has three tabs: **Einstellungen**, **Tool-Einstellungen**, and **Berechtigungen**. Tool availability changes take effect when the next tool offer is built. This is not immediate revocation of already offered or started calls in a running model round. Existing execution and post-approval checks remain effective; cancellation does not undo completed external effects.

The existing resolver applies configured rules in their normal precedence, then an optional `ToolAction.default`, then the selected preset's category baseline and named automatic capabilities. ## Runtime Data

The development stack uses named volumes:

```text
app_data -> /data
db_data  -> /var/lib/postgresql/data
```

Additional named volumes hold Python and frontend dependencies. The repository is mounted at `/workspace` for HMR.

The production Compose stack starts the `matoloop-agent` service with exactly `MATOLOOP_AGENT_DATA:/data` and `MATOLOOP_AGENT_HOME:/workspace`. The production environment template sets these host paths to `/opt/matoloop-agent/data` and `/opt/matoloop-agent/home`; Compose retains the former relative fallbacks for existing deployments. The development service keeps the Agent state bind mount, uses the project-scoped `matoloop_agent_workspace` named volume at `/workspace`, and additionally mounts the source tree at `/source` and a disposable dependency volume. Development `reset-storage` therefore removes the Agent workspace along with the other named volumes. Agent configuration is `/data/config.json`; credentials and durable state also remain below `/data`. These paths are not backend-managed storage. The backend does not migrate or delete agent home contents. Interactive pairing asks for the backend WebSocket URL, computer ID, and one-time token. Non-interactive pairing requires the complete `MATOLOOP_AGENT_BACKEND_URL`, `MATOLOOP_AGENT_ID`, and `MATOLOOP_AGENT_PAIRING_TOKEN` set. Old environment aliases are unsupported. The container currently runs as root, so these mounts and deployment policy, not MatoLoop model policies, define its operating-system scope.

Deleting a deactivated account removes its relationally owned records and backend session trees. Database deletion revokes the backend's `ExecutionAgent` records and credentials, but the backend does not erase files, caches, durable agent state, or configuration on any MatoLoop Agent, including the bundled Compose agent, nor data already written to an external service. Operators must remove those separately. Shared instance resources and credentials remain because they have no user owner.

The production stack uses the two application bind mounts and adds the MatoLoop Agent `/data` and `/workspace` mounts. `docker-compose.no-agent.yaml` is the production alternative without the agent service or its settings:

```text
/opt/mato-loop/data -> /data
/opt/mato-loop/db   -> /var/lib/postgresql/data
```

The production SPA is served by the MatoLoop container together with FastAPI. The development stack keeps separate frontend and backend processes for HMR. The production stack is not used for development work.

## CI and Release Boundary

GitHub Actions verifies changes and publishes OCI images to GHCR and GitHub releases; it never deploys MatoLoop or accesses deployment storage. Forgejo remains a Git pull mirror with Actions disabled. Its workflows stay under `.forgejo/workflows`, alongside `.github/workflows`; shared helpers use neutral names and receive the host API URL, repository, and token from each workflow. Pull requests build without secrets and feature branches retain no images. Both `develop` and `main` use branch-independent `YYYY-MM-DD-<SHA8>` versions derived from the UTC commit date. Immutable image tags match these versions; moving aliases are `develop` and `latest`. Python/npm package versions are fixed packaging placeholders. Both application images currently target `linux/amd64`. Agent setup and updates use the running backend's full commit SHA, frozen per operation, instead of tracking a branch. Missing or dirty build metadata cannot supply a reproducible target; local development checkouts remain separate. Native Agents and managed Docker Agents stage and verify that commit with stamped package versions; the container launcher reuses environment preparation and completion reporting without systemd. Version equality is not a connection requirement. Container updates survive restarts but image recreation restores the image's source version. See [computer-maintenance.md](computer-maintenance.md) for lifecycle details and [ci-and-releases.md](ci-and-releases.md) for publication and rollback.
