# Session templates and model defaults

Agent profile documents define workflow and permissions. `model-defaults` settings hold global model assignments and optional owner-bound overrides for the agent model, reasoning, compaction, titles, dreaming, vision, video, audio analysis, image generation, speech generation, audio generation, and transcription. They also hold `profileModels`, a map from agent profile ID to optional chat-model and reasoning overrides. Null means inherit; a false title-vision switch remains an explicit override. Provider/model availability and capabilities are still validated. Profile assignments share the existing personal-model-default gate and administrator exception; instance assignments can reference only instance profiles and models. The settings page uses the same agent-profile selector as tool settings: Standard edits all defaults, while a selected profile edits only chat model and reasoning.

Persisted `ai` documents use `AiProviderSettings` and `UserAiSettings` for provider inventory only. `load_effective_ai` combines that inventory with model defaults into the runtime `AiSettings` projection. Obsolete default fields in old inventory documents are ignored and disappear when the document is saved. Provider mutations clean only the authoritative model-default documents; auxiliary requests no longer load an unused agent profile.

`session-templates` settings contain global or personal named templates. Each template selects available agents, a start agent, the existing `full`, `read_only`, or `disabled` memory mode, an optional session-wide chat model and reasoning effort, and optional chat-model/reasoning overrides by agent ID. Auxiliary model overrides do not belong to templates.

- **Allgemein** (internally Default) selects Allgemein and Sysadmin, starting with Allgemein, with standard-size messages and worktree support disabled.
- **Coding** selects Plan and Build, starting with Plan, with small messages and worktree support enabled.
- Both start with full memory and inherit model defaults unless configured otherwise.
- Global and personal management use the existing administrative scope and owner boundary. Each feature has its own personal-setting gate, initially enabled. Administrators retain the established personal exception.

## Session behavior

Templates and the Session Control Center expose `messageSize` (`standard` or `small`). The size is copied into `chat_sessions.session_profile` on creation and template selection and can then be changed per session. Small messages use smaller text, Markdown headings, and code, with tighter line, paragraph, message, and user-bubble spacing. Switching sizes recalculates the virtual transcript heights. Existing sessions without a size remain standard; template edits do not rewrite sessions. Agent profiles have no presentation setting.

Home and the blank-session composer show four equal-size fields in this order: project, workspace, template, memory. At less than 600px they use a centered two-column grid. Web search is configurable in the existing Session Control Center. Projects can select a default session template alongside the computer and working directory. Creation and preview prefer an explicit template, then the project's template, then the general template. Template references are owner-validated when assigned. An unavailable reference must be replaced or explicitly overridden; existing sessions and configured drafts are not rewritten. Fresh drafts reload the current project defaults.

Plan and Build (including derived profiles) require a connected owner-bound computer with the required file operations and an accessible working directory before execution. These prerequisites are checked by the host before model work. Planning still requires relevant source evidence; a working directory alone does not identify a repository.

Accepted session requests report execution and prerequisite failures through persisted host messages, not duplicate API-error toasts. The message projection derives `state` (`normal` or `error`) from existing error data and exposes `origin=host` for host messages. The frontend localizes controlled error codes and shows `Host` in the model-name footer with the existing retry action. Pre-execution failures record `beforeExecution` in host metadata; retry uses current session configuration and repeats the same checks. Started executions retain their existing retry snapshots. Authentication, invalid input, ownership checks, and failures that cannot be persisted remain API/transport errors.

The read-only `POST /sessions/defaults` preview accepts the same typed session options as creation, including per-agent overrides. Initial loading, template selection, and manual draft changes share this preview. The frontend applies its effective memory state rather than maintaining a second memory-policy calculation. Late responses cannot replace a newer draft or template choice.

Sending a new-session message or opening a session-bound app waits for pending defaults for that draft. Model availability in session options and owned-computer revocation are execution prerequisites, so accepted messages report them through the persisted host error path. Template/settings editing keeps immediate availability validation. Once execution begins, the input message retains an `executionStarted` host marker across retries; later preparation failures cannot make an already-started request eligible for rebinding to current session configuration.

Creation copies the selected template into the session: agent selection, per-agent model overrides, and the source template ID live in `chat_sessions.session_profile`; the existing model, reasoning, and memory columns store session-wide values. The optional source ID is display metadata, not a live dependency; older sessions without it remain valid. Editing or deleting the original template does not rewrite sessions.

The Session Control Center offers template selection and direct agent, computer, memory, web-search, model, and reasoning controls. Selecting a template replaces the available agents, active agent, memory mode, and all session/agent model and reasoning overrides with its current values, including inherited values. Project, computer, working directory, and web-search settings are independent. Users then adjust the selected agent's model and reasoning locally; the agent list itself is edited in template management.

Templates expose `worktreesEnabled`, defaulting to false for custom templates and true for the shipped Coding template, including older stored Coding templates without the field. The value is copied into the session profile; no relational schema change is needed. For new sessions, the selected template controls whether project worktree defaults and explicit worktree selection are available. Disabled templates always inherit a local workspace; explicit worktree creation requests are rejected. Selecting another template in a draft reapplies the project's workspace default only for a matching computer and directory; otherwise the draft stays local. Ordinary draft edits preserve a manual local/worktree choice while normalizing explicitly disabled support to local. Older drafts and queued requests without the support flag retain their selected mode; the backend validates worktree support at creation. This is session workflow configuration, not a tool permission, and ordinary Git use is unaffected.

Once a session has a managed worktree, both the UI and backend reject template selection without worktree support, even between runs. Computer and directory remain bound to the worktree, while agent switching within the template remains available. Existing sessions are not rewritten, detached, or deleted; legacy sessions without worktree support metadata can still edit their settings without changing the binding or template. Template edits never change existing session snapshots or remove worktrees.

Model and reasoning values resolve independently: session override for the selected agent, session-wide override, allowed personal profile defaults, global profile defaults, allowed personal standard defaults, global standard defaults, then the provider's documented reasoning default. Personal profile values inherit missing fields from the global profile assignment, including when a personal standard is configured. An unavailable personal profile model also retains the global profile model as its fallback. Inherited reasoning unsupported by the selected model falls back to that model's default without rewriting stored choices. Saving model defaults revalidates explicit profile reasoning against its proposed inherited model, including unchanged and omitted profile assignments. Composer model/reasoning selections edit the current agent's session override. Agent switching uses that agent's effective model. Auxiliary requests use model defaults and their existing active-model fallback rules. Native child sessions retain the parent's selected model and resolved reasoning and keep their existing memory/permission restrictions.

When no agent-model default is configured, the runtime selects the first available chat model with tool support in inventory order (global models, then permitted personal models). This effective fallback is not persisted. Global administration resolves only global inventory and defaults. Model-default settings display the automatic candidate; session previews and runtime use the same central resolution. Auxiliary and media model assignments keep their existing fallback rules.

The runtime checks the session's available-agent list as well as current owner and instance availability. This list is session configuration, not an additional authority grant. Changes use the session-settings lock and apply to later runs; an active run retains its previous session configuration. Session model resolution skips unavailable references and models without tool support in the precedence chain and uses the next available agent model, including the effective default. When this changes the selected model, an unsupported reasoning effort falls back to the model's default without rewriting stored settings. Without an available candidate, the UI asks the user to select a model. Deleted and missing models are omitted from selectors. Unchanged stale per-agent model references may remain when editing a session; newly assigned models must pass validation.

## Migration

Revision `ee5db377dca5` removes obsolete answer-display values from agent-profile documents and initializes template message sizes, using small for the shipped Coding template and standard for other templates. Existing sessions are untouched. Downgrade removes template/session sizes; removed answer-display values are not restored.

Revision `870fad9fb7e7` adds the JSONB session configuration, initializes both templates, moves the former global default agent's model settings into `model-defaults`, and removes model fields from agent documents. It transfers built-in chat-model/reasoning overrides to the matching templates and preserves effective chat-model choices for existing sessions without constraining their formerly unrestricted agent selection. Explicit session choices retain precedence during migration.

The former model fields of each agent document are retained in inactive `agent-models-archive` settings. Conflicting auxiliary choices and custom-profile choices not represented by the two shipped templates remain there for reference rather than introducing a hidden legacy runtime layer. Downgrade restores these archived fields on surviving profiles and removes the new template/default documents and session configuration column; it cannot retain edits made only in the new configuration model.
